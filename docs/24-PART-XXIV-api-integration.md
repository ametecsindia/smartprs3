## XXIV.0 Purpose

This part decides three things.

1. **That SmartPRS 3 has one public, versioned, documented HTTP API — `/api/v3` — and that
   the product's own SPA is a client of it and of nothing else.** SmartPRS 2 has no public
   API in any meaningful sense; it has 422 route declarations, almost all of them
   session-authenticated SPA endpoints returning view-shaped payloads that no third party
   could depend on. The commercial consequence is that Ametecs cannot today sell an
   integration, cannot onboard a partner, and cannot let a customer's accounting system
   read a payroll register without writing bespoke PHP.
2. **That every crossing of a product boundary — inbound or outbound, SmartEPT, SmartDCM,
   the Smart Biometric Bridge, a bank, an ERP, a messaging provider — is a versioned
   contract over HTTP, never a shared table and never a shared database.** This is stated
   as an architectural prohibition with its rationale, because the cheapest short-term
   integration in a multi-product family is always the one that reaches into the other
   product's schema, and it is the one that makes both products unshippable thereafter.
3. **That the integration layer is configuration, not code**: a connector is a declared
   recipe with a declared capability set, a credential referenced by handle, an egress
   profile, a timeout, a retry policy, a circuit breaker and a high-water mark — none of
   which exist in SmartPRS 2, where every timeout is the literal `60` and the string
   `->retry()` does not appear anywhere in the codebase (`NEW-C-25`).

The three routes in `routes/api.php` plus the three in `routes/smartept.php` are the entire
machine-facing surface: `GET /api/v1/ping`, `POST /api/v1/attendance/punches` (the Smart
Biometric Bridge ingest) and `POST /api/v1/webhooks/smartept/{slug}` (C §1.3, §1.4). Every
other capability of the product — employees, payroll, leave, statutory, documents, reports
— is reachable only through a session cookie against an endpoint whose response shape is
whatever the 12,533-line `AppController` SPA happened to need that week (G D-14). Those
payloads are **view-shaped**: `/app/data` returns a fixed 62-field employee projection
chosen for one screen, including `ctc`, `pan`, `uan`, `bankAcc`, `ifsc`, `homeLat`,
`homeLng` and every reference's Aadhaar and PAN, with no field-level allow-list
(`AppDataController.php:302-424`; G §5.2 item 4). No third party can build against that,
and no version of it can be deprecated, because nothing declares what it promises.

**Consequence for the rebuild.** A public API cannot be retrofitted onto endpoints designed
as view models. SmartPRS 3 therefore inverts the dependency — §XXIV.2.1.

### XXIV.1.2 API keys are well engineered and gate nothing

`ApiKeyAuth` / `ApiKeys` is, in the analyst's words, *"the single best-engineered security
component in the codebase"* (G §9): the secret is `sk_prs_<4>_<40>` with ≈238 bits of tail
entropy, only its SHA-256 is stored, comparison is `hash_equals`, tenant binding is
enforced, and an `ingest`-scoped key with `tenant_id = NULL` is refused
(`ApiKeys.php:32-47`; `ApiKeyAuth.php:67-69, 103-114`; BR-SEC-008, BR-SEC-009).

Two scopes are issuable from the API Keys screen: `ingest` and `read` (C §1.9). **`read`
gates nothing.** There is no endpoint that a `read` key can reach, because there is no read
API; the scope is a checkbox that changes no behaviour. C requirement 36 states the rule
that follows: *"Scopes MUST actually gate something; a declared-but-unenforced scope is a
lie."*

Further gaps in the same component: there is **no rotation** — keys are revoke-only, so
changing a key means an outage for the integration that holds it (`NEW-C-15`); there is no
per-key IP allow-list; and rate limiting is per source IP rather than per credential, which
is wrong for the dominant deployment shape where many devices share one NAT address
(`NEW-C-21`).

### XXIV.1.3 The webhook signature is correct, and the webhook is replayable

`SmarteptSignature` verifies `hash_hmac('sha256', $rawBody, $secret)` with `hash_equals`
over the **raw** body bytes and answers one uniform 401 for every failure class
(`SmarteptSignature.php:33-87, 56-66`; `SmarteptWebhook.php:122-130`; BR-SEC-010). The
secret is `whk_ept_<48>` (≈285 bits), `Crypt`-encrypted at rest, and rotatable while keeping
the endpoint URL (C §1.9, §4.12). All of that is correct and is kept.

**What is missing is replay protection.** The signature covers the body and nothing else:
no timestamp header, no nonce, no freshness window (`SEC-C-16`). An observer of one signed
request — from a proxy log, from a plaintext hop, from an error report — can replay it
indefinitely.

The mitigation that exists is accidental. A replayed payload lands on the same derived
idempotency key, `ept_` + `sha256('smartept|company|identity|DIRECTION|Y-m-d H:i:s')`,
which deliberately excludes `sent_at` so a retry reproduces the id
(`SmarteptWebhook.php:282-287`), and the database's `attlog_natural_unique` index turns the
second insert into a no-op. But **that index leads with `tenant_id`, and in MySQL a NULL
never collides with a NULL** — so on any install whose rows carry a NULL tenant (the three
self-hosted installs, and every `/iclock` auto-registered device row, `BR-DEV-001`) the
index is inert and de-duplication rests entirely on `updateOrInsert`
(`2026_08_16_000200_extend_attendance_logs_for_sbb.php:19-28`; C requirement 18). And even
where the index does bite, a replayed `attendance.daily` payload **for a different date** is
fully accepted, because the date is part of the signed body an attacker chooses to resend.

So: the one correctly signed webhook in the product is protected against replay by a
database index that is switched off exactly where the product is least supervised.

The Generic API connector is the only part of SmartPRS 2 that already embodies "change
configuration, not code" (C §9), and it is also the most dangerous component in the
integration layer.

| Behaviour | Evidence | Consequence |

## XXIV.2 API-first architecture *(brief Section 82)*

### XXIV.2.1 The principle

**R-XXIV-001** `/api/v3` is the **only** programmatic surface of SmartPRS 3. There is no
second, private, SPA-only endpoint family. The React SPA authenticates as a first-party
user client and calls the identical routes, with the identical serialisation, the identical
authorisation and the identical error envelope as a third party would.
*Test: a CI sweep asserts that every route registered by the application is declared in the
published OpenAPI document, and that no controller is reachable from more than one route
prefix.* *(Spine S2 front-end decision; SmartPRS 2's two front ends and view-shaped
payloads, G D-14.)*

**R-XXIV-002** No endpoint returns a payload whose shape is determined by a screen. A
resource representation is defined once, in the resource schema, and screens select fields
from it (§XXIV.2.8). *SmartPRS 2's `/app/data` returns a fixed 62-field projection built for
one screen, salary and Aadhaar included, with no field-level control
(`AppDataController.php:302-424`; G §5.2 item 4).*

**R-XXIV-003** Every response is derived from the same domain services as the UI. There is
no API-only calculation path and no UI-only calculation path, because a divergence between
them is a defect that neither side's tests can see.

### XXIV.2.2 Resource design and URL grammar

```
https://{host}/api/v3/{collection}[/{uuid}[/{sub-collection}[/{uuid}]]][/{action}]
```

Rules, all enforced by the route-declaration linter:

| Rule | Statement |
|---|---|
| Nouns, plural, kebab-case | `/salary-structures`, not `/getSalaryStructure` |
| Identifiers | **UUIDv7 only.** A route whose path parameter is typed as an integer fails the build (spine S2) |
| Nesting depth | Maximum two levels. Deeper relationships are expressed as filters on a top-level collection |
| Verbs | Only where a state transition is not a resource: `/approve`, `/publish`, `/recalculate`, `/freeze`, `/void`. A verb endpoint is always `POST` and always idempotency-keyed |
| Methods | `GET` (safe, cacheable), `POST` (create, action), `PATCH` (partial update — **the only update semantic**), `DELETE` (soft delete / archive; never a hard delete, spine S16) |
| PUT | **Not used anywhere.** A full-replace update is how SmartPRS 2's employee save nulls every omitted key (spine S9); the method is removed rather than documented as dangerous |
| Effective dating | Every resource whose domain is effective-dated accepts `?as_of=YYYY-MM-DD` and defaults to today (spine S4) |
| Tenant | Never a path or query parameter. Tenant is derived from the credential, always (spine S13; `BR-TEN-002`, where NULL and 0 mean "all tenants") |

**R-XXIV-004** A path parameter is a UUID or a stable business **code** from a value set
(e.g. a component code, a leave type code). It is never a display name and never a
sequential integer. *(Spine S2; G §7.4 — 18 IDORs reachable directly from a route parameter,
354 id-only queries behind them.)*

**R-XXIV-005** `PATCH` has strict patch semantics: only supplied fields change; clearing a
field is an explicit `null` in the request body distinguished from omission; and the write
goes through the single `EntityWriteService` path (spine S9). *Test: a `PATCH` with one
field asserts every other field unchanged, including custom fields.*

### XXIV.2.3 Versioning, deprecation and sunset

**R-XXIV-006** The major version is in the path (`/api/v3`). There is exactly one supported
major version at a time in a release train, plus at most one in sunset.

**R-XXIV-007** Within a major version, changes are **additive only**. The following are
**breaking** and may not ship inside `v3`:

| Breaking | Not breaking |
|---|---|
| Removing or renaming a field, resource, endpoint, enum value or error code | Adding an optional request field |
| Changing a field's type, unit, currency or nullability from non-null to null | Adding a response field |
| Changing the meaning of a value without changing its name | Adding a new enum value **to a field the contract declares as open** |
| Making an optional request field required, or adding a required field | Adding a new endpoint, resource or sub-resource |
| Tightening validation such that a previously accepted request fails | Adding a new optional query parameter |
| Changing default sort order, default page size or default filter | Loosening validation |
| Changing an HTTP status code for an existing outcome | Adding a new HTTP status for a genuinely new outcome |
| Changing pagination or the error envelope | Adding a header |
| Changing authentication or narrowing a scope's reach | Adding a new scope |

**R-XXIV-008** **SMARTPRS 3 ARCHITECTURE RECOMMENDATION.** Every enum-typed field in the
schema declares itself `closed` or `open`. A
client is contractually required to tolerate unknown values on an `open` enum. Every status
vocabulary in SmartPRS 3 is a reference table (spine S16), so status enums are **always**
`open` — this is what allows a tenant to add a leave status without a major version.

**R-XXIV-009** Deprecation is announced in the response, not only in a changelog. A
deprecated endpoint or field returns:

```
Deprecation: Sat, 01 Aug 2026 00:00:00 GMT      -- RFC 8594
Sunset:      Sat, 01 Aug 2027 00:00:00 GMT      -- RFC 8594
Link:        <https://developer.ametecs.com/api/v3/changelog#dep-0142>; rel="deprecation"
Warning:     299 - "field `employee.department_name` is deprecated; use `employee.org.department.code`"
```

**R-XXIV-010** Minimum notice periods, held as platform configuration (not tenant-editable,
because a customer cannot be permitted to shorten another party's migration window):

| Change class | Minimum notice before removal | Default |
|---|---|---|
| Field deprecation within `v3` | 6 months | 12 months |
| Endpoint deprecation within `v3` | 12 months | 12 months |
| Major version sunset (`v3` → `v4`) | 18 months | 24 months |
| Emergency security change | Immediate, with a named approver and a published advisory | — |

**R-XXIV-011** A deprecated element emits `api.deprecated_element.called` per credential per
day, so Ametecs can tell a partner exactly what they are still calling before the sunset
date, and can tell whether a sunset is safe. *SmartPRS 2 cannot answer "who is using this"
about any endpoint, because nothing is instrumented per credential.*

**R-XXIV-012** After the sunset date the endpoint returns `410 Gone` with error code
`api.endpoint_sunset` and a `Link` to the migration note. It is never silently removed and
never returns 404.

### XXIV.2.4 Authentication

Three credential types. All three resolve to the same `(principal, tenant, permissions,
data-scope)` tuple before any handler runs.

| Type | Grant | Subject | Use | Lifetime |
|---|---|---|---|---|
| **OAuth2 client credentials** | `POST /api/v3/oauth/token`, `grant_type=client_credentials` | A **service principal** owned by a tenant (or by Ametecs for a platform integration) | Partner and server-to-server integrations | Access token ≤ 60 min (configurable, platform floor and ceiling); no refresh token — re-request |
| **Scoped API key** | Minted in the Integration Console, shown once | A service principal | On-premise agents (SBB), scripts, device collectors, low-capability clients | Configurable expiry, mandatory maximum; rotation with overlap |
| **User token** | Session exchange (first-party SPA/mobile) or `authorization_code` + PKCE (third-party acting as a user) | A **human** user | The SPA, the mobile app, and any partner acting on a named user's behalf | Access ≤ 15 min, refresh with rotation and reuse detection |

**R-XXIV-013** Every credential is bound to exactly one tenant, resolved from the credential
and never from the request. There is no credential that can address more than one tenant.
Cross-tenant platform operations use a distinct **platform** principal that must additionally
hold `platform.cross_tenant`, whose every use writes an audit row naming the tenant accessed.
*SmartPRS 2 treats `tenant_id` NULL **or 0** as "no tenant filter at all", inherited by
`platform_support`, which has zero checks anywhere (`BR-TEN-002`, `SEC-05`, G §7.1 #16).*

**R-XXIV-014** API key material is stored hashed (SHA-256 or better) and compared with
`hash_equals`; webhook secrets, which must be recomputed, are encrypted with a managed key.
This split is exactly SmartPRS 2's, and it is correct — it is retained deliberately
(`ApiKeys.php:32-47`; `SmarteptWebhook.php:99`; C requirement 34).

**R-XXIV-015** API keys support **rotation with an overlap window**: `POST
/api/v3/integrations/credentials/{uuid}/rotate` issues a successor, both keys authenticate
until `overlap_ends_at`, the console shows which key each call used, and the predecessor is
revoked automatically at the end of the window. *SmartPRS 2 offers revoke only, so rotating
a key means an outage (`NEW-C-15`).*

**R-XXIV-016** A credential may carry an optional **IP allow-list** (CIDR). An empty
allow-list means unrestricted; a populated one is enforced before the key hash is compared.
*(C §9 "add rotation, a real scope model, per-key IP allow-list".)*

**R-XXIV-017** Every credential-bearing request MUST be over TLS. Plaintext HTTP on an API
route returns `426 Upgrade Required` and the credential presented is **revoked** and its
owner notified, because it must now be assumed disclosed. *(`SEC-C-15`; C requirement 37.)*

**R-XXIV-018** Authentication failures are uniform: one `401` shape for absent, malformed,
unknown, expired, revoked and mis-scoped-tenant credentials, with the distinguishing detail
present only in the server-side security log. *SmartPRS 2 already does this correctly on the
SmartEPT webhook (`BR-SEC-010`) and incorrectly on login, where a second lookup reveals that
an account exists but is disabled (`AuthController.php:292-295`, `SEC-13`).*

**R-XXIV-019** MFA is mandatory for any human principal holding a privileged permission
(payroll approval, user administration, credential minting, rule publication, cross-tenant)
— including when that human authenticates to the API (spine S13).

### XXIV.2.5 Scopes, and how they map to permissions

A scope is **not** a permission. A scope is a **ceiling** the credential's holder placed on
what that credential may be used for. The permission model of Part XXII decides what the
principal may do at all.

```
effective_permissions(request) =
        permissions(principal)          -- Part XXII: role → permission bundle
      ∩ permissions_implied_by(scopes)  -- this part: scope → permission set
      ∩ endpoint_required_permissions   -- declared on the route

data_scope(request) = data_scope(principal)        -- Part XXII, unchanged by scopes
```

**R-XXIV-020** A scope can only ever **narrow**. Granting a scope to a credential whose
principal lacks the underlying permission grants nothing, and the console shows the
grant as ineffective rather than silently accepting it. *SmartPRS 2's `hr_manager` can create
an `admin` and set any user's password — an assigner exceeding their own authority
(`SEC-07`); the same rule applies to credentials.*

**R-XXIV-021** Every scope maps to a declared, closed set of permissions in a platform-owned
registry. Scope naming mirrors the permission grammar of Part XXII:

**R-XXIV-022** Every route declares its required permission(s) and the scopes that may carry
them. **A route with no declaration fails the build.** *Test: the route-declaration sweep
that spine S13 requires is extended to assert a scope mapping as well as a policy binding.*
*(G requirement 26: "adding a new route with no explicit permission declaration MUST deny by
default"; today 78 authenticated routes have no check because nobody wrote one.)*

**R-XXIV-023** A scope in the registry that maps to no reachable endpoint **fails the
build**. This is the direct, mechanical fix for `read`, which SmartPRS 2 issues and never
enforces (C §1.9, requirement 36).

**R-XXIV-024** Scopes are requested at credential creation and are immutable thereafter;
widening requires a new credential. Narrowing is permitted and takes effect immediately.

**R-XXIV-025** The response to a scope failure is `403` with code `auth.insufficient_scope`,
naming the scope required and the scopes presented — never the permission model's internals.

### XXIV.2.6 Rate limiting and quotas

**R-XXIV-026** Rate limits are **configuration**, resolved through the spine S4 artefact
model, not literals. *SmartPRS 2 has 34 literal `throttle:n,m` strings in one route file
(G §0.4).*

**R-XXIV-027** The limit key is, in order of precedence: **credential** → tenant → endpoint
class. IP is a fallback for unauthenticated endpoints only. *SmartPRS 2 throttles the device
ingest path per source IP, which is the wrong key when a hundred devices share one NAT
address (`NEW-C-21`).*

**R-XXIV-028** Endpoint classes and their default budgets (all configurable per plan and per
credential; these are defaults, not constants):

| Class | Examples | Default | Burst |
|---|---|---|---|
| `read.light` | Single resource `GET` | 600 / min | 60 |
| `read.collection` | List, filter, search | 120 / min | 20 |
| `read.report` | Report execution, exports | 10 / min | 3 |
| `write.single` | `POST`, `PATCH` on one resource | 120 / min | 20 |
| `write.bulk` | Bulk endpoints | 10 / min | 3 |
| `ingest` | Punch batches, event ingest | 600 / min | 120 |
| `auth` | Token issue | 30 / min | 5 |
| `job.poll` | Operation status polling | 600 / min | 60 |

**R-XXIV-029** Every response carries `RateLimit-Limit`, `RateLimit-Remaining`,
`RateLimit-Reset` and, on rejection, `Retry-After`. A `429` is a normal, documented,
retryable outcome with code `rate.limit_exceeded`, never an error page.

**R-XXIV-030** A plan may carry a monthly **quota** in addition to a rate. Quota state is
visible at `GET /api/v3/meta/usage` and is emitted as `api.quota.threshold_reached` at
configurable percentages, so a partner learns before they are cut off, not after.

### XXIV.2.7 Idempotency

**R-XXIV-031** **Every** unsafe method (`POST`, `PATCH`, `DELETE`) accepts an
`Idempotency-Key` header, and every endpoint that creates a record, moves money, transitions
a workflow, or emits a notification **requires** one. A required key that is absent returns
`400 idempotency.key_required`.

**R-XXIV-032** The idempotency record is `(tenant_id, credential_id, endpoint, key)` →
`{request_fingerprint, status, response_body, response_status, created_at, expires_at}`,
stored in `api_idempotency_keys` (§XXIV.13). Semantics:

| Situation | Response |
|---|---|
| First use | Executed; the response is recorded before it is returned |
| Replay, same fingerprint, completed | The **stored** response, byte-identical, with `Idempotency-Replayed: true` |
| Replay, same fingerprint, still in flight | `409 idempotency.in_progress`, `Retry-After` set |
| Replay, **different** fingerprint | `422 idempotency.key_reuse_conflict` — never executed |
| Key older than the retention window (default 24 h, configurable, maximum 7 days) | Treated as first use |

**R-XXIV-033** The idempotency record is written in the **same database transaction** as the
domain effect. A design where the key is recorded after a successful commit is not
idempotent under a crash between the two. *(Consolidated requirement 4 under §10.1
Concurrency; and the payroll regenerate defect where payslips are deleted 230 lines before
a transaction opens, DEF-L-32.)*

**R-XXIV-034** Idempotency is a **defence in depth over**, not a substitute for, a database
natural-key constraint. Punch ingest keeps its natural-key uniqueness
`(tenant_id, employment_id, punch_instant, source)`, which is the design SmartPRS 2 got right
and must survive (consolidated requirement 25) — but with `tenant_id NOT NULL`, so the index
cannot be inert (C requirement 18).

### XXIV.2.8 Pagination, filtering, sorting, sparse fieldsets and expansion

**R-XXIV-035** **Cursor pagination on every collection.** No endpoint offers
offset/limit, because offset pagination silently skips and duplicates rows under concurrent
writes, and every collection in a payroll system is written to while it is read.

```
GET /api/v3/employees?limit=100&cursor=eyJrIjoiMDE5M2E…

{
  "data": [ … ],
  "meta": { "limit": 100, "has_more": true },
  "links": { "next": "/api/v3/employees?limit=100&cursor=eyJrIjoiMDE5M2Ix…" }
}
```

The cursor is opaque, signed, and encodes the sort key plus the tie-break `(sort_value,
uuid)`. A cursor from a different filter or sort is rejected with
`pagination.cursor_mismatch`. Default `limit` 50, maximum 500 (configuration, per endpoint
class).

**R-XXIV-036** Total counts are **not** returned by default; `?include_total=true` returns
an estimated count and is subject to the `read.report` rate class, because an exact count on
a large tenant is a table scan.

**R-XXIV-037** Filtering uses a declared, typed grammar — never free SQL, never a raw
predicate string:

```
?filter[status]=active
?filter[joining_date][gte]=2026-04-01&filter[joining_date][lt]=2026-07-01
?filter[org.department.code][in]=COLL-HYD,COLL-BLR
?filter[custom.linkedin_profile][present]=true
?q=ravi                       -- typed free-text search over declared searchable fields only
```
Operators: `eq ne lt lte gt gte in not_in between contains starts_with present`. Every
filterable field is declared in the resource schema and appears in OpenAPI; an undeclared
field returns `400 filter.unknown_field`. Filtering on a field the caller may not read
returns `403`, not an empty result, because an empty result is itself a disclosure.

**R-XXIV-038** Sorting is `?sort=-joining_date,employee_code` over declared sortable fields
only. Sort is always stabilised by appending `uuid`.

**R-XXIV-039** **Sparse fieldsets** — `?fields[employee]=employee_code,full_name,org` — and
**expansion** — `?expand=org.department,employment.current` — with a declared maximum
expansion depth and a declared maximum expansion count per request. Sensitive fields
(`pan`, `aadhaar`, `bank_account`, `ctc`, `salary`) are **never** returned unless explicitly
requested by name **and** the caller holds the field-level permission; requesting one without
permission is a `403`, and every such successful read is audited (spine S13, S14).
*SmartPRS 2 returns all 62 fields including Aadhaar and CTC to any caller who reaches the
endpoint (`AppDataController.php:302-424`).*

**R-XXIV-040** `GET` collections and single resources return `ETag`; conditional requests
(`If-None-Match`) return `304`. Unsafe methods accept `If-Match` for optimistic concurrency,
returning `412 resource.version_conflict` on a stale write. This is the API-level expression
of "nothing is overwritten" (spine Law 3).

### XXIV.2.9 The error envelope

**R-XXIV-041** One envelope. Every non-2xx response from every endpoint, without exception,
including framework-level failures (404, 405, 415, 429, 500):

```json
{
  "error": {
    "code": "validation.failed",
    "message": "The request could not be processed.",
    "status": 422,
    "request_id": "01936c1e-9a2b-7c31-b0d9-4a2f9e7c1d55",
    "correlation_id": "01936c1e-9a2b-7c31-b0d9-4a2f9e7c1d56",
    "documentation_url": "https://developer.ametecs.com/api/v3/errors/validation.failed",
    "details": [
      { "field": "joining_date", "code": "date.before_dob",
        "message": "Joining date precedes date of birth.",
        "value_seen": "1999-03-14" }
    ],
    "retryable": false
  }
}
```

**R-XXIV-042** `code` is drawn from a **closed, published, versioned catalogue** in
`namespace.reason` form. Adding a code is additive; removing or repurposing one is breaking.
Clients branch on `code`, never on `message`. `message` is human-facing, may be localised,
and carries **no** internal detail. *SmartPRS 2 returns raw exception messages from 194 sites
across the application (consolidated requirement 45; G D-20), disclosing schema and paths to
any authenticated caller.*

**R-XXIV-043** `retryable` is a contract, not a hint: `true` only where a byte-identical
retry with the same `Idempotency-Key` is safe. `429`, `502`, `503`, `504` and
`idempotency.in_progress` are retryable; `4xx` validation and authorisation failures are not.

**R-XXIV-044** Status-code discipline:

| Status | Meaning |
|---|---|
| 400 | Malformed request (unparseable body, unknown filter field, bad cursor) |
| 401 | No valid credential — uniform for every cause (R-XXIV-018) |
| 403 | Authenticated but not permitted, or insufficient scope, or out of data scope |
| 404 | Resource does not exist **or is outside the caller's tenant** — the two are indistinguishable by design |
| 405 / 415 | Method / media type not supported |
| 409 | State conflict (already approved, period locked, idempotency in progress) |
| 410 | Sunset endpoint |
| 412 | `If-Match` precondition failed |
| 422 | Semantically invalid (business-rule violation, idempotency fingerprint conflict) |
| 423 | The target period or record is locked by a workflow |
| 429 | Rate or quota exceeded |
| 500 | Unexpected. `request_id` only; no message, no trace, ever |
| 503 | Dependency unavailable or maintenance mode, with `Retry-After` |

**R-XXIV-045** `request_id` is generated per request; `correlation_id` is accepted from the
caller (`X-Correlation-Id`) or generated, and is propagated to every log line, audit row,
queued job, outbound call and webhook delivery caused by the request. This is what makes an
integration failure traceable end to end. *(Spine S14 audit fields; consolidated requirement
41 — `bootstrap/app.php`'s exception hook is empty.)*

**R-XXIV-046** A `403` from a data-scope failure and a `403` from a permission failure carry
different codes (`auth.out_of_scope`, `auth.forbidden`) but neither reveals whether the
record exists.

### XXIV.2.10 Bulk endpoints

**R-XXIV-047** Bulk is a distinct endpoint, never a magic array on the single-resource
endpoint:

```
POST /api/v3/employees/bulk
{
  "mode": "atomic",                      -- atomic | partial
  "on_conflict": "fail",                 -- fail | skip | update
  "items": [ { "op": "create", "ref": "r1", "data": { … } },
             { "op": "patch",  "ref": "r2", "uuid": "…", "data": { … } } ]
}
```

**R-XXIV-048** `mode: atomic` applies all items in one transaction or none, and returns
`422` naming the first failing `ref`. `mode: partial` returns `207 Multi-Status` with a
per-item verdict keyed by the caller's `ref`:

```json
{ "results": [ { "ref": "r1", "status": "created", "uuid": "…" },
               { "ref": "r2", "status": "failed",
                 "error": { "code": "validation.failed", "details": [ … ] } } ],
  "summary": { "created": 1, "updated": 0, "failed": 1, "skipped": 0 } }
```

**R-XXIV-049** Every bulk endpoint declares a maximum item count (configuration, default
500) and a maximum body size; exceeding either returns `413` with the limit stated. Bulk
requests are idempotency-keyed as a whole, and each item additionally carries the natural-key
guarantees of its resource. *SmartPRS 2's ingest caps are the constants `MAX_BATCH = 1000`
and `MAX_BODY_BYTES = 2097152` (C requirement 28).*

**R-XXIV-050** A bulk request larger than the synchronous limit is rejected with a pointer
to the **import job** path (§XXIV.2.11), not silently truncated. *Nothing in SmartPRS 2 is
ever silently truncated on this path today, and that property must be preserved as the caps
become configuration.*

### XXIV.2.11 Long-running operations are jobs with a status resource

**R-XXIV-051** Any operation that cannot reliably complete inside the HTTP timeout budget is
a **job**. The catalogue at launch: payroll run execution, payroll regeneration, attendance
recalculation, bulk import (employees, attendance, salary structures, leave balances,
opening balances), report execution over a large scope, statutory register and return
generation, bank file generation, document bulk export, tenant provisioning, and rule-pack
application.

```
POST /api/v3/payroll/runs/{uuid}/execute      → 202 Accepted
Location: /api/v3/operations/019372ab-…
{ "operation": { "uuid": "019372ab-…", "type": "payroll.run.execute",
                 "status": "queued", "progress": { "done": 0, "total": null },
                 "created_at": "2026-08-01T04:02:11Z" } }

GET /api/v3/operations/019372ab-…
{ "operation": {
    "uuid": "019372ab-…", "type": "payroll.run.execute",
    "status": "running",                       -- queued|running|succeeded|failed|cancelled|partial
    "progress": { "done": 4180, "total": 9642, "stage": "statutory_deductions" },
    "started_at": "…", "estimated_completion_at": "…",
    "result": null, "error": null,
    "links": { "result": null, "cancel": "/api/v3/operations/019372ab-…/cancel" } } }
```

**R-XXIV-052** A job resource is **durable** and survives worker restarts; its terminal state
and result are retained for a configurable period (default 30 days). Polling is cheap
(`job.poll` rate class) and the same completion is also delivered as the webhook event
`operation.completed`, so a partner need not poll at all.

**R-XXIV-053** Every job is cancellable where cancellation is meaningful, and a cancelled
job states precisely what it had already committed. A job that cannot be cancelled says so
in its resource rather than accepting a cancel that does nothing.

**R-XXIV-054** A failed job returns the same error envelope in `error`, plus a
`failure_report` link where the failure is per-row (imports, bulk recalculation). **Every
rejected row is counted and reportable** — nothing is silently dropped. *SmartPRS 2's import
paths `continue` past a blank PIN, an unparseable date or an unknown table with no counter
(`DEF-C-17`), and report a single `imported` number that also counts updates (`DEF-C-18`).*

**R-XXIV-055** Queue depth, oldest pending job age and worker liveness are exposed at
`GET /api/v3/meta/health` and on the operations dashboard (spine S18). A job that cannot be
enqueued returns `503`, never a `202` that no worker will ever pick up.

## XXIV.3 OpenAPI — generated, published, and contract-tested

**R-XXIV-057** The OpenAPI 3.1 document is **generated from the code**: from route
declarations, request objects, resource schemas, the permission and scope registry, the error
catalogue and the entity-schema engine (spine S9). It is never hand-maintained. *A
hand-maintained specification drifts; SmartPRS 2's own documentation disagrees with its
source in sixteen recorded places, including three code comments that state the opposite of
the code they annotate (G §8, D-12).*

**R-XXIV-058** The document includes tenant **custom fields**. `GET /api/v3/meta/openapi.json`
returns the generic contract; `GET /api/v3/meta/openapi.json?tenant_schema=true`, on a
tenant-bound credential, returns the same document with that tenant's custom field
definitions materialised in the employee, candidate and document schemas. *This is what makes
"add a LinkedIn Profile field" a configuration task all the way out to the API, which is the
whole point of spine S9.*

**R-XXIV-059** The document is **published** at a stable public URL, versioned alongside the
release, with a rendered reference site and a machine-readable changelog.

**R-XXIV-060** Client SDKs are **generated** from the document for PHP, Python, Java, .NET,
Node/TypeScript and Go, published to their language registries, versioned to the API, and
regenerated by the release pipeline. A hand-written SDK is not maintained.

**R-XXIV-061** **Contract tests run in CI and are blocking.** Three gates:

| Gate | Assertion | Fails the build when |
|---|---|---|
| Completeness | Every registered route appears in the document with its permission, scopes, parameters, request and response schemas, and error codes | A route is added without a schema, or with no permission declaration (R-XXIV-022) |
| Conformance | Every integration test's request and response is validated against the schema at runtime | An implementation returns a field the schema does not declare, or omits a required one |
| Compatibility | The generated document is diffed against the last released one and classified against the R-XXIV-007 table | A breaking change is proposed inside `v3` without an explicit, approved, recorded `BREAKING:` waiver |

**R-XXIV-062** The examples in the published document are **executed** against the sandbox
tenant in CI. An example that no longer works is a build failure, because an example that
lies costs a partner a day.

**R-XXIV-063** The error catalogue, the scope registry, the event catalogue and the webhook
payload schemas are generated from the same sources as the API document, so all four are
mutually consistent by construction.

**R-XXIV-064** A generated **Postman collection** and an environment template are published
with each release from the same document (§XXIV.11).

## XXIV.4 The Webhook Engine *(brief Section 83)*

Outbound events are a first-class product capability, not a per-integration afterthought.
SmartPRS 2 has no outbound webhook mechanism of any kind — the SmartEPT integration is
inbound only, and SmartPRS never calls SmartEPT (C §1.4). Every outbound notification in
SmartPRS 2 is an email, a WhatsApp template or nothing.

### XXIV.4.1 The event catalogue

**R-XXIV-065** Every subscribable event is declared in a **published catalogue** with a
name, a version, a payload schema, the permission required to subscribe, and the data class
it carries. A domain event that is not in the catalogue cannot be delivered externally, so
an internal refactor cannot accidentally start publishing new data to a partner.

the family; the full enumerated list is generated into the developer site):

**R-XXIV-066** Event payloads are **thin by default**: identity, tenant, timestamps, the
changed field names, and a `links.self` to the resource. A subscriber fetches the full
resource with its own credential and its own permissions. Fat payloads are opt-in per
subscription (`payload_mode: fat`), require the equivalent read permission on the
subscription's principal, and **never** include sensitive fields (PAN, Aadhaar, bank, salary)
unless the subscription additionally holds the field-level permission — which is recorded on
the subscription and re-checked at delivery time, not only at subscribe time.

**R-XXIV-067** Every event carries `event_uuid` (UUIDv7, the idempotency key for the
receiver), `event_type`, `event_version`, `occurred_at` (the business instant),
`published_at`, `tenant_uuid`, `correlation_id` and `sequence` (per subscription, monotonic).

**R-XXIV-068** Event payload versioning follows the API's rules (R-XXIV-007). A subscription
pins an `event_version`; a new version is delivered only to subscriptions that opt in;
deprecation and sunset use the same notice periods (R-XXIV-010).

**R-XXIV-069** Delivery is **at-least-once and unordered**. The contract states this
explicitly, and every payload carries `occurred_at` and `sequence` so a receiver can
de-duplicate and order. A design that promises exactly-once over HTTP is a design that lies.

### XXIV.4.2 Subscription management

**R-XXIV-070** A subscription is a tenant-owned resource: target URL, event-type list (exact
or prefix wildcard, e.g. `payroll.run.*`), an optional SPX filter over the payload (spine S5
— e.g. `payload.legal_entity.code = "AMTC-TG"`), `payload_mode`, `event_version`, secret
state, retry profile, and enabled/disabled state.

**R-XXIV-071** The target URL is validated against an **egress profile** exactly as an
outbound connector is (§XXIV.5.6): HTTPS only by default, host allow-list, loopback,
link-local and RFC1918 blocked. A webhook target is an outbound HTTP call from the
application server chosen by a tenant administrator — precisely the shape of SmartPRS 2's
`SEC-C-04`, and it must not be reintroduced through the webhook door.

**R-XXIV-072** **SMARTPRS 3 ARCHITECTURE RECOMMENDATION.** Creating a subscription requires
proving control of the endpoint: the engine
sends a signed `webhook.verification` challenge and the subscription stays `pending` until the
endpoint echoes the challenge value. This prevents a tenant pointing subscriptions at a third
party's URL.

**R-XXIV-073** A subscription may be scoped to a subset of the tenant's data (a legal entity,
a company, a set of branches) and is always additionally bounded by its principal's data
scope at delivery time.

### XXIV.4.3 Signing

**R-XXIV-074** Every delivery is signed over the raw body **plus a timestamp and a nonce**:

```
X-Ametecs-Event:      payroll.run.approved
X-Ametecs-Event-Id:   019372ab-4c1e-7f02-9a11-6b3d2e8c74af
X-Ametecs-Timestamp:  1785312131                        -- unix seconds
X-Ametecs-Nonce:      9f2b1c7e4a5d0836
X-Ametecs-Signature:  v1=<hex hmac-sha256>[,v1=<hex, previous secret during overlap>]

signing_string = "v1" || "." || timestamp || "." || nonce || "." || raw_body_bytes
signature      = hex( hmac_sha256( signing_string, secret ) )
```

The version prefix `v1=` exists so the signing algorithm can be migrated without breaking
every receiver at once. Comparison at both ends must be constant-time — SmartPRS 2 already
does this correctly (`SmarteptSignature.php:129`, `hash_equals`), and the property is kept.

**R-XXIV-075** The signature covers the timestamp and nonce, **because SmartPRS 2's does
not**, and its only protection against replay is a natural-key index that is inert wherever
`tenant_id` is NULL (`SEC-C-16`; C requirement 18). This requirement exists because of that
finding.

**R-XXIV-076** The published receiver contract is: verify the signature over the raw bytes
before parsing; reject if `|now − timestamp|` exceeds the freshness window; reject a
previously seen `(nonce, timestamp)`; and de-duplicate on `event_uuid`. Ametecs publishes
reference verification code in every SDK language.

### XXIV.4.4 Inbound replay rejection

The same rules apply to **inbound** signed webhooks that SmartPRS 3 receives (SmartEPT, SBB,
partner attendance feeds, payment gateways):

**R-XXIV-077** An inbound signed request must carry a timestamp and a nonce, both covered by
the signature. Freshness window default **300 seconds**, configurable per endpoint within a
platform-enforced maximum. Outside the window → `401`, uniform response, security-log entry.

**R-XXIV-078** Nonces are stored per endpoint in `webhook_inbound_nonces` for at least twice
the freshness window and are checked before any body parsing. A repeated nonce is rejected
with the same uniform `401` and counted as a **replay attempt**, which is an alertable
condition — not a silently absorbed duplicate.

**R-XXIV-079** Replay rejection is enforced at the **transport** layer and is independent of
whether the payload happens to be idempotent. *SmartPRS 2 conflates the two: a replayed
`attendance.punch` is a no-op only by the accident of a derived idempotency key plus an index,
and a replayed `attendance.daily` for a different date is fully accepted
(`SmarteptWebhook.php:282-287`; `SEC-C-16`).*

**R-XXIV-080** Inbound endpoint URLs carry an unguessable segment (SmartPRS 2's 16-character
lowercase slug is ≈82 bits — adequate, C §4.12) **and** a credential. The slug is a routing
handle, never the authentication.

### XXIV.4.5 Delivery, retry and the dead-letter queue

**R-XXIV-081** Every attempt writes a row to `webhook_deliveries`: subscription, event,
attempt number, request headers (secret redacted), body digest, response status, response
body (size-capped and redacted), latency, error classification, and the next scheduled
attempt. The delivery log is queryable by the tenant and retained for a configurable period
(default 30 days; the event itself is retained longer).

**R-XXIV-082** Success is a `2xx` within the configured timeout (default 10 s, per
subscription, platform maximum 30 s). Everything else is a failure. A `410 Gone` from the
receiver disables the subscription immediately with notification, because the receiver has
said the endpoint no longer exists.

**R-XXIV-083** Retry is **exponential with full jitter**, configured per subscription from a
platform-bounded profile. Default schedule, all configuration:

| Attempt | Nominal delay |
|---:|---|
| 1 | immediate |
| 2 | 30 s |
| 3 | 2 min |
| 4 | 10 min |
| 5 | 1 h |
| 6 | 3 h |
| 7 | 6 h |
| 8 | 12 h |
| 9 | 24 h |

Total window ≈ 46 hours (configurable), after which the delivery moves to the dead-letter
queue. *SmartPRS 2 has no retry anywhere in the codebase (`NEW-C-25`), so this schedule is
new in its entirety.*

**R-XXIV-084** Retries respect `Retry-After` when the receiver sends one, and the engine
applies per-endpoint concurrency and rate caps so that a slow receiver cannot consume the
delivery worker pool. Deliveries are dispatched on a dedicated `integration` queue, never on
the interactive queue (consolidated requirement 35).

**R-XXIV-085** Exhausted deliveries land in a **dead-letter queue**, visible in the console,
retained for a configurable period (default 30 days), with the full request and the final
response. From there they can be **replayed** individually or in a filtered selection
(by subscription, event type, time range), preserving the original `event_uuid` so a receiver
that has since processed the event de-duplicates it. Replay is permission-gated
(`integration.webhook.replay`) and audited.

**R-XXIV-086** Nothing is ever dropped silently. A delivery that cannot be attempted at all
(no worker, egress refused, credential missing) is recorded as an attempt with that
classification, not skipped. *This is the direct answer to `DEF-C-14`, where a failed pull is
printed to the console and vanishes.*

### XXIV.4.6 Endpoint health and automatic disabling

**R-XXIV-087** Each subscription carries a health record: `consecutive_failures`,
`failure_rate_1h`, `last_success_at`, `last_failure_at`, `last_error_class`, `p95_latency_ms`,
`pending_depth`, `oldest_pending_age`.

**R-XXIV-088** Failures are **classified**, because the operator response differs by class:
`dns` · `tls` · `connect_timeout` · `read_timeout` · `http_4xx` · `http_401_403` ·
`http_410` · `http_429` · `http_5xx` · `egress_refused` · `payload_too_large` ·
`signature_config_error` · `unknown`.

**R-XXIV-089** A subscription is **automatically disabled** when a configurable threshold is
crossed (default: 100 consecutive failures, or a 100% failure rate sustained over 24 hours),
and **the tenant is notified** through the notification engine (Part XXIII) with the last
error, the failure class, and a one-click re-enable that first sends a test delivery.
Automatic disabling without notification is worse than the failure it prevents.

**R-XXIV-090** A disabled subscription's undelivered events remain in the dead-letter queue
for the retention period, so re-enabling within that window can recover them by replay rather
than losing the interval.

**R-XXIV-091** `integration.connector.stale` and `webhook.subscription.disabled` are
themselves catalogue events and appear on the operations dashboard (spine S18). *SmartPRS 2's
equivalent screen shows a green "last sync" for a device that has been failing for days
(`DEF-C-14`), which is worse than showing nothing.*

### XXIV.4.7 Secret rotation with overlap

**R-XXIV-092** `POST /webhooks/subscriptions/{uuid}/rotate-secret` generates a successor
secret, returns it **once**, and sets `overlap_ends_at` (default 7 days, configurable,
platform maximum 30). During the overlap, deliveries carry **two** `v1=` signatures — new
first — so a receiver may verify against either while it deploys the new secret. At the end
of the overlap the predecessor is destroyed and the console records the last delivery each
secret verified.

**R-XXIV-093** Secrets are generated server-side with at least 256 bits of entropy, stored
encrypted with a managed key (they must be recomputed, so they cannot be hashed), never
returned by any read endpoint, and never logged. A decryption failure raises an operator
alert and **never** falls back to treating the ciphertext as plaintext (spine S13; C
requirement 33, which records two such fallback sites in SmartPRS 2).

**R-XXIV-094** Rotation is available to the tenant without Ametecs involvement, and an
expiring secret raises `integration.credential_expiring` at configurable lead times.

## XXIV.5 The Integration Framework *(brief Section 84)*

### XXIV.5.1 One framework, many categories

`::sync:480-509`, `ETimeOfficeService::configuredAny:126-137`, `SyncETimeOffice::handle:76-96`

### XXIV.5.2 The connector contract

```php
interface Connector
{
    public function descriptor(): ConnectorDescriptor;   // key, category, version, vendor
    public function capabilities(): CapabilitySet;       // §XXIV.5.4
    public function configSchema(): Schema;              // renders the console form
    public function validate(Config $c): ValidationResult;      // never silently NULLs
    public function test(Config $c): Diagnostics;               // redacted, size-capped
    public function health(Config $c, State $s): HealthReport;

    // inbound pull
    public function fetch(Config $c, Cursor $from, Budget $b): FetchResult;
    public function parse(RawBatch $r): CanonicalBatch;

    // outbound push
    public function send(Config $c, OutboundMessage $m): SendResult;

    // command channel (devices, provisioning)
    public function command(Config $c, Command $cmd): CommandResult;
}
```

**R-XXIV-097** `fetch` returns a `FetchResult` carrying records, the **new cursor**, a
completeness flag, and per-record diagnostics. It never writes. Persistence, identity
resolution, business rules and payroll effects live in the domain services, exactly as the
attendance ingest lifecycle separates them (Part XI §XI.3.3).

**R-XXIV-098** `test` is read-only and side-effect-free, always. A test button that writes is
a test button nobody dares press.

**R-XXIV-099** Every connector method is **total**: it returns a typed result, including a
typed failure, and does not throw across the boundary. An unclassified failure is itself a
classification (`unknown`) that raises an alert — never a swallowed exception. *SmartPRS 2
destroys 50.5% of its caught exceptions (spine S5.6); 426 of 843 catch blocks neither log,
rethrow nor annotate (consolidated requirement 42).*

### XXIV.5.3 The declarative connector recipe

**R-XXIV-100** For any source or sink whose protocol is REST, SOAP, SQL, CSV or SFTP, **no
PHP is required**. The recipe grammar and engine are specified in Part XI §XI.3.5 and are
**the same grammar**, extended here with the fields an outbound or non-attendance connector
needs. A second recipe language is not created.

Extensions beyond the Part XI grammar, all additive:

```yaml
direction: outbound                 # inbound | outbound | bidirectional
category: accounting

emit:                               # outbound only
  trigger: event                    # event | schedule | manual
  events: [ "payroll.run.approved" ]
  batching: { max_items: 500, max_wait_s: 60 }
  template_ref: TPL-TALLY-JOURNAL-v3        # a declared, versioned payload template
  ack:
    expect_status: [200, 201, 202]
    success_path: $.status
    success_values: ["OK", "ACCEPTED"]
    id_path: $.voucherId                    # stored as the external reference

file:                               # csv | sftp | fixed_width kinds
  naming: "PAYOUT_{company_code}_{period:Ymd}_{seq:04}.txt"
  encoding: UTF-8                   # explicit; never guessed
  line_ending: CRLF
  bom: false
  checksum: sha256                  # written as a sidecar where the counterparty expects one
  archive_on_success: "processed/{date}/"

sql:                                # sql kind
  driver: mysql | pgsql | sqlsrv
  mode: read_only                   # enforced by the credential's grants, not by trust
  statement_ref: STMT-PUNCH-PULL-v2 # a named, parameterised, allow-listed statement
  bindings: { from: "{cursor}", to: "{window_end}" }
```

**R-XXIV-101** A recipe is a spine S4 configuration artefact — versioned, effective-dated,
scoped, draft/publish, diffable, schema-validated — and publishing runs a live `test` against
the source that must parse at least one record (Part XI R-XI-030).

**R-XXIV-102** An invalid recipe is **rejected on save with a field-level error**. It is
never stored as NULL, and the save never reports success. *SmartPRS 2 silently converts an
invalid `api_config` to NULL and returns `ok:true`, so an administrator who mistypes a recipe
is told it saved and the connector then does nothing (`BiometricConfigController.php:32-42`;
`DEF-C-13`).*

**R-XXIV-103** No heuristic field-sniffing exists in any recipe kind. Every field is mapped
explicitly. *`ETimeTrackLiteService::rowFromFields()` identifies the employee code as "the
first non-datetime cell containing a digit" (`:233-244`), and on a parse failure feeds the
entire raw body — which may be an HTML login page — into that sniffer (`:130-149`;
`DEF-C-15`, `DEF-C-16`).*

**R-XXIV-104** A SQL-kind recipe executes only **named, allow-listed, parameterised**
statements with bound parameters, against a credential holding read-only grants. String
concatenation of a query is not expressible in the grammar.

### XXIV.5.4 Capability declaration

**R-XXIV-105** Every connector declares its capabilities, and the console renders **only**
the fields and actions that capability set supports:

```
pull · push · webhook_in · command · enrol · realtime · backfill · test
paginate · incremental · delete_detection · rate_limited · bulk · attachments
```

*SmartPRS 2 renders a four-branch `if` in the SPA against a provider string
(`AppController.php:9695-9710`), so a new provider means editing the front end (C
requirement 4).*

**R-XXIV-106** A capability a connector does not declare is not callable. Invoking it returns
`409 connector.capability_unsupported` — never a silent success. *SmartPRS 2's ADMS
`getrequest` command endpoint always answers `OK` while implementing no command channel at
all (`PushController.php:57-62`).*

### XXIV.5.5 Credentials by reference, never by interpolation

**R-XXIV-107** A connector configuration **never contains a secret**. It contains a
`credential_ref` — a handle into the credential vault. The secret is resolved at call time by
the engine and placed **only** where the transport declares it belongs (an `Authorization`
header, a SOAP header element, a connection string field, an SSH key).

**R-XXIV-108** A recipe may **not** interpolate a credential into any admin-authored string
— not a URL, not a header value, not a body, not a filename. The placeholder vocabulary
available to admin-authored strings excludes every credential token by construction, and the
validator rejects a recipe that references one. *SmartPRS 2 substitutes `{pass}`, `{user}` and
`{serial}` into admin-supplied `url`, `headers` and `body`
(`GenericApiService.php:186-188, 94, 126, 206`; `SEC-C-05`), so an administrator can place a
device password into a query string that every intermediary logs.*

**R-XXIV-109** Credential vault entries carry: type (`basic`, `bearer`, `header_key`,
`oauth2_client_credentials`, `oauth2_authorization_code`, `mtls`, `ssh_key`, `pgp`,
`hmac_secret`, `db_password`), an owning tenant, an owning connector or a shared handle,
`expires_at`, `rotation_state`, `last_used_at`, and a `usage_binding` naming exactly which
transport slot may receive it.

**R-XXIV-110** Secrets are encrypted at rest with a **managed key** (spine S13), are
write-only over the API, are never echoed by any read endpoint, are redacted in every log and
every test output, and are excluded from every export and backup manifest that is not itself
encrypted. A decrypt failure raises an operator alert and never falls back to treating the
ciphertext as plaintext. *(C requirement 33, two such fallback sites; `SEC-C-13`.)*

**R-XXIV-111** Credential expiry is tracked and surfaced: `integration.credential_expiring`
at configurable lead times, and the Integration Console shows days-to-expiry per connector.
*An OAuth client secret that expires unnoticed at 02:00 on the 1st is how a month's payroll
inputs go missing.*

### XXIV.5.6 Egress control

**R-XXIV-112** Every outbound call from the application — connector, webhook, file transfer,
document fetch, SSO metadata retrieval — is bound to an **egress profile**. There are no
unbound outbound calls. *SmartPRS 2 has no egress control of any kind, and its Test button
returns the response body to the browser, which converts blind SSRF into readable SSRF
(`SEC-C-04` + `SEC-C-14`, both HIGH; `GenericApiService.php:70, 94, 146`;
`BiometricConfigController.php:423-425`).*

```
egress_profile
  key, name, tenant_id (NULL = platform-wide, Ametecs-owned)
  schemes            [https]                          -- http requires an explicit exception
  host_allow         [ "*.etimeoffice.com", "api.partner.example" ]   -- exact or single-label wildcard
  port_allow         [443]
  ip_policy          block_loopback | block_link_local | block_private | block_multicast
                     -- all four ON by default
  lan_exception      { enabled: false, cidrs: [], approved_by, approved_at, expires_at }
  dns_pin            optional pinned resolution
  max_redirects      0                                 -- redirects are followed only if declared
  max_response_bytes 5_242_880
  proxy_ref          optional
```

**R-XXIV-113** Loopback, link-local (`169.254.0.0/16`, including the cloud metadata address),
RFC1918, RFC6598 CGNAT, multicast and reserved ranges are **blocked by default**, on both the
configured hostname and **every address it resolves to**, re-checked at connection time to
defeat DNS rebinding. A blocked call fails with `egress.blocked` and is logged with the host
and the resolved address.

**R-XXIV-114** A LAN connector (an on-premise device, a customer's internal SOAP endpoint)
requires an explicit, named, time-boxed `lan_exception` with a recorded approver. It is not a
checkbox on the connector; it is a change to an egress profile, and it is audited.
*PRODUCT OWNER DECISION REQUIRED — see D-XXIV-04 on who approves an egress exception.*

**R-XXIV-115** Redirects are **not followed** unless the profile declares a maximum, and a
followed redirect is re-validated against the profile. A redirect to a blocked address is the
classic SSRF bypass.

**R-XXIV-116** Response size is capped by the profile. A connector that receives more than
the cap fails with `response.too_large` rather than streaming an unbounded body into memory.

### XXIV.5.7 Timeouts, retry and circuit breaking

**R-XXIV-117** Every outbound call declares a **connect timeout** and a **read timeout**,
per connector, as configuration. There is no global default constant. *SmartPRS 2 uses the
literal `60` on every connector (`ETimeOfficeService.php:158`; `ETimeTrackLiteService.php:89`;
`GenericApiService.php:114, 147`; `NEW-C-25`) and no timeout at all on five payment-gateway
calls (consolidated requirement 23).*

**R-XXIV-118** Every outbound call declares a **retry policy**: attempts, backoff base,
strategy (exponential with full jitter), maximum delay, and the classified failures that are
retryable. A non-idempotent outbound call is retried **only** when the counterparty supports
an idempotency key or a natural key that makes the retry safe; where it does not, the policy
declares `attempts: 1` and the failure is surfaced. *The string `->retry()` appears nowhere in
SmartPRS 2 (`NEW-C-25`).*

**R-XXIV-119** Every connector has a **circuit breaker**: after N consecutive failures
(default 10, configurable) the breaker opens for a cooldown (default 15 minutes), during
which calls fail fast with `connector.circuit_open` and are queued or deferred rather than
attempted. A single half-open probe closes it. This protects both the counterparty and the
worker pool.

**R-XXIV-120** Per-connector **rate limits and concurrency caps** are declared and enforced
client-side, so SmartPRS 3 is a well-behaved API consumer and does not get itself banned by a
vendor.

**R-XXIV-121** No external call is ever made **synchronously from inside a request handler or
from inside a scheduled task holding a lock**. All integration I/O runs on the `integration`
queue. *(Consolidated requirement 24: `WaService.php:146` is called inline per tenant inside
`billing:alerts`; `DEF-C-03`: late-arrival notifications are sent inline from the ingest
path.)*

### XXIV.5.8 High-water-mark cursoring

**R-XXIV-122** Every incremental connector maintains a **durable high-water mark** per
connector instance — a cursor value, not a relative window. The cursor advances **only** on a
successfully persisted batch, in the same transaction as the persistence.

```
cursor := { kind: timestamp | sequence | opaque_token | file_digest,
            value, advanced_at, advanced_by_run_uuid }
```

**R-XXIV-123** A failed run leaves the cursor untouched, so the next run re-attempts the
**missed range**. *SmartPRS 2 recomputes `now() - days` on every tick, so a scheduler outage
loses the missed punches permanently (`routes/console.php:225`; C requirement 25; consolidated
requirement 22 calls `--days=1` the highest-impact hard-coded value in that area).*

**R-XXIV-124** Each connector declares a `max_look_back` (so a long outage does not produce
one unbounded request), a `max_span` per request (so the range is walked in windows), and an
`overlap` (so a source with imprecise timestamp ordering does not lose boundary records —
duplicates are free, because the natural key absorbs them).

**R-XXIV-125** The cursor is **manually resettable** by a permitted administrator, with a
mandatory reason, an impact preview ("this will re-fetch approximately N records from
DD-MMM"), and an audit row. Resetting a cursor is a supported operation because it is what an
operator needs after a vendor-side data correction; it must not be a database edit.

**R-XXIV-126** For file-based connectors the cursor is the set of processed **file digests**,
not filenames, so a re-uploaded file with the same name is re-read and an unchanged file is
not.

## XXIV.6 The Integration Console

The single screen an administrator opens when an integration is not working. It is designed
against one measurement: *how long does it take to know what is wrong and what to do?*

### XXIV.6.1 The connector list

| Column | Content |
|---|---|
| Connector | Name, category, adapter or recipe key, adapter version |
| State | `connected` · `degraded` · `disconnected` · `disabled` · `never_connected` · `circuit_open` · `credential_expired` |
| Last attempt | Timestamp and outcome — **of the last attempt, not the last success** |
| Last success | Separate column, with age |
| Records | Last run: inserted / updated / duplicate / quarantined / **dropped**, each a link |
| Last error | Classification + a short redacted message + a link to the run detail |
| Consecutive failures | Integer, with the auto-disable threshold shown |
| Retry state | Next attempt at, or `circuit open until`, or `awaiting operator` |
| Cursor | Current high-water mark and its age |
| Credential | Type, days to expiry, rotation state |
| Health | Derived from staleness, failure rate and cursor lag |

**R-XXIV-127** `last_status` reflects the **last attempt**. `last_success_at` is a separate,
separately displayed field. *SmartPRS 2 stamps nothing on failure, so the screen shows a
green "last sync" for a device that has been failing for days (`DEF-C-14`, HIGH). Displaying
a stale success as current status is worse than displaying nothing, because it suppresses
the investigation.*

**R-XXIV-128** Error classification is a declared vocabulary, identical to the webhook
classification (R-XXIV-088) plus `auth_failed`, `schema_mismatch`, `parse_failed`,
`cursor_conflict`, `quota_exceeded`. Free-text errors are stored but never used to drive
behaviour or display state.

**R-XXIV-129** Health is derived and explainable: clicking it shows the inputs (staleness
against the connector's own interval, failure rate, cursor lag, credential expiry) and the
rule that produced the verdict — spine Law 4 applies to operational verdicts too.

**R-XXIV-130** A staleness alert exists per connector — "connector X has not succeeded for N
intervals" — with N configurable, defaulting from the connector's own sync interval, and it
is delivered through the notification engine, not only rendered on a screen nobody has open
(C requirement 45).

### XXIV.6.2 Run history and diagnostics

**R-XXIV-131** Every run is a row: started, finished, duration, cursor before and after,
request count, records by verdict, bytes, error classification, and the `correlation_id` that
ties it to every log line and audit entry it produced.

**R-XXIV-132** Per-run counts distinguish **inserted / updated / duplicate / quarantined /
dropped**, and every dropped record is retained with its reason and is exportable.
*SmartPRS 2 reports one `imported` number that also counts updates (`DEF-C-18`) and silently
`continue`s past blank identifiers, unparseable dates and unknown tables (`DEF-C-17`).*

**R-XXIV-133** Per-connector diagnostics offer, subject to permission: DNS resolution and
the resolved addresses, TLS handshake and certificate chain summary with expiry, egress
profile verdict, authentication verdict, a **sample parse** of the first N records showing
each mapped field beside its source path, cursor position, and clock skew against the
counterparty.

### XXIV.6.3 Test output

**R-XXIV-134** Test output is **structured, redacted and size-capped**: HTTP status, latency,
resolved address, content type, record count, and a field-by-field parse table for at most N
sample records with every value truncated to a declared length. **The raw response body of a
foreign host is never returned to the browser.** *SmartPRS 2 echoes 1,500 raw characters from
an arbitrary host to the browser, and returns a token endpoint's raw body on login failure
(`BiometricConfigController.php:423-425, 444-445`; `GenericApiService.php:80-82`;
`SEC-C-14`).*

**R-XXIV-135** Redaction is applied by declared rule — any value bound to a credential
handle, anything matching declared secret patterns, and any field declared `pii` in the
resource schema — and is applied at the point of capture, so an unredacted value never
reaches a log, a support export or an error report.

**R-XXIV-136** Where a raw body genuinely is required to diagnose a vendor's malformed
response, it is captured into a **support artefact**: encrypted, retention-bounded,
permission-gated (`integration.diagnostics.raw`), audited on access, and never rendered
inline.

**R-XXIV-137** Every console action that changes behaviour — enable, disable, rotate, reset
cursor, replay, edit configuration, approve an egress exception — writes an audit row with
before and after values (spine S14). *SmartPRS 2 writes no audit record for device mapping,
device claiming or historic backfill (`NEW-C-11`).*

## XXIV.7 SmartEPT integration *(brief Section 85)*

SmartEPT is an Ametecs product that observes employee productivity/presence and today pushes
attendance events into SmartPRS. In SmartPRS 2 that integration is a single signed webhook,
`POST /api/v1/webhooks/smartept/{slug}`, accepting two event types (`attendance.punch` and
`attendance.daily`), with SmartPRS never calling SmartEPT at all (C §1.4). The signature and
the tenant-from-endpoint design are correct and are kept; the replay gap and the
SmartEPT-specific parsing embedded in a controller class are not.

### XXIV.7.1 The contract is explicit, versioned and two-directional

**R-XXIV-138** The SmartPRS ↔ SmartEPT contract is a **published, versioned document** owned
jointly and changed only through the R-XXIV-007 rules. It has two halves:

| Half | Mechanism | Owner of the schema |
|---|---|---|
| SmartEPT → SmartPRS | Signed inbound webhook at `POST /api/v3/ingest/webhooks/{endpoint_uuid}`, adapter profile `smartept` | SmartPRS publishes the accepted event schemas |
| SmartPRS → SmartEPT | `/api/v3` read endpoints called by SmartEPT with an OAuth2 client-credentials principal, **plus** outbound webhooks for the events SmartEPT subscribes to | SmartPRS publishes both |

**R-XXIV-139** The SmartEPT-specific event names and field translation become **profile
data** on the generic `webhook.signed` adapter, not a PHP class. *SmartPRS 2 implements them
as `SmarteptWebhook`, a controller carrying its own timezone conversion, its own identity
assembly and its own derived idempotency key (C §4.8, §4.9, §4.14); the analysis's own
migration verdict is "MERGE into a general signed-webhook ingest" (C §9).*

**R-XXIV-140** The inbound endpoint carries an unguessable UUID segment **and** a credential,
and enforces the full §XXIV.4.4 replay rules: timestamp and nonce inside the signature, a
300-second freshness window, and a nonce store. *This closes `SEC-C-16` directly.*

**R-XXIV-141** Tenant is derived from the endpoint's own binding, never from a field in the
payload. *SmartPRS 2 already does this correctly on the SmartEPT path (`SmarteptSignature.php:72-78`)
and incorrectly on the `/iclock` path, where a caller-supplied serial selects the tenant
(`PushController.php:201-228`; G §7.1 #5). The correct one is the one that is generalised.*

### XXIV.7.2 Canonical events exchanged

**SmartEPT → SmartPRS**

| Event | Payload (canonical) | SmartPRS effect |
|---|---|---|
| `attendance.punch` | canonical punch (spine S10.1): `external_event_id`, `device_serial`, `device_user_id`, `employee_code`, `punch_datetime_local`, `timezone`, `direction`, `verification_method`, `source`, `occurred_at` | One punch through the standard ingest lifecycle: raw → normalised → derived. Per-punch verdict returned |
| `attendance.daily` | employee, business date, `first_in`, `last_out`, worked minutes, source system id | Expanded into two canonical punches (IN, OUT) **carrying an explicit `derived_from: daily_summary` provenance flag**, so downstream rules and the explainability trace can state that intra-day punches were never observed |
| `session.started` / `session.ended` | employee, workstation, instants | Optional productivity sessions; ingested as evidence, never as attendance, unless a tenant rule promotes them |
| `presence.idle_reported` | employee, interval, idle minutes | Evidence only; feeds rules if the tenant configures one |
| `employee.identity_observed` | SmartEPT identity ↔ device/user mapping hints | Feeds the mapping worklist; never auto-maps |

**SmartPRS → SmartEPT**

| Event / endpoint | Purpose |
|---|---|
| `employee.created` / `.updated` / `.exited` (webhook) | Keeps SmartEPT's roster current without SmartEPT reading SmartPRS's tables |
| `employee.assignment_changed` | Org and shift context |
| `attendance.day.finalised` | The authoritative attendance verdict, so SmartEPT can reconcile its own view |
| `GET /api/v3/employees`, `/org-units`, `/attendance/shifts` (API) | Bootstrap and reconciliation reads under a scoped credential |

**R-XXIV-142** `attendance.daily` expansion carries an explicit provenance flag, because a
day derived from a summary and a day derived from observed punches are not the same evidence
and must not be indistinguishable in the trace (spine S15). *SmartPRS 2 expands a daily
summary into two punches with no marker (C §1.4), so the resulting attendance day is
indistinguishable from one built from real punches.*

**R-XXIV-143** Every inbound event is idempotent on `event_uuid` at the transport layer and
on the natural key at the domain layer. Both. *SmartPRS 2 relies on a derived key plus an
index that is inert when `tenant_id` is NULL (C requirement 18) — one mechanism, conditionally
present.*

### XXIV.7.3 Versioning between the products

**R-XXIV-144** The SmartEPT contract carries its own version, independent of the SmartPRS
application version, and both products declare the contract versions they support. A release
of either product that drops support for a contract version follows the R-XXIV-010 notice
periods, **including for a sibling product** — a sibling is not a reason to skip the process,
because customers run the two on different upgrade cycles, particularly on-premise.

**R-XXIV-145** A compatibility matrix (SmartPRS version × SmartEPT version × contract
version) is published and is asserted by an integration test in both products' CI pipelines.

### XXIV.7.4 The prohibition on shared tables — stated as an architectural rule

> **RULE.** No Ametecs product may read from, write to, or hold a foreign key into another
> Ametecs product's database schema. Every crossing of a product boundary is an API call or a
> signed webhook against a versioned, published contract. This applies to SmartEPT, SmartDCM,
> the Smart Biometric Bridge and every future product, on SaaS, private cloud and
> on-premise, without exception, including where the two products happen to share a database
> server.

**R-XXIV-146** The rule is enforced mechanically, not by convention: the application database
user for each product has grants only on its own schema; a CI check fails the build on any
cross-schema reference in a query, migration or model; and the deployment templates provision
separate schemas and separate credentials even in a single-server on-premise install.

**Rationale**, stated once so it survives the first cost-saving argument:

1. **A shared table is a shared release train.** The moment SmartEPT reads a SmartPRS table,
   neither product can change that table's shape without co-ordinating a release across two
   teams and every customer running both. SmartPRS 3's entire premise is that behaviour
   changes as configuration rather than as a release (spine S0); a shared table reintroduces
   the deployment coupling the rebuild exists to remove.
2. **A shared table has no version, no deprecation and no notice period.** A contract does.
   Everything in §XXIV.2.3 — additive change, `Deprecation`/`Sunset` headers, an 18-month
   sunset, an "is anyone still calling this" signal — is unavailable to a `JOIN`.
3. **A shared table bypasses authorisation, tenancy and audit.** Every access-control
   guarantee in SmartPRS 3 lives in the application layer: policies, data scopes, field-level
   permissions, the audit ledger. A foreign product reading the table gets none of them, and
   the audit ledger silently ceases to be a complete record of who read what — which, given
   DPDP obligations over PAN, Aadhaar and bank data, is a compliance failure, not a design
   preference.
4. **A shared table defeats explainability.** Spine Law 4 requires every derived number to
   carry its trace. A row read directly carries no trace, no version ids, and no statement of
   which rule produced it, so a number that leaves through the side door can never be
   defended.
5. **A shared table cannot be deployed apart.** On-premise customers buy the products
   separately and upgrade them separately. A schema dependency makes "SmartPRS 3.4 with
   SmartEPT 2.9" an untested configuration, and eventually an unsupported one.
6. **The precedent already exists in SmartPRS 2 and it is instructive.** `attendance_pending`
   serves two unrelated features with **disjoint schemas**, and whichever code path runs first
   on a virgin database determines the shape the other one then fails against (`CONF-C-01`;
   spine S16). That is a single-product instance of exactly this failure mode. The
   cross-product version is not recoverable by a rename.

**R-XXIV-147** Where a genuine bulk-data need exists that an API cannot serve efficiently
(a warehouse extract, a reconciliation of millions of rows), the answer is a **published
export contract** — a job producing a versioned file to an agreed location with an agreed
schema — not a database grant. The export is versioned, permissioned and audited like every
other product surface.

## XXIV.8 Smart Biometric Bridge *(brief Section 86)*

SBB is the Ametecs on-premise agent that sits on a customer's LAN, talks to biometric
terminals in their native protocols, and forwards punches to SmartPRS. It is the reference
implementation of the ingest contract, and everything else converges on its semantics (C §9).

### XXIV.8.1 The responsibility split

| Concern | SBB | SmartPRS 3 |
|---|---|---|
| Device transport (TCP/UDP 4370, ADMS, ISAPI, vendor SDKs) | **Owns** | Never |
| Device discovery, polling schedule, device credentials on the LAN | **Owns** | Never |
| Vendor payload normalisation to the canonical punch | **Owns** | Validates |
| Local persistence and offline buffering | **Owns** | Never |
| Forwarding, batching, retry, backpressure | **Owns** | Never |
| Local device health and firmware/serial reporting | **Owns** | Displays |
| **Identity mapping** (device user id / employee code → employment) | Never | **Owns** |
| **Shift resolution, attendance day attribution, pairing** | Never | **Owns** |
| **Attendance business rules, penalties, OT, comp-off** | Never | **Owns** |
| **Leave interaction, settlement, payroll** | Never | **Owns** |
| **Quarantine of unmapped punches and their replay** | Never | **Owns** |
| Tenant determination | Never | **Owns** (from the credential) |
| Audit of ingest and of mapping decisions | Local operational log | **Owns** the ledger |

**R-XXIV-148** SBB **never** performs identity mapping. It forwards what the device said —
device serial, device user id and, where the device holds one, an employee code — and
SmartPRS resolves it through the ordered, candidate-major identity strategy of Part XI
§XI.4.2. *Putting mapping in the bridge would mean the mapping rules, their history and their
audit live outside the system of record, on a customer's PC.*

**R-XXIV-149** SBB **never** decides attendance. A bridge that decides what counts as "late"
is a second attendance engine, and two attendance engines is how a customer gets two answers.

**R-XXIV-150** Neither product reaches into the other's storage; the contract is the canonical
punch API plus a versioned webhook (spine S10, S17; Part XI R-XI-038).

### XXIV.8.2 The canonical punch contract

The wire contract SBB writes is the canonical punch of spine S10.1, unchanged:

```
POST /api/v3/attendance/punches
Authorization: Bearer sk_prs_…              -- API key, scope attendance.ingest
Idempotency-Key: 019372c1-…                 -- per batch
Content-Type: application/json

{
  "collector":   { "kind": "sbb", "version": "3.2.1", "install_uuid": "…" },
  "batch_uuid":  "019372c1-…",
  "punches": [
    { "external_event_id":     "ZK-K40-0043-8891277",   -- REQUIRED, unique per device
      "device_serial":         "K40-0043",
      "device_user_id":        "1043",
      "employee_code":         "AME1043",               -- optional, when the device holds it
      "punch_datetime_local":  "2026-08-26 09:41:00",   -- naive wall clock, no offset
      "timezone":              "Asia/Kolkata",          -- the assumption applied
      "direction":             "in",                    -- in|out|break_out|break_in|unknown
      "verification_method":   "fingerprint",
      "source":                "device",
      "raw_payload_hash":      "sha256:…",
      "device_captured_at":    "2026-08-26T09:41:00+05:30",
      "buffered_since":        "2026-08-26T09:41:03+05:30",
      "adapter":               "zk.tcp",
      "adapter_version":       "3.2.1" }
  ]
}
```

**R-XXIV-151** `external_event_id` is **required** and must be stable and unique per device
across the device's lifetime. It is the receiver-side idempotency key, and it is what makes a
retry after an ambiguous timeout free of consequence.

**R-XXIV-152** `direction` includes `unknown` as a **first-class value** that routes to a
review queue. *SmartPRS 2 silently maps every unrecognised direction token to `in` at four
separate sites (`NEW-C-04`), which quietly manufactures attendance.*

**R-XXIV-153** Time is a naive wall clock plus a declared timezone. An offset-bearing
timestamp on the device contract is **rejected**, not coerced. *SmartPRS 2 already enforces
exactly this on the SBB path with a round-trip guard that also rejects `2026-02-30`
(`PunchIngestService.php:308-331`) — one of the best pieces of validation in the codebase —
while falling back to `Carbon::parse` on four other paths (`DEF-C-04`). The good rule is
generalised; the fallback is deleted.*

**R-XXIV-154** Response is a **per-punch verdict**, and punches are persisted **before** the
acknowledgement is sent:

```json
{ "batch_uuid": "019372c1-…",
  "results": [
    { "external_event_id": "ZK-K40-0043-8891277", "status": "accepted",
      "punch_uuid": "019372c2-…" },
    { "external_event_id": "ZK-K40-0043-8891278", "status": "duplicate",
      "punch_uuid": "019372a0-…" },
    { "external_event_id": "ZK-K40-0043-8891279", "status": "pending",
      "reason": "identity_unresolved", "quarantine_uuid": "019372c3-…" },
    { "external_event_id": "ZK-K40-0043-8891280", "status": "rejected",
      "error": { "code": "punch.invalid_timestamp", "message": "…" } } ],
  "summary": { "accepted": 1, "duplicate": 1, "pending": 1, "rejected": 1 } }
```

`accepted` · `duplicate` · `pending` (quarantined, will be replayed on mapping) · `rejected`
(will never be accepted; the bridge must not retry it). *This four-verdict contract is
SmartPRS 2's SBB contract (C §1.3) and it is correct — it is adopted as the standard for
every ingest path, replacing `/iclock`'s `OK: n` and the pull paths' bare counts (C
requirement 17).*

**R-XXIV-155** A `rejected` verdict is **terminal and explained**. The bridge stops retrying
it, marks it locally, and surfaces it in its own UI. A verdict the sender cannot act on is a
verdict that produces an infinite retry loop.

**R-XXIV-156** Batch size and body size caps are **configuration**, returned by
`GET /api/v3/meta/limits` so the bridge can adapt without a release. *SmartPRS 2 hard-codes
`MAX_BATCH = 1000` and `MAX_BODY_BYTES = 2097152` (C requirement 28).*

### XXIV.8.3 Bridge authentication and enrolment

**R-XXIV-157** An SBB installation authenticates with a **scoped API key** bound to one
tenant, holding `attendance.ingest` and nothing else, or with an OAuth2 client-credentials
principal where the customer's policy requires short-lived tokens. The key never grants read
access to employee data.

**R-XXIV-158** **SMARTPRS 3 ARCHITECTURE RECOMMENDATION.** Enrolment is an explicit, audited,
two-step act with a pinned install fingerprint:

```
1. Administrator creates a Bridge Installation in the Integration Console
     → receives a one-time, short-lived enrolment code (not the credential)
2. The bridge posts POST /api/v3/integrations/bridges/enrol with the code plus
     its install fingerprint (hostname, OS, agent version, public key)
     → receives its credential, its tenant context and its assigned device scope
3. The console shows the installation as `enrolled`, with its fingerprint pinned
```

A credential presented from an install fingerprint that does not match the enrolment raises
an alert and is refused. *SmartPRS 2 has no enrolment concept: an unknown device serial
**auto-registers itself** with `tenant_id = NULL` and `enabled = true` from an
unauthenticated request (`PushController.php:201-228`; `BR-DEV-001`), and unknown-device
behaviour cannot be turned off.*

**R-XXIV-159** Unknown-device behaviour is a **per-tenant policy** with three settings —
`reject`, `quarantine_pending_approval` (default), `auto_register` — applied to devices
reported by an enrolled bridge (C requirement 9; Part XI).

**R-XXIV-160** `(tenant, device_serial)` is unique, and every device lookup is tenant-scoped
(C requirement 10; Law 6). *SmartPRS 2 has no unique index on `serial_number` and looks up by
`provider='push' AND serial_number=?` with **no tenant filter**, taking the highest id
(C §2.1).*

**R-XXIV-161** `GET /api/v3/meta/whoami` returns the customer name, the tenant, the granted
scopes, the assigned device scope and the server's business timezone, so an installer can
confirm the key points at the right workspace **before** shipping punches. *This preserves
SmartPRS 2's `GET /api/v1/ping` behaviour, which exists for exactly this reason (C §1.3) and
is genuinely good product design.*

### XXIV.8.4 Offline buffering and acknowledgement semantics

**R-XXIV-162** SBB buffers locally and durably. The contract states the buffer's minimum
guarantee — **at least 30 days of punches at the installation's rated volume** — and the
bridge raises a local alarm and a `bridge.buffer_pressure` event long before that limit.

**R-XXIV-163** A punch is deleted from the local buffer **only** on an explicit `accepted`,
`duplicate` or `rejected` verdict for that `external_event_id`. `pending` keeps it, because a
quarantined punch may still need re-sending if the server-side quarantine is purged. A
network failure, a timeout, a 5xx and a 429 all keep it.

**R-XXIV-164** On an ambiguous outcome (timeout after send), the bridge re-sends the same
batch with the same `Idempotency-Key` and the same `external_event_id`s. Both the idempotency
record (§XXIV.2.7) and the natural key make this exactly-once in effect.

**R-XXIV-165** Back-pressure is explicit: a `429` or `503` with `Retry-After` instructs the
bridge to back off; the bridge honours it and reports its backlog depth and oldest buffered
punch on every batch, so the server side can see a bridge falling behind before the customer
does.

**R-XXIV-166** Ordering is not required. The bridge may send out of order; SmartPRS 3
re-derives the attendance day idempotently when an earlier punch arrives late, because
recalculation is a first-class command (spine S10). *SmartPRS 2's direction-by-rank algorithm
already recomputes over the union of the incoming batch and stored punches, which is the
right instinct (C §4.6), and Part XI generalises it.*

**R-XXIV-167** The bridge reports its own health to `POST /api/v3/integrations/bridges/{uuid}/heartbeat`
— version, uptime, devices reachable and unreachable, buffer depth, last successful forward,
clock skew — and a missing heartbeat is an alertable staleness condition, distinct from "no
punches", because a factory on a holiday and a dead bridge look identical in punch volume.

### XXIV.8.5 Contract versioning between SmartPRS and SBB

**R-XXIV-168** The punch contract carries a version, declared by the bridge in `collector` and
negotiated on enrolment. SmartPRS 3 supports the current contract version and at least the
one preceding it, for no less than **18 months** — because a bridge sits on a customer's LAN
and cannot be assumed upgradable on the server's schedule. This is the single strongest
argument for versioning discipline in the whole product family.

**R-XXIV-169** `GET /api/v3/meta/limits` and the enrolment response tell the bridge what the
server supports (batch caps, contract versions, optional fields), so a newer bridge degrades
gracefully against an older server and vice versa.

**R-XXIV-170** A bridge running an unsupported contract version receives `409
contract.version_unsupported` naming the supported range, and the console shows the
installation as `upgrade_required` with the deadline — never a silent failure.

## XXIV.9 SmartDCM and the wider Ametecs ecosystem

### XXIV.9.1 The pattern

**R-XXIV-171** Every Ametecs product integrates with SmartPRS 3 through exactly the pattern
established above, with no product-specific machinery:

```
Sibling product  →  SmartPRS 3   :  signed inbound webhook (timestamp + nonce + HMAC)
                                    or a scoped OAuth2 client-credentials principal
                                    calling /api/v3
SmartPRS 3       →  Sibling      :  outbound webhook subscription from the published
                                    event catalogue, and/or the sibling calling /api/v3
Identity         :  a shared identity provider (§XXIV.9.3)
Data             :  never a shared table, never a shared schema, never a foreign key
```

**R-XXIV-172** A sibling product is a **tenant-owned integration** like any other: it appears
in the Integration Console, holds a credential the customer can rotate and revoke, is bound
by scopes and data scope, is rate-limited, and its every access is audited. A sibling product
holding an unrevokable, unscoped, invisible credential is how a customer's data leaves their
control without their knowledge.

### XXIV.9.2 SmartDCM

SmartDCM (document and content management) is the natural owner of the document estate that
SmartPRS 2 currently keeps on a **web-served public disk** — employee documents, photos,
commission proofs, off-roll agent KYC, and onboarding ID/address/bank/PCC/DRA documents that
are *copied* from the private disk to the public one at hire
(`DocumentController.php:234`; `LetterController.php:348, 467`; `RequestController.php:1605`;
`OffrollAgentController.php:450`; `SelfOnboardingController.php:953-955`; `SEC-23`, rated
CRITICAL deployment-dependent).

**R-XXIV-173** The SmartPRS ↔ SmartDCM contract is:

| Direction | Mechanism | Content |
|---|---|---|
| SmartPRS → SmartDCM | `POST` document + metadata over the DCM API, or a direct-upload ticket; classification, retention class, PII class and owning entity travel with it | Employee documents, letters, payslips, statutory returns, audit packs |
| SmartDCM → SmartPRS | Webhooks: `document.stored`, `document.verified`, `document.expiring`, `document.expired`, `document.superseded`, `document.deleted` | Drives compliance items, gates and expiry workflows |
| Retrieval | SmartPRS holds a **document reference**, never a file path, and resolves it to a signed, expiring, permission-checked URL at access time | — |

**R-XXIV-174** SmartPRS 3 never stores a document at a path a web server can serve, whether
or not SmartDCM is deployed. Where SmartDCM is not deployed, documents live on a private disk
behind the same authenticated, tenant- and ownership-scoped controller with signed expiring
URLs (spine S13). The interface the rest of the application sees is identical in both cases —
a document reference — so adopting SmartDCM later is a configuration change.

**R-XXIV-175** Retention class, legal-hold state and PII classification travel with every
document across the boundary, because a retention policy that stops at a product boundary is
not a retention policy (spine S16).

### XXIV.9.3 Shared identity and SSO

**R-XXIV-176** **SMARTPRS 3 ARCHITECTURE RECOMMENDATION.** A customer using more than one Ametecs product must not hold more than one set
of credentials. The ecosystem therefore assumes a **shared identity provider**, and SmartPRS 3
supports:

| Mode | Use |
|---|---|
| **SmartPRS as SP** — SAML 2.0 or OIDC against the customer's IdP (Azure AD, Google Workspace, Okta, ADFS) | Enterprise customers, the common case |
| **Ametecs Identity as IdP** — one Ametecs account signing in to SmartPRS, SmartEPT, SmartDCM | The multi-product SMB customer |
| **Local accounts** | On-premise and small customers with no IdP; still subject to the full password, lockout and MFA policy of Part XXII |

**R-XXIV-177** Whichever mode is in use, **authorisation stays in SmartPRS 3**. The IdP
asserts identity; roles, permissions and data scopes are resolved from SmartPRS's own model
(Part XXII). An IdP group may be **mapped** to a SmartPRS role by explicit, audited
configuration; it is never trusted as a permission. *SmartPRS 2 stores its whole role matrix
in a JSON blob any authenticated user can overwrite (`SEC-03`, CRITICAL) — permission data
must have exactly one owner and one write path.*

**R-XXIV-178** SSO provisioning is explicit: SCIM or a mapped just-in-time provisioning rule
that creates the user with a **declared default role and data scope**, never with an inherited
or guessed one. An unmapped IdP group results in a user with **no** access and an operator
notification. *An unmapped role in SmartPRS 2 renders as `Admin` (`AppController.php:93`;
`BR-SEC-003`).*

**R-XXIV-179** Session, MFA and step-up policies for SSO users are Part XXII's, and MFA
enforcement for privileged roles is satisfied either by the IdP (with an asserted AMR/ACR
claim that SmartPRS validates) or by SmartPRS itself. A claim that MFA occurred is accepted
only from an IdP explicitly configured as trusted for that assertion.

**R-XXIV-180** SSO configuration is per tenant, effective-dated and versioned like any other
configuration artefact, and a broken SSO configuration must never lock every administrator
out: a break-glass local administrator path exists, is MFA-mandatory, is time-boxed, and
every use raises an alert and an audit row.

## XXIV.10 Public API security

### XXIV.10.1 Threat model

| # | Threat | Control |
|---|---|---|
| T-01 | Credential theft (leaked key in a repo, a log, a support ticket) | Hashed at rest; shown once; scoped; expiry mandatory; rotation with overlap; IP allow-list; per-credential anomaly detection; `GET /meta/whoami` so a holder can see what a key can do without testing it destructively |
| T-02 | **Cross-tenant access** | Tenant from credential only; `tenant_id NOT NULL` and in every unique index (Law 6); a generated isolation test per aggregate **and per endpoint** in CI (§XXIV.10.4) |
| T-03 | **Object enumeration / IDOR** | UUIDv7 public ids only; a numeric path parameter fails the build; 404 for out-of-tenant and for non-existent alike |
| T-04 | Privilege escalation via scope or role | Scopes narrow only; an assigner may not grant beyond their own authority; scope-to-permission map is platform-owned and versioned |
| T-05 | Replay of a signed request | Timestamp + nonce inside the signature; freshness window; nonce store (§XXIV.4.4) |
| T-06 | **SSRF via connector or webhook target** | Egress profiles; loopback/link-local/RFC1918 blocked; re-resolution at connect time; no redirect following by default; redacted test output |
| T-07 | Injection (SQL, template, command) | Bound parameters only; named allow-listed statements in SQL recipes; SPX is not a programming language and cannot reach the filesystem, a socket or the database (spine S5) |
| T-08 | Mass data exfiltration through legitimate reads | Per-credential rate limits and quotas; sensitive fields require explicit request + field permission; volume anomaly alerting; every sensitive read audited (spine S14) |
| T-09 | Denial of service | Rate limits, quotas, body-size caps, expansion-depth caps, cursor pagination (no unbounded offsets), report execution as jobs, per-connector concurrency caps |
| T-10 | Malicious upload | MIME and magic-byte validation, never the client-supplied filename; private storage; virus scanning where configured; no client-supplied path ever stored or dereferenced (`SEC-23`, `SEC-24`) |
| T-11 | Supply chain (a partner's compromised system) | Per-partner credentials and scopes; revocation in one action; partner activity visible in the console; delivery and access logs retained |
| T-12 | Insider abuse of a platform credential | `platform.cross_tenant` is a separate permission, MFA-mandatory, per-use audited with the tenant named, and reportable to the customer |
| T-13 | Timing and error-message oracles | Uniform 401; constant-time comparisons; no account-existence or record-existence signal in status codes |
| T-14 | Log and telemetry leakage | Declared redaction at capture; no secret, token, PII field or raw foreign body in any log, error report or support export |

### XXIV.10.2 Non-negotiables

**R-XXIV-181** Every API route has an explicit permission and scope declaration; a route
without one **fails the build** and, at runtime, denies (spine S13; G requirement 26).

**R-XXIV-182** Authorisation **fails closed**. An exception inside authorisation denies,
logs, and alerts. *SmartPRS 2 has six controls that return "allowed" from `catch (\Throwable)`,
with the explicit comment "fail open — availability over strictness"
(`ApprovalService.php:377-379`; `FeaturePermissions.php:99-105`; `ApiKeyController.php:516-518`;
`EditionGuard.php:55-57`; `DemoWriteGuard.php:73-75`; `LicenseGate.php:73-75`;
`EnsureSubscriptionActive.php:58-59`; `SEC-01`, CRITICAL). No SmartPRS 3 control fails open,
ever, for any reason.*

**R-XXIV-183** An unknown role, an unmapped capability, a missing scope mapping or a null
data scope **denies** and raises an operational alert. *SmartPRS 2 degrades an unknown
capability key to `admin` + `hr_manager` (`FeaturePermissions.php:102`; `BR-SEC-002`).*

**R-XXIV-184** Self-service endpoints resolve the subject from the authenticated principal,
never from the request body or a path parameter. There is no `employee_uuid` parameter on a
self-service transaction (spine S13).

**R-XXIV-185** No raw exception message, stack trace, SQL fragment, file path or internal
class name reaches an API client, in any environment, for any status code. *194 sites do
today (consolidated requirement 45).*

**R-XXIV-186** Every sensitive-field read through the API writes an audit row (actor,
credential, fields, subject, purpose where declared). *G requirement 24: the
highest-impact findings in SmartPRS 2 are read paths that leave no trace.*

**R-XXIV-187** No production artefact contains a seeder, command or scheduled task that mints
an account or a credential with a known secret, and any credential-creating path refuses to
run under `APP_ENV=production` without an environment-supplied secret. *SmartPRS 2 ships
`Schedule::command('demo:reset')->dailyAt('03:30')` with no environment guard, which recreates
three known-password logins nightly on any server running the scheduler, taking over
pre-existing accounts by an unscoped lowercase email lookup (`routes/console.php:208-211`;
`DemoReset.php:35, 106-122`; `SEC-19`, CRITICAL).*

### XXIV.10.3 No sequential ids in URLs

**R-XXIV-188** Every externally visible identifier is a UUIDv7. Internal `bigint` keys never
appear in a URL, a payload, an export, a webhook or a filename (spine S2).

**R-XXIV-189** A route declaring an integer-typed path parameter, or a resource schema
exposing a column named `id` of an integer type, **fails the build**. *This is a mechanical
check, not a review convention, because SmartPRS 2's 18 route-reachable IDORs sit on top of
354 id-only queries — a volume no review process catches (G §7.4).*

**R-XXIV-190** Out-of-tenant and non-existent resources are indistinguishable: both return
`404` with `resource.not_found`. An authorisation-shaped `403` on a resource in another tenant
confirms that the resource exists.

### XXIV.10.4 API security tests that run in CI

**R-XXIV-191** The following suites are generated, blocking, and run on every pipeline. They
exist because SmartPRS 2 ships **three assertions and zero negative role tests** across its
entire authorisation surface (`tests/Feature/AuthAccessTest.php`, 21 lines; `D-15`).

| Suite | Generated from | Asserts |
|---|---|---|
| **Route coverage** | The route registry | Every route has a permission, a scope mapping, an OpenAPI entry and a policy binding |
| **Cross-tenant isolation** | The resource registry | For every endpoint: tenant A's credential receives 404 for every one of tenant B's resources — read, write and delete — including sub-resources, filters, exports and webhook payloads |
| **Permission matrix** | Permission registry × endpoint registry | For every (role, endpoint) pair, the expected allow/deny; a change to either registry that changes an outcome fails until the expectation is updated deliberately |
| **Scope enforcement** | Scope registry | A credential holding scope S reaches exactly the endpoints S maps to and no others; a scope mapping to nothing fails the build |
| **Fail-closed fault injection** | — | An exception injected into permission resolution, scope resolution, tenant resolution and data-scope resolution each produce a denial, a log line and an alert — never an allow |
| **IDOR sweep** | Route registry | Every path parameter is a UUID or a value-set code; guessed and enumerated UUIDs return 404 |
| **Idempotency** | Endpoint registry | Every unsafe endpoint replays identically under a repeated key; a changed fingerprint conflicts; concurrent duplicate submissions produce exactly one effect |
| **Rate limit** | Endpoint class registry | Limits apply per credential, headers are correct, 429 is retryable and honours `Retry-After` |
| **Webhook signature and replay** | — | A valid signature outside the freshness window is rejected; a repeated nonce is rejected; a tampered body is rejected; a rotated secret verifies during overlap and fails after |
| **Egress** | Egress profile registry | Every connector and webhook target is refused for `127.0.0.1`, `169.254.169.254`, `10.0.0.0/8`, `192.168.0.0/16`, `172.16.0.0/12`, a hostname resolving to those, and a redirect to those |
| **Error envelope** | OpenAPI | Every documented error path returns the envelope with a catalogued code, and no response body anywhere matches internal-detail patterns (SQL keywords, file paths, class names) |
| **Sensitive field** | Resource schemas | A sensitive field is absent unless explicitly requested and permitted, and every permitted read produced an audit row |
| **Contract compatibility** | OpenAPI diff | No breaking change inside `v3` without a recorded waiver |

**R-XXIV-192** The API test suite runs against the **sandbox tenant fixture**, which is the
same fixture published to partners, so a partner's failing call can be reproduced by Ametecs
exactly.

### XXIV.10.5 Abuse prevention

**R-XXIV-193** **SMARTPRS 3 ARCHITECTURE RECOMMENDATION.** Per-credential behavioural
baselines: request volume, error rate, sensitive-field
read volume, and geographic/IP spread. A deviation raises `api.credential.anomaly`, notifies
the tenant, and — above a configurable threshold — throttles rather than blocks, because
blocking a payroll integration at month end has its own cost.

**R-XXIV-194** Bulk read of sensitive fields is separately budgeted from ordinary reads and
requires the sensitive scope; exceeding the budget requires an explicit, audited, time-boxed
elevation rather than a silently higher limit.

**R-XXIV-195** A credential may be **revoked instantly** by a tenant administrator, and
revocation takes effect on the next request without a cache-expiry delay. Revocation writes an
audit row and notifies the credential's declared owner.

### XXIV.10.6 What a machine principal may never do

**R-XXIV-196** **SMARTPRS 3 ARCHITECTURE RECOMMENDATION.** The following are **never** available to a non-human principal, regardless of
scope: approving payroll; approving any maker-checker workflow step; changing bank details;
changing salary; publishing a statutory configuration, rule, formula or workflow; changing
roles or permissions; minting or rotating another credential with wider scope; deleting an
employee; and approving a full-and-final settlement. Each of these requires a human identity
with MFA, because each is a control whose entire value is that a person is accountable for it
(spine S8 maker-checker; S13).

**R-XXIV-197** An API-initiated action that requires human approval creates a workflow
instance and returns `202` with the instance's URL. It never performs the action and never
reports success. *This is the mechanism by which a partner integration can be given useful
write access without being given authority.*

## XXIV.13 Data model

Conventions per spine S16: `snake_case`; every business table carries `tenant_id BIGINT
UNSIGNED NOT NULL` with an FK and participation in every unique index; `uuid CHAR(36)` (v7)
unique per tenant is the external identifier; `created_at`/`updated_at` on every table;
`deleted_at` where soft delete applies; no database `ENUM` — every vocabulary is a reference
table with a code; instants are `DATETIME(3)` in UTC; dates are `DATE`; money is
`DECIMAL(18,4)` (no money in this part). "Audit" means the write path emits a spine S14
ledger row. PII classes: `none` · `internal` · `confidential` · `secret`.

Platform-scoped registries (scope registry, event catalogue, error catalogue, adapter
registry) are **generated from code at build time** and shipped as versioned seed data, not as
tenant tables — they are contracts, and a runtime-editable contract is not a contract.

## XXIV.14 Rules and expressions

SPX (spine S5) appears in this part in exactly two places, and nowhere else — there is no
second expression language for integrations.

**1. Webhook subscription filters.** A subscription may carry an SPX Boolean over the event
payload, evaluated with the `payload.*` namespace only:

```
-- Deliver payroll approvals only for the Telangana legal entity, and only above a threshold
payload.legal_entity.code = "AMTC-TG"
  AND payload.run.net_total > MONEY(50,00,000.00)

-- Deliver employee exits only for on-roll employees, excluding transfers between companies
payload.employment_type.code IN ["ON_ROLL"] AND payload.exit_reason.code <> "INTER_CO_TRANSFER"

-- Deliver a compliance expiry only within 30 days
DATEDIFF(payload.valid_to, period.start, "days") <= 30
```

**R-XXIV-209** A filter is type-checked and compiled at subscription time, stored as source
plus AST (spine S5), and is bounded by node count and evaluation time. A filter that errors at
delivery time **fails the delivery** (recorded, retried, and ultimately dead-lettered) rather
than silently dropping the event — because a dropped event is indistinguishable from an event
that never happened, and that is exactly how an integration loses a month of data without
anyone noticing.

**2. Connector recipe conditions.** A recipe may use SPX for a record-level inclusion
predicate and for derived field mapping within the declared grammar. It may **not** call any
function with I/O, because SPX has none (spine S5 absolute constraints). Customer-supplied
PHP, JavaScript or Python is never accepted in a recipe, under any configuration, for any
customer.

**Worked example — an Indian payroll integration filter.** A collections BPO runs payroll for
three legal entities but sends journals to Tally only for one of them, and only for approved
runs of the main monthly lot:

```
Subscription   "Tally journal — Ametecs Collections TG"
Events         payroll.run.approved
Filter (SPX)   payload.legal_entity.code = "AMTC-TG"
                 AND payload.run.type_code = "MONTHLY"
                 AND payload.run.lot_no = 1
Payload mode   fat  (requires payroll.read on the subscription's principal)
Target         https://tally-bridge.customer.example/hooks/payroll
Egress profile CUSTOMER_TALLY_BRIDGE  (host allow-list, HTTPS only)
Retry          9 attempts, exponential, full jitter, 46-hour window
Auto-disable   100 consecutive failures → notify Payroll Manager + IT Admin
```

None of this is code. Changing the entity, the lot, the threshold, the retry schedule or the
audience is configuration, which is the Section 127 standard applied to this part.

## XXIV.17 Migration implication

| SmartPRS 2 artefact | Verdict | Transformation |
|---|---|---|
| `api_keys` | **RETAIN** — "the single best-engineered security component in the codebase" (G §9) | Rows migrate to `api_credentials` with a generated `api_clients` principal each. `scopes` JSON is re-mapped: `ingest` → `attendance.ingest`; **`read` is dropped**, because it gated nothing (C requirement 36), and every holder is contacted before their key is re-scoped. `expires_at` is **mandatory** in v3, so a NULL expiry is set to migration + 90 days with notification |
| `ApiKeyAuth` / `ApiKeys` logic | **RETAIN as the pattern** | Hashing, `hash_equals`, prefix lookup with collision tolerance, tenant binding, NULL-tenant refusal and throttled `last_used_at` are carried forward unchanged into the new middleware |
| `smartept_webhook_endpoints` | **MIGRATE** | Rows become `webhook_inbound_endpoints` with `adapter_key='webhook.signed'`, `adapter_profile_code='smartept'`. Slug becomes `path_segment`. Counters carry over. **Secrets are re-encrypted under the new managed key and every endpoint is required to rotate within the overlap window**, because the old key material is derived from `APP_KEY`, which the commission-proof path traversal (`SEC-24`) may have exposed |
| `SmarteptSignature` / `SmarteptWebhook` | **MERGE** into the generic signed-webhook ingest | The signature, uniform 401 and tenant-from-endpoint design are kept; the SmartEPT event names, timezone conversion and identity assembly become adapter profile data (C §9) |
| The replay gap | **CLOSE at cut-over** | Timestamp and nonce become **required** on a declared date; a transition window accepts unsigned-timestamp requests with a `Deprecation` header, a per-endpoint counter, and a hard sunset. SmartEPT must ship its side first — this is a cross-product release dependency and is the reason D-XXIV-06 exists |
| `biometric_configs` (connector rows) | **MIGRATE** to `integration_connectors` | `provider` → `adapter_key`; `api_config` JSON → a **validated recipe artefact**, rejected rather than NULLed on failure; credentials (currently `Crypt`-encrypted, correctly) move to `integration_credentials` and are referenced by handle. **Any `api_config` that fails validation blocks that connector's migration and is reported for manual correction — it is not migrated as NULL** |
| `biometric_configs.tenant_id IS NULL` rows | **CLAIM OR PURGE before migration** | Law 6 admits no null tenant. Auto-registered `/iclock` device rows must be claimed by an administrator or purged, with a report per install (G §9) |
| `last_sync_at` / `last_status` | **SPLIT** | `last_success_at` takes the existing value; `last_attempt_at` and `last_attempt_status_code` start empty. The console must not imply an attempt history that was never recorded |
| Rolling `--days=1` window | **REPLACE** with a cursor | Each migrated connector's cursor is seeded from `last_sync_at` minus a configurable safety overlap, so the first v3 run re-fetches a bounded overlap rather than starting cold |
| `mobile_devices`, `biometric_unmapped`, runtime `biometric_configs` columns | **MIGRATE the data, delete the runtime DDL** | All runtime-created tables become migrations (Law 2). Shapes must be reconciled first: `PushController::ensure()` and `BiometricConfigController::ensureTable()` produce **different** `biometric_configs` definitions and whichever ran first wins on a given install (`DEF-C-10`), so migration begins with a per-install schema survey, not an assumption |
| `/api/v1/*` and `/iclock/*` | **COMPATIBILITY SHIM, then sunset** | See D-XXIV-12. A shim translating `/api/v1/attendance/punches` to the v3 contract lets deployed SBB installs keep working through the transition; `/iclock` is redesigned per Part XI |
| Public bearer-token portals | **REDESIGN** (Part XXII owns the token model) | Tokens hashed at rest, expiry and revocation added; **all existing tokens are invalidated at cut-over**, because they are cleartext, non-expiring and may have been disclosed (`SEC-17`) |
| 34 literal throttle strings | **REPLACE** with rate-limit configuration | Existing values seed the defaults so behaviour does not change silently at cut-over |
| Four error envelopes | **REPLACE** with one | The SPA is rebuilt against `/api/v3`, so there is no legacy consumer of the old shapes to preserve |
| `personal_access_tokens` (Sanctum, unused) | **DROP** | Installed, migrated, and used by zero routes (`D-21`) |
| `TenantController`, `CompanyScope`, `BelongsToCompany` | **DROP** | Dead or inert (G §9) |

**R-XXIV-214** Migration is **not** complete until every previously issued credential has been
re-scoped or revoked, every connector's recipe validates, every NULL-tenant integration row is
claimed or purged, and every inbound endpoint has rotated its secret. A partially migrated
integration layer is more dangerous than the old one, because the console then reports a
health it does not have.

**What does not come across:** the `read` scope; the `/app/*` view-shaped endpoints; the
client-side permission matrix and the `app_state` blob that carries it (`SEC-03`); the
fail-open guards; `GenericApiService`'s credential interpolation; the raw-body test output;
the `Company::value('id')` fallback in the legacy controllers (`BR-TEN-004`); and the demo and
seeder paths that mint known credentials (`SEC-19`, `SEC-20`).

## XXIV.18 Edge cases and failure states

| # | Situation | Behaviour |
|---|---|---|
| 1 | Idempotency key replayed while the first request is still running | `409 idempotency.in_progress` with `Retry-After`. Never executed twice |
| 2 | Idempotency key reused with a different body | `422 idempotency.key_reuse_conflict`. Never executed |
| 3 | Client retries after a network timeout; the server actually committed | The stored response is returned with `Idempotency-Replayed: true` |
| 4 | Two bridges send the same punch simultaneously | The natural-key unique index makes one a `duplicate`; both receive a coherent per-punch verdict |
| 5 | Cursor pagination while rows are inserted before the cursor | Not returned in this pass; found on the next full scan. Documented explicitly, because the alternative (offset) silently skips |
| 6 | Cursor presented with a changed filter or sort | `400 pagination.cursor_mismatch` — never a wrong page |
| 7 | Webhook receiver returns 200 but has not processed the event | Ametecs' responsibility ends at 200. The receiver contract states that 200 means durably accepted; the delivery log proves what was sent |
| 8 | Receiver is slow and the delivery times out after processing | The event is retried; the receiver de-duplicates on `event_uuid`. The contract's at-least-once guarantee makes this the receiver's documented obligation |
| 9 | Receiver's TLS certificate expires | `tls` failure class, retried, dead-lettered, subscription auto-disabled with notification naming the certificate |
| 10 | Receiver's DNS starts resolving to `127.0.0.1` | `egress.blocked` at connect time (re-resolution defeats rebinding); delivery fails; security event raised |
| 11 | Secret rotated but the receiver still verifies with the old one | Both signatures are sent during the overlap; the console shows which generation each delivery verified |
| 12 | Overlap ends while the receiver is still on the old secret | Deliveries fail with `http_401_403`, retry, dead-letter, auto-disable with notification. Replay after re-rotation recovers them within the retention window |
| 13 | An event is emitted for a transaction that then rolls back | Impossible — the outbox row is written in the same transaction |
| 14 | A tenant subscribes to an event carrying data its principal may not read | Subscription is accepted but the payload is filtered at delivery time; a `fat` subscription without the read permission is rejected at creation |
| 15 | A principal's permissions are narrowed after a subscription is created | Re-checked at delivery; the payload narrows; if nothing remains deliverable the subscription is auto-paused with notification |
| 16 | Connector credential expires mid-run | Run fails with `auth_failed`; connector state `credential_expired`; cursor **not** advanced; notification names the credential and its expiry |
| 17 | Vendor changes its response shape | Parse failure per record; records rejected and retained with excerpts; run outcome `partial`; **no heuristic sniffing attempts a guess** (`DEF-C-15`) |
| 18 | Vendor returns an HTML login page with status 200 | Content-type mismatch → `schema_mismatch`, whole run rejected. *SmartPRS 2 feeds such a body into a field-sniffing heuristic (`DEF-C-16`)* |
| 19 | Vendor's clock is 40 minutes ahead | Records beyond `now + skew_tolerance` are quarantined, not accepted; the connector's clock-skew diagnostic reports it |
| 20 | Scheduler outage of 3 days | The cursor is untouched; the next run walks the gap in `max_span` windows up to `max_look_back`; if the gap exceeds `max_look_back`, the run is **blocked** with an operator decision required, never silently truncated |
| 21 | An operator resets a cursor backwards by a month | Impact preview states the approximate re-fetch volume; duplicates are absorbed by the natural key; the reset is audited with its reason |
| 22 | A connector's counterparty is down for a week | Circuit opens; runs fail fast; staleness alert fires at 2 intervals; recovery emits `integration.connector.recovered` |
| 23 | Two administrators edit the same connector concurrently | `If-Match` / `412 resource.version_conflict`; last-write-wins is not available |
| 24 | An API key is leaked publicly | Anomaly detection or a customer report → instant revocation, effective on the next request; audit row; `integration.credential.revoked` notification |
| 25 | A partner requests a scope broader than its certification | Rejected at credential creation, naming the scope and the certification level |
| 26 | A tenant points a webhook at a competitor's URL | Endpoint verification challenge fails; subscription stays `pending_verification` and never delivers |
| 27 | A tenant's egress target is inside their own LAN (a valid on-prem case) | Requires a named, time-boxed LAN exception on the egress profile with a recorded approver — not a connector checkbox |
| 28 | A rate limit is hit mid-payroll-integration at month end | `429` with `Retry-After`; the integration backs off and completes; the anomaly path throttles rather than blocks (R-XXIV-193) |
| 29 | A bulk request exceeds the item cap | `413` naming the cap and pointing at the import-job path — never silently truncated |
| 30 | A long-running job's worker dies mid-run | The operation resource remains `running` until the heartbeat lapses, then transitions to `failed` with `worker_lost` and states exactly what was committed. Payroll's staged pipeline makes the restart point explicit (spine S11) |
| 31 | An `operation.completed` webhook is delivered before the client's poll | Both are correct and idempotent; the operation resource is the single source of truth |
| 32 | A sunset endpoint is called after its date | `410 api.endpoint_sunset` with a migration link. Never 404, never silent |
| 33 | A client sends `Idempotency-Key` on a `GET` | Ignored, documented |
| 34 | An inbound webhook arrives with a valid signature but a 20-minute-old timestamp | `401`, uniform response, `webhook.inbound.replay_rejected` raised — this is the case SmartPRS 2 accepts (`SEC-C-16`) |
| 35 | An inbound webhook arrives twice within the freshness window with the same nonce | The unique constraint on `(endpoint, nonce)` rejects the second even under concurrency |
| 36 | A bridge's local clock is wrong, so its signed timestamps fail freshness | Rejected with a distinguishable **operator-facing** diagnostic (clock skew is reported on the bridge's heartbeat), while the HTTP response stays uniform |
| 37 | A bridge is restored from a backup and re-sends a month of punches | All are `duplicate` on the natural key; the bridge clears its buffer; nothing is double-counted |
| 38 | A bridge upgrades to a contract version the server does not support | `409 contract.version_unsupported` naming the supported range; the console marks it `upgrade_required` |
| 39 | A tenant is suspended for non-payment while an integration runs | Credentials pause; in-flight runs complete; new requests return `403 tenant.suspended` with a distinct code so the partner can distinguish it from a permission failure |
| 40 | An on-premise install has no outbound internet | Outbound connectors and webhooks fail with `egress_refused`/`dns`; the console states plainly that no egress is available, rather than reporting a mysterious timeout |
| 41 | An API response would contain a sensitive field the caller may not read | The field is absent; requesting it explicitly returns `403`, not an empty value, because an empty value is an inference |
| 42 | A deprecated field is removed while a partner still calls it | Impossible without a waiver: the compatibility gate fails the build, and `api.deprecated_element.called` shows the caller before the sunset date |

## XXIV.20 Compliance with the seven laws

| Law | How this part complies |
|---|---|
| **1 — No business literal in code** | Rate limits, timeouts, retry policies, circuit thresholds, freshness windows, batch caps, retention periods, staleness thresholds, notice periods and webhook schedules are all configuration or platform-owned reference data. The only fixed values are security floors (§XXIV.12.3), which are stated as such |
| **2 — No schema change at runtime** | No integration path executes DDL. Every SmartPRS 2 runtime-created integration table (`biometric_unmapped`, `mobile_devices`, `biometric_configs` columns, a fourth `attendance_logs` shape) becomes a migration; the unauthenticated DDL path is deleted outright (`DEF-C-09`, Law 2) |
| **3 — Nothing overwritten; versioned and dated** | Recipes, egress profiles and SSO configuration are spine S4 artefacts. Credentials rotate rather than mutate. Deliveries, runs, rejections and events are append-only. `ETag`/`If-Match` prevents blind overwrite at the API boundary |
| **4 — Every number explains itself** | §XXIV.15: every delivery, every run, every quarantined and dropped record, every health verdict and every `403` is explainable from the console or from `/meta/whoami` |
| **5 — Authorisation server-side, declarative, fails closed** | Every route declares a permission and a scope; a missing declaration fails the build; every failure path denies; fault injection is a blocking CI suite (T-08). No control in this part fails open |
| **6 — Tenancy is structural** | Tenant comes from the credential only; `tenant_id NOT NULL` on every table here and in every unique index; generated cross-tenant isolation tests per endpoint (T-07); NULL-tenant integration rows must be claimed or purged before migration |
| **7 — Money is exact** | This part carries no money arithmetic. Money crossing the API boundary is serialised as an explicit `{ "amount_minor": 15000000, "currency": "INR" }` object — integer minor units and a currency, never a float and never a formatted string — so a client cannot reconstruct ₹1,50,000.00 wrongly. Formatted display strings, where offered, are an additional field, never the value |

## XXIV.21 Open items

**PRODUCT OWNER DECISION REQUIRED — D-XXIV-01: how much of the write API ships at v3.0.**
*Recommendation: the full read API plus writes for employees, leave, attendance inputs,
payroll variable inputs and documents; payroll execution and approval available as
job-and-workflow endpoints; statutory filing writes deferred to v3.1.*
Trade-off: a read-only launch is faster and lower-risk but leaves every customer's HRIS
integration one-directional, which is the integration customers actually ask for. A full write
launch multiplies the authorisation and idempotency test surface. The middle path above
front-loads the endpoints that unblock partners while keeping the highest-consequence writes
(payroll approval, statutory) behind workflows that require a human anyway (R-XXIV-196).

**PRODUCT OWNER DECISION REQUIRED — D-XXIV-02: is user-delegated OAuth (`authorization_code`
+ PKCE) in scope at v3.0?**
*Recommendation: no. Ship client credentials and API keys at v3.0; add the delegated flow at
v3.1 when a partner needs to act as a named user.*
Trade-off: delegated flow is required for consumer-facing partner apps (an expense app acting
as the employee). Deferring it costs nothing until such a partner exists; building it early
costs consent-screen, refresh-rotation and reuse-detection work that must be right first time.

**PRODUCT OWNER DECISION REQUIRED — D-XXIV-03: is API access included in every plan, or is it
a commercial tier?**
*Recommendation: read API included in all plans at a modest rate; write API and webhooks
included from the mid tier; higher rate limits and quota as a paid add-on.*
Trade-off: charging for the API suppresses exactly the ecosystem this part exists to build;
including it entirely forfeits a defensible revenue line and invites abuse by heavy pollers.
Note the precedent to avoid: SmartPRS 2's plan gating is **dead code** — `applyPlanGate()`
begins with an unconditional `return` (`D-09`) — so plans are sold with module lists nothing
enforces. Whatever is decided must be enforced by the same authorisation layer as roles
(G requirement 35).

**PRODUCT OWNER DECISION REQUIRED — D-XXIV-04: who approves an egress exception?**
*Recommendation: a tenant administrator may request; an Ametecs platform-security owner
approves; the exception is time-boxed (default 180 days) and auto-expires with notification.*
Trade-off: an egress allow-list weakens the "any vendor without code" promise — a customer's
on-premise device on an odd port needs an explicit permission, which is friction on the exact
path SmartPRS 2's customers use most (C open question 6). Self-approval by the tenant removes
the friction and restores `SEC-C-04` on Ametecs' infrastructure. **This decision is blocking
for the on-premise LAN connector design.**

**PRODUCT OWNER DECISION REQUIRED — D-XXIV-05: are the sunset windows commercially
acceptable?**
*Recommendation: 12 months for an endpoint, 18–24 months for a major version, 18 months
minimum for the SBB punch contract.*
Trade-off: long windows mean maintaining two behaviours and two test matrices. Short windows
break on-premise customers who upgrade annually at best and partners with their own release
cycles. The SBB window is the constraining one, because a bridge lives on a customer's LAN.

**PRODUCT OWNER DECISION REQUIRED — D-XXIV-06: SmartEPT contract ownership and the
SmartPRS → SmartEPT direction.**
*Recommendation: a single jointly owned contract document with a named owner in each product;
ship the inbound half (existing behaviour, plus replay protection) at v3.0 and the outbound
half (employee and attendance events to SmartEPT) at v3.1.*
Trade-off: SmartEPT today maintains its own roster by unknown means; giving it
`employee.created/.updated/.exited` removes that duplication but creates a cross-product
release dependency. **Closing the replay gap requires SmartEPT to ship its side first** — the
PO must confirm that SmartEPT can and will, and by when, because otherwise the transition
window in §XXIV.17 becomes indefinite.

**PRODUCT OWNER DECISION REQUIRED — D-XXIV-07: the SBB support window and who pays for bridge
upgrades.**
*Recommendation: support the current contract version and the one preceding it for 18 months;
bridge upgrades are included in the customer's support contract and are delivered by a
self-updating agent with a signed update channel (spine S18).*
Trade-off: a manually upgraded bridge fleet is an ongoing support cost and the reason
contract versions live forever. A self-updating agent on a customer's LAN needs the same
signing discipline as the application updater and must be agreed with customers' IT.

**PRODUCT OWNER DECISION REQUIRED — D-XXIV-08: Ametecs Identity as an IdP — now or later?**
*Recommendation: at v3.0 support SAML 2.0 and OIDC as a service provider only; defer Ametecs
Identity as an IdP until at least two products are live on the shared contract.*
Trade-off: a single Ametecs sign-on is a genuine multi-product selling point and the natural
answer to "we have three logins". Building it early makes SmartPRS 3 a dependency of every
other product's authentication, which is a heavy commitment to make before the ecosystem
exists. **This decision affects Part XXII's session model and should be taken with it.**

**PRODUCT OWNER DECISION REQUIRED — D-XXIV-09: who runs partner certification, and is it
chargeable?**
*Recommendation: a published, runnable certification suite that a partner executes themselves,
with an Ametecs review of the requested scopes and the data-handling declaration; free for the
first certification, chargeable for re-certification after a partner-side breaking change.*
Trade-off: a heavyweight certification protects customers and the Ametecs brand but is a
barrier at exactly the moment a partner ecosystem needs volume.

**PRODUCT OWNER DECISION REQUIRED — D-XXIV-10: sandbox data and who resets it.**
*Recommendation: wholly synthetic Indian seed data authored once by Ametecs; self-service
reset by the partner; automatic reset weekly.*
Trade-off: synthetic data will not exercise the messy shapes real customers have (duplicate
device codes, missing PAN, mid-month joiners). The mitigation is that the seed set is authored
from the migration analysis's real failure cases — never from customer data, which cannot
leave its tenant.

**PRODUCT OWNER DECISION REQUIRED — D-XXIV-11: does Ametecs or the customer own the partner
credential relationship?**
*Recommendation: the customer. A partner credential exists only with the customer's recorded,
inspectable, revocable consent, is per customer, and is visible in the customer's own console
(R-XXIV-205, R-XXIV-206).*
Trade-off: partner-wide credentials would be operationally simpler for the partner and for
Ametecs support, and are how `platform_support` works today — with `tenant_id = NULL`, zero
checks and full cross-tenant reach (`SEC-05`). Under DPDP the customer is the data fiduciary;
a credential they cannot see or revoke is not defensible.

**PRODUCT OWNER DECISION REQUIRED — D-XXIV-12: the compatibility window for `/api/v1` and
`/iclock`.**
*Recommendation: ship a translating shim for `/api/v1/attendance/punches` and `/api/v1/ping`
for 12 months, with `Deprecation`/`Sunset` headers and per-install usage reporting; `/iclock`
is redesigned per Part XI and its legacy behaviour is not shimmed beyond the device
quarantine path.*
Trade-off: no shim means every deployed SBB and every device integration must be upgraded in
the migration window, which is not achievable across an on-premise estate. A shim means
carrying the old contract — but the shim is thin, because the v1 punch contract is already
close to the canonical one (C §1.3). **The PO must confirm how many SBB installs exist and
who can reach them**, which is unanswered in the analysis and is a prerequisite for the
migration plan.
