## XXIX.0 Purpose

This part decides whether the rebuild is **deliverable**, and on what conditions.

It decides three things.

1. **That no migration design is approved until a live schema and data profile has been
   captured from every SmartPRS 2 install.** SmartPRS 2's schema is not reproducible from its
   own migrations. It is a function of which screens were opened, in which order, on which
   install. No production schema dump has ever been taken from any install
   (`N-…` Q-13, which records this as blocking *"every data-migration estimate"*;
   `J-…` §9 Q3, which concludes *"the only faithful reproduction of a production schema is a
   `mysqldump --no-data` of that specific database"*). Every number in this part —
   every effort estimate, every row count, every cutover window — is therefore **provisional
   until the discovery pack in §XXIX.2 has been run per install and signed off.** This is
   stated here as a hard gate, not as a caveat, and §XXIX.1.4 gives it a numbered gate
   condition that the programme plan cannot pass.
2. **That several categories of SmartPRS 2 data must not be migrated naively, because they are
   contaminated by defects.** Eleven months of fabricated `paid` payroll generated by a page
   load; leave filed as Loss of Pay and paid in full; loan `outstanding` values that are
   structurally unreliable; commissions stranded by an enum mismatch; cross-midnight
   attendance recorded as two days; PCC `'overdue'` values destroyed by a migration; an audit
   chain already broken in four places; and KYC/PCC/PAN documents on a publicly readable disk.
   Each is specified in §XXIX.4 with a handling recommendation and each is marked
   **PRODUCT OWNER DECISION**. Several are not migration questions at all — they are
   mispayment, disclosure and remediation questions with a legal clock, and they are called
   that here.
3. **That the largest and least appreciated part of the migration is not data — it is
   configuration.** SmartPRS 2's business rules are mostly hard-coded, so a customer's
   *actual* policy is not in their database. It is in the PHP, plus whatever the customer does
   manually in a spreadsheet outside the system. Migrating the rows without reconstructing the
   policy produces a SmartPRS 3 install that computes different numbers from the same inputs
   and cannot say why. §XXIX.5 specifies the three instruments that reconstruct it: a
   structured policy interview with a question bank derived from the rule engine's own
   configuration surface, back-testing against the customer's historical payroll and
   attendance, and a shadow-run harness that executes SmartPRS 3 rules against SmartPRS 2
   inputs and diffs the outputs.

It also decides the tooling (§XXIX.6), the signed reconciliation report and its **tolerance
policy** (§XXIX.7), the cutover strategy including the on-premise estate (§XXIX.8), the UAT and
sign-off artefact (§XXIX.9), and the hour-by-hour runbook (§XXIX.10).

**A note on tone.** This part is deliberately more hedged than the rest of the blueprint,
because it is the only part whose subject matter is *unknown data on machines nobody has
looked at*. Where the rest of the blueprint says "the system will", this part frequently says
"this cannot be known until discovery runs". That is not weakness in the plan; it is the plan.
A migration plan that pretends to know the shape of 200 unexamined databases is the single most
reliable way to fail this programme.

## XXIX.1 The migration problem, stated plainly

### XXIX.1.1 The schema is not reproducible from source

| Fact | Figure | Evidence |
|---|---|---|
| Distinct tables in a live SmartPRS 2 database | **~152** | `J-…` §9 Q1 |
| Tables defined by migrations | 102 (96 literal + 6 config-named) | `J-…` §9 Q1 |
| Tables that exist **only** because application code created them at runtime | **49** | `J-…` §9 Q1, §2.1.1 |
| Tables defined in **both** places | 52 | `J-…` §9 Q1 |
| …of which the migration produces a **different** schema from the runtime path | **15** | `J-…` §6.1, §9 Q2 |
| Migration-defined tables that are **dead** | 11 | `J-…` §2.1.2 |
| Foreign keys on business tables | **0** (4 total, all in the vendor Spatie migration) | `J-…` §9 Q4 |
| `*_id` columns with no constraint behind them | ~180 | `J-…` §9 Q4 |
| DDL `ENUM` columns | 35, of which 7 already emergency-widened and **12 live violations remain** | `J-…` §6.6, §9 Q6 |
| Runtime `Schema::create` / `Schema::table` call sites | 71 / 84, across 58 files | `G-…`; `J-…` §6.5 |
| Raw `ALTER TABLE` on HTTP request paths | 6 | `J-…` §6.5 |

`php artisan migrate:fresh` on an empty database produces 102 tables. A live database has
~152. Among the 49 that only runtime code creates are **`statutory_settings`** (the entire
PF/ESI/PT/TDS rate blob, `SettingsController.php:82`), **`pay_cycles`** (the payroll period),
**`roster`** and **`overtime`** (which feed attendance and payroll), **`salary_payments`** and
**`loan_recoveries`** (money ledgers), **`min_wages`**, **`dra_certs`** and
**`posh_complaints`** (regulated evidence), and **`user_password_resets`** (without which
authentication cannot function). Three migrations explicitly delegate to or hard-depend on
runtime-created tables: `2026_07_26_000400:25-28` calls `SchemaHelper::ensureColumns('pay_cycles', …)`
which returns immediately when the table is absent (`SchemaHelper.php:66-68`);
`2026_08_28_000200:32-34` returns early with the comment *"created with the column by
`BiometricConfigController::ensureTable()`"*; and `2026_08_16_000200:41-48` throws
`RuntimeException('attendance_logs is missing…')`.

### XXIX.1.2 Column *types* depend on which screens were opened first

This is the property that makes a single migration script impossible. The same column is a
different type on different customer installs, decided by execution order.

| Column | Type A | Type B | Decided by | Consequence |
|---|---|---|---|---|
| `employees.dra_expiry`, `.pcc_expiry`, `.pcc_deadline` | `DATE` (`2026_01_01_000100:139-142`, `2026_08_27_000100:71-81`) | `VARCHAR(255)` (`AppDataController.php:53-74`) | whichever ran first | date arithmetic becomes string comparison; **compliance alerts fire on the wrong people** (`J-…` §9 Q9 D1) |
| `employees.dob`, `.doj` | `DATE` (`2026_01_01_000100:113,128`) | `VARCHAR(255)` (`2026_06_24_000000:110-124`) | as above | service length, retirement, probation and gratuity all derive from a string (`J-…` D2) |
| `salary_components.calc_value` | `VARCHAR` (migration) | `DECIMAL(12,2)` (`MasterController`) | as above | a formula string `"0.4 * BASIC"` becomes `0.40`. **Payroll correctness diverges by install** (`J-…` §9 Q2, M3) |
| `settings.value` | `json` | `longText` | as above | invalid-JSON errors on one install; on the other, no unique key, so duplicate settings rows and `first()` reads an arbitrary one (`J-…` §9 Q2) |
| `attendance_pending` | bulk-upload schema | SBB quarantine schema | as above | **two disjoint features share one table name; one of them is always broken** (`J-…` §9 Q2; `B-…` DEFECT-B-03; `C-…` CONF-C-01) |
| `code_of_conduct_ack.acknowledged` | default `false` | default `true` | as above | **a compliance record that defaults to "acknowledged"** (`J-…` §9 Q2) |
| `training_subjects` | `program_id` bigint, no `tenant_id` | `program` string, with `tenant_id` | as above | the link column differs in name *and* type; cross-tenant content leakage (`J-…` §9 Q2) |
| `incentive_schemes` | `name`/`basis`/`slabs` | `title`/`rate_type`/`payout_method` | as above | **two different entities sharing a table name**; scheme saves fail on migrated installs (`J-…` §9 Q2, TRANSFORM list) |
| `offroll_agents` | `company_id NOT NULL`, `rate DECIMAL(12,2)` | no `company_id`, `rate DECIMAL(14,2)` | as above | candidate→agent conversion fails on migrated installs (`J-…` §9 Q2) |
| `messages_log.sent_at` | `timestamp` | `date` | as above | broadcast time lost on runtime installs (`J-…` D11) |
| `documents.tenant_id` | `NOT NULL` | nullable | as above | NULL-tenant document rows invisible to their owner (`J-…` §9 Q2) |
| `faqs.question` | `VARCHAR(255) NOT NULL` | `VARCHAR(500) NULL` | as above | `1406 Data too long` on one install (`J-…` §9 Q2) |

There are further divergences on `attendance_logs` (nullability, `direction` width, `source`
default, and a **missing composite index** on some installs), `letters.status`,
`training_programs.status` case, and `test_attempts.score` scale (`J-…` §9 Q2).

### XXIX.1.3 No production schema dump has ever been taken

This is the single most consequential fact in this part. It is recorded independently by two
analysts:

- `N-…` Q-13: *"Is the live schema what the code builds? … 59 runtime-created tables, at least
  8 with competing definitions, and **no live dump was ever taken**. … `mysqldump --no-data`
  from a production install. **This blocks every data-migration estimate in §9.**"*
- `J-…` §9 Q3: *"The only faithful reproduction of a production schema is a `mysqldump
  --no-data` of that specific database."*

And `J-…` §9 records five structural migration blockers that follow from it:

1. **The source schema cannot be read from source code.** Every migration script must
   introspect `information_schema` **per install**.
2. **No install is a reference install.** There is no canonical schema to diff against.
3. **Duplicates are guaranteed** on `employees.pan / uan / bank_acc / esic_no / mobile /
   email`, on `payroll_runs (company, month)` and on `payslips (employee, month)`, because the
   constraints were deliberately never applied — migration `2026_08_28_000100:121-124` states
   in terms that these are *"deliberately plain indexes, never UNIQUE"*.
4. **Orphans are guaranteed** everywhere, because there are no foreign keys, and
   `RequestController.php:1246-1259` exists *solely* to sweep them.
5. **The demo-data contamination has no reliable discriminator** beyond
   `attendance_logs.source='demo'` and `tenants.subdomain='demo'` — and even that fails,
   because rows fabricated before rev 51 were tagged `source='biometric'` and the purge
   command's own docblock records that they *"are indistinguishable from real device punches"*
   (`PurgeDemoAttendance.php:16-18`).

### XXIX.1.4 Therefore: the discovery gate

**R-XXIX-001.** No SmartPRS 3 migration script, effort estimate, cutover date or commercial
commitment may be approved for a given install until that install's **Discovery Pack**
(§XXIX.2) has been captured, validated and countersigned. This is **Gate G-1**. The programme
plan treats an install with no Discovery Pack as **not yet in scope**, not as "assumed
standard".

**R-XXIX-002.** Every quantitative statement in this part — table counts, row counts, effort,
duration, tolerance thresholds — is declared **PROVISIONAL** and carries that marker until
superseded by the corresponding Discovery Pack figure. A provisional figure may not be used as
an acceptance criterion.

**R-XXIX-003.** The migration tooling MUST introspect `information_schema` at run time for
every source table and column it reads, and MUST refuse to run against a schema whose
fingerprint (§XXIX.2.2) is not present in its compatibility register. It MUST NOT assume any
column type, nullability, index or presence from SmartPRS 2's migration files.

**R-XXIX-004.** The migration tooling MUST NOT execute any DDL against the source database, and
MUST connect to it with a **read-only** database user. This is not a convenience: SmartPRS 2's
own migrations delete rows (`2026_08_16_000200:154`, `2026_08_17_000100:232` hard-delete from
`attendance_logs` inside `up()`), and `2026_08_16_000200:128` invokes
`Artisan::call('attendance:dedupe')` — an unlogged, unbounded hard delete — automatically
during `php artisan migrate` (`B-…` DEFECT-B-25; `M-…` Q-12). Nothing the migration tooling
does may risk triggering that class of behaviour.

**R-XXIX-005.** Before any read of a source database, a **full verified backup** of that
database (schema + data) and of the document storage tree MUST exist, MUST have been restored
into a scratch instance, and MUST have passed a row-count comparison. An unrestored backup is
not a backup (spine S18; `I-…` Q-08 records that no restore has ever been performed from a
SmartPRS backup and that no restore path exists in the product at all).

**R-XXIX-006.** All migration development, dry-running and rehearsal MUST be performed against
a **restored copy** of the customer's database in an isolated environment, never against the
live database.

## XXIX.2 The pre-migration discovery programme

### XXIX.2.1 What discovery is and what it produces

The Discovery Pack is a **single, signed, read-only evidence archive** produced per install. It
is produced by a tool Ametecs ships and an Ametecs engineer or a supervised customer
administrator runs. It is the input to migration design, to the effort estimate, to the
contamination dispositions in §XXIX.4, and to the configuration reconstruction in §XXIX.5.

**R-XXIX-007.** The Discovery Pack MUST be reproducible: running it twice on an unchanged
database MUST produce byte-identical output except for the timestamp and signature.

**R-XXIX-008.** The Discovery Pack MUST be signed by the collection tool using an
Ametecs-issued key and MUST record the collecting engineer, the customer, the install
identifier, the application revision, the collection start and end instants, and the source
database server version and SQL mode.

**R-XXIX-009.** The Discovery Pack MUST be classified as containing **personal data** (it
carries counts, samples and, for some checks, identifying values), MUST be encrypted at rest,
MUST be transported over an authenticated channel, and MUST carry an explicit retention clock
(recommendation: destroy 90 days after the install's sign-off, §XXIX.9). SmartPRS 2's own PII
posture makes this non-optional: employee documents currently sit on a publicly readable disk
(§XXIX.4.8).

Establishes which of the type-divergence cases in §XXIX.1.2 this install has | Everything |

**The schema fingerprint.** `D1` yields a **schema fingerprint**: the SHA-256 of a canonical
serialisation of `information_schema.COLUMNS` and `STATISTICS` for the application's tables,
excluding row counts and auto-increment values. Installs sharing a fingerprint share a
migration profile. This is what turns "200 unknown databases" into a manageable number of
**profiles**. Spine S18 requires the same fingerprint mechanism in SmartPRS 3 at boot; this is
its first application.

**R-XXIX-010.** The migration tooling MUST maintain a **schema profile register** keyed by
fingerprint, recording for each profile: the installs that carry it, the resolved type of every
divergent column in §XXIX.1.2, which of the two `attendance_pending` shapes is present, which
tables are absent, and the transformation variant selected for each affected entity.

### XXIX.2.3 D1 — schema capture (runnable)

```sql
-- discovery/d1_schema.sql
-- Run as a READ-ONLY user. Substitute :db for the application database name.

-- D1.1  Table inventory with engine, collation, row estimate and comment.
SELECT TABLE_NAME, ENGINE, TABLE_COLLATION, TABLE_ROWS, DATA_LENGTH, INDEX_LENGTH,
       CREATE_TIME, UPDATE_TIME, TABLE_COMMENT
FROM information_schema.TABLES
WHERE TABLE_SCHEMA = :db
ORDER BY TABLE_NAME;

-- D1.2  Full column definition for every table. THIS is the authority, not the migrations.
SELECT TABLE_NAME, ORDINAL_POSITION, COLUMN_NAME, COLUMN_TYPE, DATA_TYPE,
       CHARACTER_MAXIMUM_LENGTH, NUMERIC_PRECISION, NUMERIC_SCALE,
       IS_NULLABLE, COLUMN_DEFAULT, EXTRA, COLUMN_KEY, COLLATION_NAME, COLUMN_COMMENT
FROM information_schema.COLUMNS
WHERE TABLE_SCHEMA = :db
ORDER BY TABLE_NAME, ORDINAL_POSITION;

-- D1.3  Every index, so a missing composite index is visible per install.
SELECT TABLE_NAME, INDEX_NAME, NON_UNIQUE, SEQ_IN_INDEX, COLUMN_NAME,
       SUB_PART, NULLABLE, INDEX_TYPE
FROM information_schema.STATISTICS
WHERE TABLE_SCHEMA = :db
ORDER BY TABLE_NAME, INDEX_NAME, SEQ_IN_INDEX;

-- D1.4  Foreign keys. Expect four, all Spatie. Anything else is a surprise worth knowing.
SELECT CONSTRAINT_NAME, TABLE_NAME, COLUMN_NAME,
       REFERENCED_TABLE_NAME, REFERENCED_COLUMN_NAME
FROM information_schema.KEY_COLUMN_USAGE
WHERE TABLE_SCHEMA = :db AND REFERENCED_TABLE_NAME IS NOT NULL
ORDER BY TABLE_NAME, CONSTRAINT_NAME;

-- D1.5  The migration ledger. Tells us which migrations this install believes it ran,
--       which is NOT the same as which schema it has.
SELECT id, migration, batch FROM migrations ORDER BY id;

-- D1.6  The type-divergence probes of XXIX.1.2, answered directly.
SELECT TABLE_NAME, COLUMN_NAME, COLUMN_TYPE, IS_NULLABLE, COLUMN_DEFAULT

 OR (TABLE_NAME = 'incentive_schemes')

 OR (TABLE_NAME = 'letters')
 OR (TABLE_NAME = 'loans')
 OR (TABLE_NAME = 'commissions')
 OR (TABLE_NAME = 'shifts')
 OR (TABLE_NAME = 'late_policy')
  )
ORDER BY TABLE_NAME, COLUMN_NAME;

-- D1.7  Which of the 49 runtime-only tables exist here, and which of the 11 dead ones do.
SELECT t.n AS expected_table,
       CASE WHEN i.TABLE_NAME IS NULL THEN 'ABSENT' ELSE 'PRESENT' END AS state
FROM (

  SELECT 'roster'               UNION ALL SELECT 'overtime'        UNION ALL
  SELECT 'salary_payments'      UNION ALL SELECT 'loan_recoveries' UNION ALL
  SELECT 'min_wages'            UNION ALL SELECT 'dra_certs'       UNION ALL

  SELECT 'policies'             UNION ALL SELECT 'awards'          UNION ALL
  SELECT 'notices'              UNION ALL SELECT 'feature_flags'   UNION ALL
  SELECT 'transfers'            UNION ALL SELECT 'onboarding'      UNION ALL
  SELECT 'onboarding_items'     UNION ALL SELECT 'offroll_agents'  UNION ALL
  SELECT 'agent_earnings'       UNION ALL SELECT 'biometric_configs' UNION ALL
  SELECT 'biometric_unmapped'   UNION ALL SELECT 'attendance'      UNION ALL
  SELECT 'attendance_pending'   UNION ALL SELECT 'employee_company' UNION ALL
  SELECT 'notifications_feed'   UNION ALL SELECT 'company_emails'  UNION ALL
  SELECT 'pf_esi_settings'      UNION ALL SELECT 'tds_rules'       UNION ALL
  SELECT 'pt_slabs'             UNION ALL SELECT 'password_reset_tokens' UNION ALL
  SELECT 'salary_runs'          UNION ALL SELECT 'salary_slips'    UNION ALL
  SELECT 'leave_applications'   UNION ALL SELECT 'mobile_devices'  UNION ALL

```

**The `attendance_pending` discriminator.** `D1.6` returns the table's column list; the
collection tool classifies it by column presence and records the verdict in the fingerprint:

```
bulk shape       → columns include in_at, out_at, batch, log_date  (AttendanceBulkController.php:47-48)
quarantine shape → columns include punch_at, device_code, external_id, source
mixed            → both sets present  → rows must be routed individually (J-… §9 AMBIGUOUS; C-… OQ 13)
```

**R-XXIX-011.** Where `attendance_pending` is classified **mixed**, the migration MUST route
every row individually by populated-column set, MUST count rows matching neither shape, and
MUST list them in the exception report. It MUST NOT guess.

### XXIX.2.4 D2 — row counts and date ranges (runnable)

`TABLE_ROWS` from `information_schema` is an estimate on InnoDB and must not be used for
reconciliation. Exact counts are required.

```php
<?php
// discovery/d2_counts.php — read-only. Emits profile/row_counts.csv and profile/date_ranges.csv
// Usage: php d2_counts.php --dsn=... --user=ro_user --pass=... --out=./pack

$pdo = new PDO($dsn, $user, $pass, [PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION]);
$db  = $pdo->query('SELECT DATABASE()')->fetchColumn();

$tables = $pdo->query(
    "SELECT TABLE_NAME FROM information_schema.TABLES
      WHERE TABLE_SCHEMA = " . $pdo->quote($db) . " AND TABLE_TYPE='BASE TABLE'
      ORDER BY TABLE_NAME"
)->fetchAll(PDO::FETCH_COLUMN);

// Date-bearing columns worth ranging, discovered rather than assumed.
$dateTypes = ['date','datetime','timestamp'];

$counts = [];
$ranges = [];
foreach ($tables as $t) {
    $q = $pdo->quote($t);

    // Exact count. On a large attendance_logs this is the expensive part; it is also the
    // only number the reconciliation report may cite.
    $counts[] = [$t, (int) $pdo->query("SELECT COUNT(*) FROM `$t`")->fetchColumn()];

    // Per-tenant count where a tenant column exists — four possible names (J-… §9 Q7).
    foreach (['tenant_id','company_id'] as $tc) {
        $has = $pdo->query(
            "SELECT COUNT(*) FROM information_schema.COLUMNS
              WHERE TABLE_SCHEMA=" . $pdo->quote($db) . " AND TABLE_NAME=$q
                AND COLUMN_NAME=" . $pdo->quote($tc)
        )->fetchColumn();
        if (! $has) { continue; }
        foreach ($pdo->query(
            "SELECT `$tc` AS k, COUNT(*) c FROM `$t` GROUP BY `$tc` ORDER BY `$tc`"
        ) as $r) {
            // NULL and 0 are BOTH in production use as the platform sentinel (J-… PO-13),
            // and a NULL-tenant row is invisible to every ->when($tid,…) filter (G-…).
            $counts[] = ["$t#$tc=" . ($r['k'] === null ? 'NULL' : $r['k']), (int) $r['c']];
        }
    }

    // Date ranges for every date-typed column: sizes the retention cut-off and proves
    // which months of history actually exist.
    $cols = $pdo->query(
        "SELECT COLUMN_NAME, DATA_TYPE FROM information_schema.COLUMNS
```

```php
// discovery/d5_app_state.php — read-only extraction and inventory of the app_state blob.
// Emits blobs/app_state/<tenant>.json (verbatim) and blobs/app_state_inventory.csv.

$rows = $pdo->query(
    "SELECT id, tenant_id, `key`, `value`, updated_at
       FROM settings

)->fetchAll(PDO::FETCH_ASSOC);

foreach ($rows as $r) {
    $tid = $r['tenant_id'] === null ? 'NULL' : $r['tenant_id'];

    // 1. Store the blob VERBATIM. Never re-encode: re-encoding loses key order,
    //    numeric-string coercion and any invalid UTF-8 that is itself evidence.
    file_put_contents("$out/blobs/app_state/$tid.json", $r['value']);

    // 2. Parse defensively. A blob that does not parse is itself a finding — the column
    //    type is json on some installs and longText on others (J-… §9 Q2), so an install
    //    on longText can hold a truncated or invalid document with no error ever raised.
    $doc = json_decode($r['value'], true);
    if (! is_array($doc)) {
        $inv[] = [$tid, '(UNPARSEABLE)', 0, 0, strlen($r['value']),
                  json_last_error_msg(), $r['updated_at']];
        continue;
    }

    // 3. Inventory every collection: name, element count, whether elements are homogeneous,
    //    the union of keys observed, and whether it looks like prototype seed data.
    foreach ($doc as $coll => $val) {
        $n     = is_array($val) ? count($val) : 0;
        $keys  = [];
        $shapes = [];
        if (is_array($val)) {
            foreach ($val as $el) {
                if (! is_array($el)) { continue; }
                $k = array_keys($el);
                sort($k);
                $shapes[implode('|', $k)] = ($shapes[implode('|', $k)] ?? 0) + 1;
                $keys = array_unique(array_merge($keys, $k));
            }
        }
        sort($keys);
        $inv[] = [
            'tenant'        => $tid,
            'collection'    => $coll,
            'elements'      => $n,
            'distinct_shapes' => count($shapes),   // >1 means the collection is heterogeneous
            'key_union'     => implode('|', $keys),
            'bytes'         => strlen(json_encode($val)),
            'updated_at'    => $r['updated_at'],
        ];
    }
}
```

### XXIX.2.9 D7 — loan and advance balance reconciliation

`DEF-P02` (CRITICAL) means loan EMIs have either **never been recovered** or have been
**recovered indefinitely**. The migrated `loans` table is
`id, tenant_id, employee_id, amount, emi, tenure, outstanding, status, timestamps`
(`2026_01_01_000300:119-129`). `loanEmiDue():670-709` reads `installment_amount`,
`start_month`, `installments_total`, `tenure_months` and `type` — **none of which exists in any
migration**; `installments_paid` is created at runtime by `generate():2580-2587`; and the one
migrated column that could work, `tenure`, is **never read by anything**. The request form's
`tenure_months` field is silently discarded on every save because `ApprovalService::safeRow():265`
intersects the payload with the actual column list.

The two failure modes, both live:

- **`outstanding = 0`** (the column default): the guard at `:696` reads
  `0 !== null && (float) 0 <= 0` → `continue`. **The EMI is never recovered at all.** Nothing
  in the application ever writes `loans.outstanding` — verified by grep across `app/`.
- **`outstanding` non-zero** (a legacy row or a manual DB edit): `$total` evaluates to `0`, so
  the "fully recovered" guard never fires and the auto-close guard at `:2795` never fires.
  **The EMI is deducted every month forever** until someone manually sets `status='closed'`.

Advances are worse: they recover in one month, key on `created_at`, have no ledger, and ignore
`per_month`/`balance`; shortfalls were silently dropped (`A-…` §9; `A-…` OQ-6, DEF-P19).

```sql
       SUM(outstanding > 0)                                    AS forever_recovered_candidates,
       SUM(status = 'closed')                                  AS closed,
       SUM(emi IS NULL OR emi = 0)                             AS no_emi,
       SUM(tenure IS NULL OR tenure = 0)                       AS no_tenure
FROM loans;

-- D7.2  Per-loan truth table. The ONLY reliable evidence of what was actually recovered
--       is loan_recoveries — a runtime-only table with NO INDEX ON ANY COLUMN
--       (J-… §9 Q5), whose rows for a regenerated run were hard-deleted at :2448.
SELECT l.id, l.tenant_id, l.employee_id, e.emp_code, e.name,
       l.amount           AS sanctioned,
       l.emi              AS emi_declared,
       l.tenure           AS tenure_declared,
       l.outstanding      AS outstanding_stored,
       l.status,
       COUNT(lr.id)       AS recovery_rows,
       COALESCE(SUM(lr.amount), 0) AS recovered_total,
       l.amount - COALESCE(SUM(lr.amount), 0) AS derived_outstanding,
       MIN(lr.created_at) AS first_recovery,
       MAX(lr.created_at) AS last_recovery
FROM loans l
  LEFT JOIN employees       e  ON e.id  = l.employee_id
  LEFT JOIN loan_recoveries lr ON lr.loan_id = l.id
GROUP BY l.id
ORDER BY ABS(l.amount - COALESCE(SUM(lr.amount), 0)) DESC;

-- D7.3  Over-recovery: a loan where recovered EXCEEDS sanctioned. Each of these is a
--       potential repayment owed to an employee.
SELECT l.id, e.emp_code, e.name, l.amount, SUM(lr.amount) recovered,
       SUM(lr.amount) - l.amount AS over_recovered
FROM loans l JOIN loan_recoveries lr ON lr.loan_id = l.id
  LEFT JOIN employees e ON e.id = l.employee_id
GROUP BY l.id HAVING SUM(lr.amount) > l.amount
ORDER BY over_recovered DESC;

-- D7.4  Recovery rows pointing at a run that no longer exists — the :2448 best-effort
--       try/catch failure. The instalment counter for these loans is permanently wrong.
SELECT lr.loan_id, COUNT(*) orphan_recoveries, SUM(lr.amount) orphan_amount
FROM loan_recoveries lr LEFT JOIN payroll_runs r ON r.id = lr.run_id
WHERE r.id IS NULL GROUP BY lr.loan_id;

-- D7.5  installments_paid — created at runtime, so absent on some installs.
SELECT COUNT(*) FROM information_schema.COLUMNS
 WHERE TABLE_SCHEMA = :db AND TABLE_NAME='loans' AND COLUMN_NAME='installments_paid';

-- D7.6  Advances: recovered in one month from created_at, per_month and balance ignored
--       (A-… §9). Any advance whose balance is non-zero is an unresolved liability.
SELECT a.id, a.tenant_id, a.employee_id, e.emp_code, a.amount, a.per_month, a.balance,
       a.status, a.created_at,
       (SELECT COUNT(*) FROM deductions d
         WHERE d.employee_id = a.employee_id AND d.type LIKE '%advance%') AS deduction_rows
FROM advances a LEFT JOIN employees e ON e.id = a.employee_id
ORDER BY a.balance DESC;

-- D7.7  Clawbacks and their run keying — the one-month-only rule is not configurable
--       (A-… §9).
SELECT id, tenant_id, employee_id, amount, month, recovered_run_id, status
FROM clawbacks ORDER BY tenant_id, month;
```

### XXIX.2.10 D8 — leave balance derivation

There is no leave ledger. The balance is a derived figure, carry-forward was never applied, and
`leaves.type_id` is **never written by any code path** — verified by grep: two reads, zero
writes (`E-…` §2, DEF-LVE-02). Consequently the paid/unpaid flag never reaches payroll and
**every approved leave, including leave explicitly filed as "Loss of Pay", was credited as a
paid present day**.

```sql

-- D8.1  Confirm the defect on THIS install: type_id must be NULL on every row.
SELECT COUNT(*) total,
       SUM(type_id IS NULL) null_type_id,
       SUM(type_id IS NOT NULL) populated_type_id,
       COUNT(DISTINCT type_name) distinct_type_names
FROM leaves;

-- D8.2  The blast radius: approved leave whose TYPE NAME indicates unpaid/LOP, which was
--       nevertheless credited as paid. This is the mispayment population (E-… PO-01).
--       The name match is deliberately broad; every hit is triaged by a human.
SELECT l.id, l.tenant_id, l.employee_id, e.emp_code, e.name AS employee,
       l.type_name, l.from_date, l.to_date, l.days, l.status, l.decided_at,
       DATE_FORMAT(l.from_date, '%Y-%m') AS period_label
FROM leaves l LEFT JOIN employees e ON e.id = l.employee_id
WHERE l.status = 'approved'
  AND (  LOWER(l.type_name) LIKE '%loss of pay%'
      OR LOWER(l.type_name) LIKE '%lop%'
      OR LOWER(l.type_name) LIKE '%unpaid%'
      OR LOWER(l.type_name) LIKE '%without pay%'
      OR LOWER(l.type_name) LIKE '%lwp%' )
ORDER BY l.from_date;

-- D8.3  Which of those overlap a GENERATED payslip — i.e. money actually moved.
SELECT p.id AS payslip_id, p.employee_id, e.emp_code, p.month, p.gross, p.net,
       SUM(l.days) AS lop_days_credited_as_paid
FROM leaves l
  JOIN employees e ON e.id = l.employee_id
  JOIN payslips  p ON p.employee_id = l.employee_id
                  AND p.month = DATE_FORMAT(l.from_date, '%Y-%m')
WHERE l.status = 'approved'
  AND (LOWER(l.type_name) LIKE '%loss of pay%' OR LOWER(l.type_name) LIKE '%lop%'
    OR LOWER(l.type_name) LIKE '%unpaid%'      OR LOWER(l.type_name) LIKE '%without pay%'
    OR LOWER(l.type_name) LIKE '%lwp%')
GROUP BY p.id
ORDER BY p.month, e.emp_code;

-- D8.4  Leave types whose names no longer resolve — the manual reconciliation step
--       (E-… §9: "a manual reconciliation step per tenant for renamed/orphaned names").
SELECT l.tenant_id, l.type_name, COUNT(*) c
FROM leaves l
  LEFT JOIN leave_types t ON t.tenant_id = l.tenant_id AND t.name = l.type_name
WHERE t.id IS NULL
GROUP BY l.tenant_id, l.type_name ORDER BY c DESC;

-- D8.5  The naive derived balance per employee per type per year, on the CALENDAR-year
--       basis the code uses today. This is an INPUT to the customer conversation, never
--       an opening balance (E-… PO-02, PO-06, PO-07).
SELECT l.tenant_id, l.employee_id, e.emp_code, l.type_name,
       YEAR(l.from_date) AS leave_year,
       SUM(CASE WHEN l.status='approved' THEN l.days ELSE 0 END) AS approved_days,
       SUM(CASE WHEN l.status='pending'  THEN l.days ELSE 0 END) AS pending_days,
       t.quota AS declared_quota, t.paid AS declared_paid, t.carry_forward
FROM leaves l
  LEFT JOIN employees   e ON e.id = l.employee_id
  LEFT JOIN leave_types t ON t.tenant_id = l.tenant_id AND t.name = l.type_name
GROUP BY l.tenant_id, l.employee_id, l.type_name, YEAR(l.from_date)
ORDER BY l.tenant_id, e.emp_code, l.type_name, leave_year;

-- D8.6  Calendar-days-charged vs working-days-credited divergence (E-… PO-07): a Fri–Mon
--       leave costs 4 days of balance and credits 2 days of attendance.
SELECT COUNT(*) spanning_a_weekend
FROM leaves
WHERE status='approved' AND DATEDIFF(to_date, from_date) >= 2
  AND (WEEKDAY(from_date) >= 4 OR WEEKDAY(to_date) <= 1);
```

**R-XXIX-026.** Opening leave balances MUST be **stated by the customer per employee per leave

## XXIX.3 The entity-by-entity migration matrix

### XXIX.3.0 Verdict vocabulary

| Verdict | Meaning |
|---|---|
| **MIGRATE AS-IS** | Row-for-row copy with column renames and type normalisation only. No semantic change. |
| **TRANSFORM** | Copy with a defined, testable data transformation — reshaping, splitting, exploding a blob, resolving a name to an id. |
| **DERIVE** | The target is computed from source data rather than copied; the source shape does not survive. |
| **RECONSTRUCT** | The target cannot be produced from data at all. It is authored — from the policy interview, from the customer's manual records, or from the SmartPRS 2 source code read as a specification. |
| **FREEZE** | Migrated as immutable historical fact, marked legacy, never recomputed, never re-derived, and excluded from SmartPRS 3's forward-looking engines. |
| **DO NOT MIGRATE** | Left behind. |

Every entity below carries: **source tables** · **target** · **transformation** ·
**verdict** · **data-quality risk** · **the reconciliation check that proves it**.

The reconciliation checks are the same ones §XXIX.7 aggregates into the signed report.

### XXIX.3.2 Employees — the largest single migration

Source: `employees` (plus `offroll_agents`, merged — see below). Target: the SmartPRS 3
**Worker/Employee** aggregate plus `entity_field_values` (spine S9) plus effective-dated
assignments.

The transformation has seven distinct passes. Each is separately dry-runnable and separately
reconciled.

**Pass E1 — type normalisation of the 34 runtime-created string columns.**
`D-…` §9 records: *"the 34 runtime-`string` columns must be re-typed (dates as DATE, booleans
as BOOLEAN, enums as FK-to-value-set)"*. Which columns are strings **on this install** comes
from `D1.6`, never from source. The date columns are the dangerous ones: `dob`, `doj`,
`dra_expiry`, `pcc_expiry`, `pcc_deadline` (`J-…` D1, D2).

```
for each date-semantic column C in {dob, doj, dra_expiry, pcc_expiry, pcc_deadline, …}:
    if D1.6 says C is DATE      → copy
    if D1.6 says C is VARCHAR   → parse with an ORDERED, DECLARED format list;
                                  on ambiguity (e.g. 03/04/2026 — d/m/Y or m/d/Y?)
                                  → DO NOT GUESS: raise a blocking exception per distinct
                                    ambiguous pattern, resolved once per install by the
                                    customer, then applied to all matching rows
    unparseable                  → load NULL + exception row + retain the raw string in
                                   `legacy_raw_values` so nothing is lost
```

`ETimeOfficeService::parseDate():208` tries `d/m/Y` and never `m/d/Y`, so a US-ordered feed
emitting `03/04/2026` is read as 3 April with no configuration available (`B-…` Appendix Q5
#15). The same ambiguity exists in these columns and MUST be resolved by the customer, not by
the migration.

**R-XXIX-035.** Date parsing during migration MUST use a declared, per-install, customer-confirmed
format list. Ambiguous patterns MUST block, not default. Every parsed value MUST retain its
source string in `legacy_raw_values` so the parse can be re-audited.

**Pass E2 — duplicate-column reconciliation.** `aadhaar` ↔ `national_id` and
`employment_type` ↔ `employment_stage` are duplicate pairs; the back-fill migration
`2026_08_28_000100:86-113` populated only *some* rows (`J-…` §9 TRANSFORM employees (b)).
Resolution rule, applied in order, with the rule recorded per row: both populated and equal →
take either; one populated → take it; both populated and different → **blocking exception**;
neither → NULL + exception.

**Pass E3 — case and vocabulary normalisation.** `dra_status`, `pcc_status` and the seat-free
statuses. `SEAT_FREE_STATUSES` recognises `exited`, `resigned`, `terminated`, `left`,
`absconded`, but **no path in the employee subsystem can produce them** — they can only have
arrived by import or direct SQL (`D-…` §9; `D-…` PO-16). Every occurrence therefore needs a
data audit per tenant before mapping.

**Pass E4 — lifecycle split.** Three orthogonal dimensions are currently conflated:
`deleted_at` (soft delete), `archived_at`/`backup_due_at` (archive, with a 3-day grace and a
JSON snapshot in `employee_archives.snapshot`), and `status` (`active`/`inactive`, **rewritten
on every save** — `D-…` §9: *"Binary Active/Inactive rewritten on every save cannot support
exit, notice, suspension or LOA"*). These become an explicit lifecycle state plus separate
retention and archive flags.

**Pass E5 — denormalised names → foreign keys.** `D-…` §9 calls this *"the largest single
migration task in this area"*: for department, designation, branch, team and reporting manager,
names-only records, FK-only records and both-together records **coexist**. Resolution: prefer
the FK where present and consistent; where only a name is present, resolve per tenant; report
every unmatched name for HR to fix **before** load, not after.

**Pass E6 — de-duplication.** PAN, UAN, bank account, ESIC, mobile, email, national id and
device id are all "block" rules enforced only by a race-prone PHP `SELECT`
(`EmployeeFieldRules::duplicateErrors():576-611`) that also ignores soft-deleted and archived
rows; migration `2026_08_28_000100:121-124` states the unique indexes are **deliberately never
created**. Duplicates are therefore guaranteed (`J-…` blocker 3, PO-12).

**R-XXIX-036.** De-duplication MUST be a customer decision per duplicate group, never an
automatic merge. The migration presents each group with all differing field values and the
records' activity evidence (last payslip, last punch, last login); the customer nominates the
surviving record or declares the duplicates to be genuinely different people; the decision is
recorded with its actor. A merged record retains **all** `legacy_id`s.

**Pass E7 — off-roll agent merge.** `offroll_agents` is *"a second, weaker employee model with
no code, no uuid, no unique constraint, no statutory data and name-based idempotency"*
(`D-…` §9). It merges into the employee/Worker model with `engagement='off_roll'`, real codes
allocated, and the free-text `bank_details` field split into structured columns. Its `dra` and
`pcc` columns are `VARCHAR` with no comment and it is **undetermined from source** whether they
hold a status, a certificate number or an expiry date (`J-…` PO-4; `F-…` §9: *"needs manual
triage into structured items"*).

| | |
|---|---|
| **Verdict** | **TRANSFORM** (E1–E6) + **TRANSFORM** (E7) |
| **Data-quality risk** | **HIGHEST in the migration.** Non-deterministic column types, guaranteed duplicates, unresolvable name references, a status vocabulary with orphan values, and no history to migrate |
| **Reconciliation checks** | (1) `COUNT(employees)` by lifecycle state matches source, with soft-deleted and archived counted separately and explicitly. (2) Every source row has exactly one target row or a recorded merge/exclusion decision. (3) Zero unresolved name references, or an explicitly accepted list. (4) Zero unmapped status values. (5) `SUM(ctc)` matches to the paise. (6) Every date column parsed or exception-listed; zero silent NULLs |

**R-XXIX-037.** The employee migration MUST NOT proceed to load until Passes E5 and E6 have zero
outstanding items or an explicitly signed acceptance of the remaining list. These two passes are
the only ones that require material customer effort and they must not be discovered late.

**R-XXIX-038.** `also_works_for` ("Multiple companies") and the `employee_company` pivot are
captured on four surfaces and read by nothing (`D-…` PO-15; `J-…` PO-3). The migration MUST
carry the *declared* value forward as a custom field so the intent is not lost, and MUST NOT
synthesise multi-company employments. Whether multi-company employment is a SmartPRS 3
capability is a **PRODUCT OWNER DECISION owned by Part V** (`J-…` PO-3; `D-…` PO-15), listed at
§XXIX.16.2 as a decision this migration is blocked by but does not own.

## XXIX.4 The contaminated-data problem

Eight categories of SmartPRS 2 data are known to be wrong, fabricated, destroyed or exposed.
Each is stated here with its evidence, its blast radius, a recommendation, and its status as a
**PRODUCT OWNER DECISION**. None of them can be resolved by the migration engineer.

Three of them are not migration problems at all. §XXIX.4.2 is a **mispayment**. §XXIX.4.3 is a
**mispayment in both directions**. §XXIX.4.8 is a **possible personal-data disclosure with a
legal clock**. Treating them as migration tasks would be a category error.

### XXIX.4.1 Eleven months of fabricated `paid` payroll

**What.** `AppDataController::ensurePayrollHistory():2340-2380` is called on **every**
`/app/data` load (`:458`). For each of the last twelve months with no existing run it inserts a
`payroll_runs` row and a `payslips` row per employee, with
`'status' => $k === 0 ? 'draft' : 'paid'` (`:2361`). The payslips are computed
`self::computeSlip((float) $e->ctc, …)` (`:2367`) — **full CTC, no LOP, no attendance, no
salary components, no commissions, no recoveries**.

**Why it is worse than demo data.**

- `$emps` at `:297` is **self-scoped for non-privileged users** (`:268-270`). If a plain
  employee is the first person to open the app on a fresh install, the entire company's twelve
  months of payroll history is created containing **one person**, with `employees_count = 1`.
- It is **not reversible through the UI**: `generate():2362` refuses any month whose run is
  `paid` — *"A paid run already exists for &lt;month&gt;. It can no longer be regenerated."*
  **The back-fill permanently blocks real payroll for the previous eleven months of every
  company.**
- The fabricated slips feed `esiPeriodLock()` (which scans stored payslips), feed
  `payslipYtd()`, and satisfy `PayrollLock::isPeriodFinalised()` — which then **blocks statutory
  configuration changes dated into those months.**

**Identification.** No single reliable discriminator exists. Four heuristics, all in `D9`:
`employees_count` inconsistent with the real headcount; `net_total = 0` at insert; no
`calc_note`; no `period_start` (`A-…` §9). A fifth, stronger signature: `net` exactly equal to
`ctc / 12` with one or zero earning lines and zero deduction lines (`D9` DEF-P01b).

**Blast radius.** Up to eleven months × every company × every employee, on **most live
databases** (`A-…` OQ-5: *"most live databases contain fabricated `paid` runs with full-CTC
payslips"*). Contaminates YTD figures, ESI period locks, finalised-period locks and any
reconciliation that trusts `payslips`.

**Options.**

| Option | For | Against |
|---|---|---|
| **A. Quarantine — migrate to a segregated, clearly-marked structure, excluded from every total (recommended)** | Nothing is destroyed; the reconciliation can prove the exclusion; the customer can see exactly what was fabricated; a false positive is recoverable | Requires the heuristics to be run and reviewed per install |
| B. Delete before migration | Cleanest target | Destroys evidence of the defect; a false positive destroys a real run; irreversible |
| C. Migrate as-is, marked "unverified" | Least work | Contaminates every payroll total in SmartPRS 3 and every statutory register derived from it; makes the reconciliation report meaningless |

**Recommendation: Option A.** Quarantine, with a per-run human review of any run matching only
one or two heuristics. A run matching **three or four** heuristics is quarantined
automatically; a run matching **one or two** is escalated for review; a run matching **none** is
migrated normally.

**> PRODUCT OWNER DECISION D-XXIX-01.** *What happens to eleven months of fabricated `paid`
payroll on every existing install?* — recorded by `A-…` OQ-5 as **blocking migration**:
*"Nothing else in the migration can be planned until this is answered."* Also `K-…` OQ 5 and
`M-…` Q-6.

**R-XXIX-046.** Fabricated payroll runs and payslips MUST be identified by the four-plus-one
heuristic set, MUST be quarantined rather than deleted, MUST be excluded from every figure in
the reconciliation report, and MUST be listed individually in an annex to it with the heuristics
each matched.

**R-XXIX-047.** Because a fabricated `paid` run permanently blocks the real run for that month,
the migration MUST report, per company, **which months have no real payroll** and MUST present
that list to the customer as a finding, not as a data-quality footnote. Those months' payroll
was never run.

### XXIX.4.2 LOP leave paid in full — a mispayment, not a migration task

**What.** Payroll decides paid-versus-unpaid from `leaves.type_id`. `LeaveController::apply()`
writes `type_name` and **never** `type_id`. Verified by grep across `app/`: two reads, **zero
writes** (`E-…` §2, DEF-LVE-02). So `type_id` is always NULL, `paid` is always true, and the
`continue` that skips unpaid leave is unreachable. `paidLeaveDates()` has the same defect in a
different shape: `(int)($lv->type_id ?? 0)` yields `0`, which is never a key in `$paidMap`, so
its `array_key_exists` default `true` fires.

Evidence: insert at `LeaveController.php:364-378`; consumers at
`PayrollGenController.php:1063-1067` and `:743-746`. Severity **CRITICAL**.

**Consequence.** *"Every approved leave — including leave explicitly filed as 'Loss of Pay' —
is credited as a paid present day. LOP deductions never happen through the leave route. Direct
salary overpayment."*

There is a second-order effect: the sandwich rule's "covered" test uses the same broken
`paidLeaveDates()`, so it currently treats LOP leave as coverage and **will not fire across it**
(`E-…` §7A).

**Blast radius.** Every approved leave since go-live that overlapped a generated payslip.
`D8.2` and `D8.3` size it in days and in rupees per employee per period. This is a data query,
not an estimate — but it has never been run.

**The three questions the Product Owner must answer, in order.**

1. **How far back must it be corrected?** (`E-…` PO-01.)
2. **Is the overpayment recovered, written off, or disclosed?**
3. **Are affected employees told?**

**Options.**

| Option | For | Against |
|---|---|---|
| **A. Quantify, write off historically, correct forward (recommended)** | Recovering months-old salary from employees is industrially and often legally fraught in India; the amounts per employee are typically small; the defect is the vendor's, not the employee's | An accounting write-off must be recognised; the customer's auditor will see it |
| B. Recover through future payroll | Restores the correct position | Recovery from employees for an employer-side software defect invites dispute and, for employees who have left, is uncollectable |
| C. Disclose to employees without recovery | Most transparent | Invites claims in the opposite direction and may surface other grievances |
| D. Do nothing and migrate silently | No effort | Migrates a known, quantified, unlawful-in-effect overpayment into a new system and forecloses the customer's own choice. **Not recommended under any circumstance.** |

**Recommendation: Option A**, with the quantification supplied to the customer per employee per
period whatever they choose, and the decision recorded in the sign-off artefact.

**Critically:** SmartPRS 3 **fixes** this defect. Therefore the first SmartPRS 3 payroll run
will deduct LOP where SmartPRS 2 did not, and net pay for affected employees will **drop**.
That is a **correct outcome**, and §XXIX.7.3 requires it to be reported as a success, not as a
reconciliation failure. It must also be communicated to affected employees **before** the first
run, not discovered by them on a payslip.

**> PRODUCT OWNER DECISION D-XXIX-02.** *The LOP mispayment: blast radius, recovery, write-off
or disclosure, and employee communication.*

**R-XXIX-048.** The LOP blast radius (`D8.2`, `D8.3`) MUST be quantified per employee, per
period, in rupees, and MUST be presented to the customer before Gate G-3. The migration MUST NOT
proceed to load leave data without a recorded disposition.

**R-XXIX-049.** Historical leave rows MUST migrate with their recorded `days` and an explicit
`legacy_paid_treatment='paid_regardless_of_type'` marker, so that any future audit can see that
the historical treatment was wrong and known.

### XXIX.4.3 Loan `outstanding` is unreliable — balances cannot be trusted

**What.** Set out in full at §XXIX.2.9. In short: `loanEmiDue()` reads five columns that do not

has been taken**.

**Options.**

| Option | For | Against |

| B. Migrate `loans.outstanding` as the opening balance | Trivial | Migrates a figure that is structurally meaningless. **Not acceptable.** |
| C. Derive from `loan_recoveries` alone | Uses real evidence | `loan_recoveries` has **no index on any column**, its rows for regenerated runs were **hard-deleted** at `:2448`, and orphaned rows exist. It is incomplete by construction |

### XXIX.4.4 Commissions stranded by an enum mismatch

**What.** The migration creates `commissions.status ENUM('provisional','confirmed','reversed')`
(`2026_01_01_000300:80`). Every code path writes `'pending'`, `'approved'` or `'rejected'`
(`IncentiveController:81`, `:238`; `SchemeController:644`, `:839`, `:901`), and
`commissionByEmployee():605` filters on `where('status','approved')`.

On strict MySQL every commission insert **throws** `SQLSTATE[01000] Data truncated`. On
non-strict MySQL the status is **silently blanked**, so no commission is ever `approved` and
**no commission ever reaches a payslip**. The project has a standard remedy for exactly this —
`SchemeController::ensure():102-117` widens a legacy ENUM to VARCHAR — and applies it only to
`incentive_schemes`, never to `commissions`. Compare `2026_06_24_000100_widen_payroll_runs_status.php`,
which exists solely because the identical problem bit `payroll_runs.status` in production.

**Impact.** *"On a freshly migrated database, commissions, incentives and arrears never pay."*
Severity **CRITICAL** (`A-…` DEF-P03).

**Note the asymmetry.** Older installs (created before the enum was tightened, or with the
runtime widening applied) may have working commissions; **freshly migrated installs** do not.
So the affected population is a function of install history — `D9`'s `declared_enum` probe and
status census answer it per install.

**Blast radius.** On affected installs: every commission claim since the install was migrated.
For a collections customer this may be the **majority of variable pay**, and the agents were
never paid it through payroll. Whether they were paid outside payroll is a question only the
customer can answer.

**Options.**

| Option | For | Against |
|---|---|---|
| **A. Migrate all commission rows with their observed status, reconstruct the intended status from `commission_payments` and `commission_logs`, and quantify unpaid claims for the customer (recommended)** | Recovers the intent from the ledger and the audit prose; nothing is lost; the customer learns what was never paid | The audit prose is English text in a `varchar(1000)` and will not always resolve |
| B. Migrate as-is with blank statuses | Trivial | Carries a stranded population forward invisibly |
| C. Assume all blanks were `approved` | Makes the numbers "work" | **Fabricates an approval.** Not acceptable |

**Recommendation: Option A.** Unresolvable rows load with `status='UNKNOWN_FROM_MIGRATION'`
(R-XXIX-014) and are listed. The **unpaid-claim value** is reported to the customer as a finding.

**> PRODUCT OWNER DECISION D-XXIX-04.** *Stranded commissions: what is owed, to whom, and is it
paid?*

### XXIX.4.5 Cross-midnight attendance recorded as two days

**What.** No ingest path is shift-aware. Every one of the nine writers sets `log_date` to a
calendar date (`B-…` Appendix Q2). For a 22:00–06:00 shift the 22:00 IN gets `log_date = D` and
the 06:00 OUT gets `log_date = D+1`. `pairPunches()` groups strictly by `emp_code|log_date`
(`AttendanceReportController.php:119-123`), so:

- day D shows an open session, `last_out = —`, `total_work = 0`, and an early-exit measured
  against a 06:00 shift end on D+1 that no punch can reach — **≈ 480 minutes of phantom early
  exit every night** (`summarise():729-735`);
- day D+1 shows an orphan OUT;
- `presentDays()` counts **two** present days for one shift (`PayrollGenController.php:211-216`);
- if D is 30 September and D+1 is 1 October, **the two halves fall in different payroll months**;
- and because `first_in_min = hour*60 + minute` (`:741`), a 00:15 arrival against a 22:00 start
  computes `max(0, 15 − 1320) = 0` — **the night worker is never late.**

**Blast radius.** Every night-shift employee, every night, for the life of the install — but
only on installs that actually run an overnight shift. `D9`'s overnight-shift probe and the
orphan-punch query size it. `B-…` OQ-B-01 notes that `SELECT name, start_time, end_time FROM
shifts` per tenant is needed to know whether **any** customer runs one today.

**Options.**

| Option | For | Against |
|---|---|---|
| **A. Migrate punches 1:1 (unchanged), derive a shift-aware `attendance_date` in SmartPRS 3, and FREEZE historical payroll (recommended)** | Punch evidence is untouched and the derivation is correct going forward; frozen payroll means no historical figure changes | The derived history will not match the frozen payroll for night-shift employees, and that difference must be explained, not hidden |
| B. Re-attribute historical punches and recompute historical payroll | Internally consistent | Changes what employees were paid. Requires the **historic** roster, which the name-keyed `roster` may not support (`B-…` §9). Unacceptable without a specific customer instruction |
| C. Leave the derivation calendar-based to match history | No divergence | Perpetuates the defect. Rejected |

**Recommendation: Option A.** The attendance-day rule is configuration in SmartPRS 3 (spine
S10), and its first value is set by the policy interview (§XXIX.5.2). Historical night-shift
attendance is derived under the **new** rule and clearly labelled as a re-derivation, while
historical payroll stays frozen at what was actually paid. Expect a manual reconciliation for
night-shift employees, and say so to the customer in advance.

**> PRODUCT OWNER DECISION D-XXIX-05.** *The correct attendance day for a cross-midnight shift*
— (a) the shift's start date owns the whole shift; (b) the calendar date of the first punch;
(c) a fixed day-boundary hour — *and whether historic night-shift punches are re-attributed.*
(`B-…` OQ-B-01.)

### XXIX.4.6 PCC `'overdue'` values destroyed by a migration

**What.** Migration `2026_08_27_000100:26-29, :60-66` retired the stored PCC `'overdue'` status
and rolled affected rows back to `'pending'`, on the explicitly stated basis that *"Compliance
Alerts already derives overdue from PCC Deadline / PCC Expiry"*. **It does not.**
`pcc_deadline` is selected by `scan()` (`:57`) and **never evaluated** — there is no reader
(`F-…` DEFECT-F-16, severity HIGH).

So the migration **destroyed** data in favour of a derivation that was never implemented. Every
agent who was genuinely overdue on a Police Clearance Certificate now reads as `pending`, and
nothing computes otherwise.

**Blast radius.** Every employee whose PCC was recorded as overdue at the moment the migration
ran, on every install that ran it. `D9`'s PCC probe reports the current distribution and whether
the migration ran here; the destroyed values exist only in backups taken before it.

**Options.**

| Option | For | Against |
|---|---|---|
| **A. Recover from a pre-migration backup where one exists; where none exists, re-derive from `pcc_deadline` and re-assert with the customer (recommended)** | Restores a regulated compliance fact | Depends on backup availability, which for on-prem is unknown and for SaaS depends on retention |
| B. Re-derive from `pcc_deadline` only | Simple; uses data that survived | The deadline may itself be unpopulated, and the derived state is not the same fact as the recorded one |
| C. Accept the loss and treat all PCC states as `pending` until re-verified | Honest | Every affected agent must be re-verified, which is the customer's cost |

**Recommendation: Option A, falling back to C** with an explicit re-verification list. This is
a regulated compliance record for a population subject to RBI recovery-agent norms; "we lost it"
is a statement the customer must make knowingly, not one the migration makes for them.

**> PRODUCT OWNER DECISION D-XXIX-06.** *Is the destroyed PCC `'overdue'` data recoverable from
backups, and should it be restored?* (`F-…` §12 item 7.)

### XXIX.4.7 The audit chain is already broken in four places

**What.** Four code paths insert into `activity_logs` **directly**, with no `prev_hash` and no
`row_hash`: `RequestController.php:1382-1387`, `:1424-1429`, `:1444-1449`, `:1822-1827` —
commission approvals carrying a DRA/compliance/grievance warning, and bounces.
`Audit::verify():118-121` treats a null `row_hash` as a legacy row, **skips it and resets
`$prev` to `'GENESIS'`**, which is what makes these inserts chain-**breaking** rather than
merely unaudited (`E-…` NEW-AUD-104).

Two further direct writers exist elsewhere: `ReportController::export` and
`MasterController::draGateWarning` (`H-…` §9, UD-05) — so *the audit-trail report's own export
action pollutes the chain it reports on.*

Three structural problems compound it: the chain is **global across tenants**, not per tenant
(`G-…` §9); the columns are added **at runtime** and never verified on read (`J-…` PO-18); and
`Audit::record()` is **fail-soft**, so a business action can succeed with no audit row at all
(`J-…` §10 item 34).

**Consequence.** The existing audit trail **cannot migrate as verified history**.
`M-…` §9 states it plainly: *"migrate rows as historical evidence; **do not migrate the chain**
— it will not verify."* `E-…` PO-14: *"Recommend migrating with an explicit 'pre-migration,
unverifiable' marker."*

This matters commercially because the product **sells** a compliance report backed by this
chain (`L-…` §9).

**Options.**

| Option | For | Against |
|---|---|---|
| **A. Migrate rows as `pre_migration_unverified`, anchor a fresh per-tenant chain at the migration event, and state the position in the sign-off artefact (recommended)** | Honest, preserves the content, and gives SmartPRS 3 a verifiable chain from a known instant | The customer learns their existing audit trail is not tamper-evident. That is a true fact they need |
| B. Re-chain the migrated rows | Produces a verifiable-looking chain | **Manufactures evidence.** A re-chained history proves only that the migration hashed it. Not acceptable |
| C. Do not migrate the audit trail | Cleanest | Destroys the content, which does have investigative value even unverified |

**Recommendation: Option A.** Additionally, the migration itself writes a **first anchor row**
into the new ledger recording the source install, the schema fingerprint, the row counts and the
break count, so the boundary between unverified and verified history is itself an audited fact.

**> PRODUCT OWNER DECISION D-XXIX-07.** *Does `activity_logs` migrate as verified history?
(It cannot.) Is the customer told, and in what terms?* (`E-…` PO-14; `J-…` PO-18.)

**R-XXIX-050.** The migration MUST write an audit anchor into SmartPRS 3's ledger recording:
source install id, schema fingerprint, per-entity source and target counts, the reconciliation
report hash, the operator, and the instant. This anchor is the genesis of the tenant's

## XXIX.5 Configuration reconstruction — the largest and least appreciated part of the migration

### XXIX.5.1 Why configuration cannot be migrated

SmartPRS 3's premise (spine S0) is that *"the product a customer experiences is configuration
running on that platform."* SmartPRS 2's premise is the opposite: its business behaviour is
written in PHP. The migration therefore has an asymmetry that no data transformation can close.

**The customer's actual policy is not in their database.** It is in three places, and only the
first of them is machine-readable:

1. **A thin layer of stored settings** — `statutory_settings` (a JSON blob), `late_policy`,
   `shifts`, `holidays`, `leave_types`, `salary_components`, `pay_cycles`, `app_settings` and
   whatever survives in `app_state`.
2. **The SmartPRS 2 PHP source**, which encodes the rest as literals. `B-…` §Q3 alone
   enumerates **thirty-two** hard-coded attendance thresholds — `09:30`, `18:30`, `480`,
   `9` hours, `4.5` hours, `0.5` day, `1.0` day, a 30-minute break block, a `0.25`-day step,
   a `60`-second repeat window, a `{strict:0.0, '1km':1.0, '2km':2.0}` geofence ladder, and a
   hidden L1 fall-through rule that is *"invisible in the UI"* — most of them not overridable at
   all. Payroll adds the 50/40 basic split, the `26`/`8` overtime divisors, the EPS
   `8.33`/`₹1,250`/`₹15,000` constants, the EDLI `0.5`, the `12` annual divisor for arrears, and
   sixteen PT state tables as `private const`.
3. **The customer's manual practice** — the spreadsheet, the WhatsApp message to the payroll
   clerk, the "we always do X for the Chennai branch" that never entered the system because the
   system could not express it. This is invisible to every query and is exactly what the rule
   engine now has to hold.

**The failure mode if this is skipped** is specific and severe: SmartPRS 3 goes live with
migrated data and default configuration, computes a different number from the same inputs on
the first payroll run, and cannot explain the difference — because the *old* number was produced
by a literal in a controller that nobody wrote down. The customer's confidence does not survive
that, and neither does the reconciliation report.

**Three instruments close the gap**, in order, each gating the next:

```
   (1) POLICY INTERVIEW          → candidate configuration, authored, versioned, unpublished
             ↓
   (2) BACK-TEST                 → replay candidate configuration against the customer's OWN
                                   historical inputs; diff against what SmartPRS 2 produced
             ↓
   (3) SHADOW RUN                → run SmartPRS 3 in parallel on live inputs for N cycles;
                                   diff every payslip line, every attendance day
             ↓
        seeded, versioned, effective-dated configuration with a signed effective-from date
```

**R-XXIX-054.** Configuration reconstruction is a **deliverable of the migration**, sized,
scheduled and staffed as such. It MUST NOT be treated as post-go-live tuning. Gate G-4 depends
on it.

**R-XXIX-055.** Every reconstructed configuration artefact MUST be created through SmartPRS 3's
ordinary draft → testing → pending_approval → published lifecycle (spine S4), MUST carry an
`effective_from` date, and MUST carry `reason` and `change_note` fields identifying it as
migration-authored with the interview response or back-test that justified it. There is no
special migration-only configuration path.

### XXIX.5.2 Instrument 1 — the structured policy interview

The question bank is **derived from the rule engine's configuration surface**, not written from
scratch. Every configurable point that Parts VI–XVIII expose becomes a question; every
SmartPRS 2 literal that Part II identified becomes a question with the literal offered as the
default answer and explicitly labelled *"the value SmartPRS 2's code currently uses"* — never
as a recommendation, and never as a statement of law.

**Structure.** Nine sections, ~180 questions, of which roughly 60 are mandatory for a minimal
payroll+attendance install and the rest are conditional. Each question carries:

```
question_key            stable identifier, referenced by the seeded artefact's change_note
section                 workweek | attendance | leave | payroll | statutory | approvals |
                        compliance | notifications | commercial
prompt                  the question as asked, in plain business language
why_it_matters          one sentence: what breaks if this is wrong
smartprs2_behaviour     what the code does today, with its file.php:line
smartprs2_configurable  yes | no | partially      ← "no" means the customer has never chosen
answer_type             single | multi | number | money | date | duration | time | free_text
options                 where enumerated
default                 the SmartPRS 2 value, labelled as such
scope_question          may this differ by company / branch / grade / employee?  (S3 dimensions)
effective_from_question has this always been the policy? if not, since when?
evidence_prompt         what document or spreadsheet supports the answer
target_artefact         the SmartPRS 3 artefact this answer configures
blocking                yes | no      ← "yes" prevents Gate G-4
```

The `smartprs2_configurable = no` questions are the important ones. They are the points where
the customer **has never been asked** — where SmartPRS 2 imposed a behaviour and the customer
either accepted it or worked around it manually. These are where the manual practice in
category (3) surfaces.

**Extract of the bank — the questions that matter most.** Every "SmartPRS 2 today" value below

**R-XXIX-056.** The policy interview MUST be conducted with a named customer signatory who has
authority over payroll and HR policy, MUST be recorded, and MUST produce a signed response
document. Every blocking question MUST be answered; a blocking question answered *"as it is
today"* MUST still be answered concretely, because *"as it is today"* is frequently a literal
the customer has never seen.

**R-XXIX-057.** Where the interview reveals a policy the customer has been applying **manually**
— outside the system — it MUST be captured as a first-class configuration artefact with its own
`effective_from`, and MUST be back-tested (§XXIX.5.3) against the customer's manual records, not
against SmartPRS 2's output. SmartPRS 2's output is by definition wrong for such a policy,
because the system could not express it. This is the point of the exercise: the manual
workarounds are the requirements that were never captured.

**R-XXIX-058.** Where an answer differs from SmartPRS 2's behaviour, the interview MUST record
whether the customer believes SmartPRS 2 has been behaving correctly. A "yes" against a known
defect (AT-06's hidden fall-through, AT-08's zero-punch full pay, PR-08's probationer
suppression) is itself a finding requiring escalation, because the customer's understanding of
their own payroll is wrong.

**R-XXIX-059.** Statutory answers (ST-01 to ST-05) MUST be routed to the named compliance owner
(spine D-03) and MUST NOT be settled by the migration engineer or by the customer alone. No
statutory value enters a rule pack without `(source_reference, effective_from, verified_by,
verified_on)` (`F-…` §12 item 1).

### XXIX.5.3 Instrument 2 — back-testing candidate configuration

The interview produces an *assertion* about policy. Back-testing tests it against the
customer's own history, before anything is published.

**Method.**

```
INPUT   the customer's historical inputs, exactly as migrated:
          attendance punches (raw, layer 1)
          leave applications (as recorded)
          salary structures and CTC as at each period
          loans, advances, commissions, incentives as at each period
          the period definition for each historical run
CANDIDATE the draft (unpublished) SmartPRS 3 configuration from the interview,
          with effective_from set to the earliest period being tested
RUN     the SmartPRS 3 engines, in dry-run mode, for N historical periods
COMPARE against the FROZEN migrated payslips and their exploded line rows
OUTPUT  a per-line, per-employee, per-period diff, classified
```

**Every difference is classified into exactly one of five classes.** This classification is the
entire point, and it is reused verbatim by the shadow run (§XXIX.5.4) and by reconciliation
(§XXIX.7.3).

| Class | Meaning | Required action |
|---|---|---|
| **C1 — MATCH** | Identical to the paise | none |
| **C2 — EXPECTED (defect corrected)** | SmartPRS 3 differs because it is fixing a known SmartPRS 2 defect: LOP now deducted, loan EMI now recovered, night shift now one day, OT now in the ESI base, arrears now taxed | Must map to a **named defect** from the register. **Reported as a success.** Quantified and communicated |
| **C3 — EXPECTED (policy change)** | SmartPRS 3 differs because the customer chose a different policy in the interview (e.g. leave now charged in working days) | Must map to a **named interview answer**. Quantified; requires the customer's explicit acknowledgement of the effect |
| **C4 — UNEXPLAINED** | A difference with no defect and no policy answer behind it | **Blocking.** Either the candidate configuration is wrong, or SmartPRS 2 was doing something not yet understood. Must be investigated to root cause |
| **C5 — DEFECT IN SMARTPRS 3** | SmartPRS 3 is wrong | **Blocking.** Fix, re-run |

**R-XXIX-060.** Back-testing MUST run against at least **twelve** historical periods where
twelve exist, or all periods where fewer exist, and MUST include at minimum: a period with a
mid-month joiner, a period with a leaver, a period with LOP, a period with overtime, a period
with a loan recovery, a period with a commission payout, a period spanning a statutory change,
and — where the customer runs one — a period containing a cross-midnight shift.

**R-XXIX-061.** Back-testing MUST exclude quarantined fabricated runs (§XXIX.4.1). Back-testing
against fabricated data proves nothing and will manufacture C4s.

**R-XXIX-062.** Gate G-4 requires **zero C4 and zero C5** differences. C2 and C3 differences are
permitted in unlimited number provided each is individually attributed, quantified and
acknowledged.

**R-XXIX-063.** Every C2 difference MUST carry the money delta per employee per period, and the
aggregate MUST be presented to the customer **before** go-live, because it is the size of the
change their employees will see on their first SmartPRS 3 payslip.

**Worked example — the LOP correction.** Realistic figures; the arithmetic is illustrative, and
every rate shown is *the value SmartPRS 2's code currently uses*, not an assertion of law.

```
Employee    R. Kulkarni, EMP-0416, Hyderabad Collections
Period      01-Aug-2026 – 31-Aug-2026    (calendar month; 31 calendar days; 26 working days)
CTC         ₹4,80,000 p.a.  →  gross ₹40,000.00 per month
Leave       12-Aug-2026 – 14-Aug-2026, type "Loss of Pay", status approved, days 3

SmartPRS 2 result (migrated, frozen)
  Paid days                        26.00 of 26
  Basic                          ₹20,000.00        (50% of gross — a hard-coded literal)
  HRA                            ₹ 8,000.00
  Special allowance              ₹12,000.00
  Gross                          ₹40,000.00
  LOP deduction                  ₹     0.00   ←   leaves.type_id was never written, so the
                                                  unpaid branch is unreachable (DEF-LVE-02)
  Net (before statutory)         ₹40,000.00

  LOP days                            3.00

Classification    C2 — EXPECTED (defect corrected)
```

### XXIX.5.4 Instrument 3 — the shadow-run harness

Back-testing proves the configuration reproduces history. The shadow run proves it handles
**live** operation, on inputs nobody has seen yet, with the customer's real staff making real
decisions.

**Definition.** For N cycles before cutover, SmartPRS 2 remains the system of record. In
parallel, SmartPRS 3 receives the same inputs and produces outputs that **nobody acts on**. Both
are diffed after each cycle.

```
                 ┌──────────────────────────────────────────────┐
  live inputs    │  SmartPRS 2  (system of record)              │→ payslips PAID
  ──────────────►│                                              │
       │         └──────────────────────────────────────────────┘
       │                                │
       │                        incremental extract
       │                     (punches, leave, master,
       │                      variable pay, approvals)
       ▼                                ▼
  ┌────────────────────────────────────────────────────────────┐
  │  SmartPRS 3  (shadow)  — same period, same employees       │→ payslips NOT paid,
  │  candidate configuration, published in the shadow tenant   │  NOT visible to employees
  └────────────────────────────────────────────────────────────┘
                                │
                          DIFF ENGINE  → per-line classification C1–C5
                                        + explainability trace for every C2–C5
```

**R-XXIX-064.** The shadow environment MUST be a separate SmartPRS 3 tenant or instance with
**payslip publication, notification, bank-file generation and disbursement disabled at the
platform level**, not merely unused. A shadow run that can email an employee a payslip is a
production incident waiting to happen.

**R-XXIX-065.** The shadow extract MUST be **incremental and idempotent**, keyed on the source
row's primary key plus a change watermark, and MUST be re-runnable without duplicating rows.

**R-XXIX-066.** The diff engine MUST compare at **line level**, not at total level. Two payslips
with the same net and different component breakdowns are a **difference**, and it is exactly the
kind that a totals-only comparison hides.

**Diff scope, per cycle.**

| Layer | Compared | Tolerance |
|---|---|---|
| Attendance day | status, worked minutes, late minutes, early-exit minutes, LOP fraction, OT minutes — per employee per day | exact; every difference classified |
| Leave | units charged, paid/unpaid treatment, resulting balance | exact |
| Payslip lines | every earning and deduction, by code, in paise | **exact to the paise** |
| Payslip totals | gross, total deductions, net, employer contributions | **exact to the paise** |
| Statutory | PF, EPS, EDLI, ESI, PT, TDS, LWF per employee | exact; differences must map to a named defect or interview answer |
| Loans / advances | EMI recovered, closing balance | exact |
| Commission / incentive | amount, TDS, net payable, payout routing | exact |
| Run totals | employee count, gross total, deduction total, net total | **exact to the paise** |

**R-XXIX-067.** Every C2–C5 difference MUST carry SmartPRS 3's full explainability trace (spine
S15) and the corresponding SmartPRS 2 figure. A diff line without a trace is a programming
error (Law 4).

**Acceptance criteria for the shadow run** — these are also the parallel-run acceptance criteria
in §XXIX.8.3:

| # | Criterion |
|---|---|
| SR-1 | **Zero C4 (unexplained)** differences in the final cycle |
| SR-2 | **Zero C5 (SmartPRS 3 defect)** differences in the final cycle |
| SR-3 | Every C2 difference maps to a named entry in the defect register, and the aggregate money delta is signed by the customer |
| SR-4 | Every C3 difference maps to a named interview answer, and the aggregate money delta is signed by the customer |
| SR-5 | Employee count matches exactly |
| SR-6 | `SUM(payslip lines) = run totals`, exactly, in SmartPRS 3 (spine S11) |
| SR-7 | Every exception the preview raises is either resolved or explicitly accepted |
| SR-8 | The customer's payroll operator has run the cycle themselves, unaided, at least once |
| SR-9 | The trace for a randomly sampled payslip line satisfies the customer that they can defend the number to an auditor |

**R-XXIX-068.** SR-8 is not a courtesy. A shadow run executed only by Ametecs proves the
software works and proves nothing about whether the customer can operate it. Go-live is a
handover, and the handover is tested here or it is tested on the first real payroll.

**R-XXIX-069.** The number of shadow cycles is **PRODUCT OWNER DECISION D-XXIX-13**, with a
recommendation of **two full payroll cycles** for a standard install and **three** for any
install with: a cross-midnight shift, more than one company, an active DRA payment gate, a
commission population above 100, or a C2 aggregate exceeding an agreed money threshold.

### XXIX.5.5 From reconstruction to seeded configuration

**R-XXIX-070.** Reconstructed configuration MUST be published with an `effective_from` equal to
the **cutover date**, not backdated — with one exception (R-XXIX-071). Backdating a
reconstructed policy would silently change how migrated historical records resolve, and
historical records are frozen (R-XXIX-044).

**R-XXIX-071.** The single exception is configuration required to **explain** history: the
statutory rate rows decomposed from `statutory_settings` (§XXIX.3.10) are dated from the
tenant's earliest payroll run so that a historical payslip's statutory lines can be resolved
"as at" their own period (spine S4). These rows MUST be marked
`provenance='reconstructed_for_history'` and MUST be excluded from forward resolution unless the
customer explicitly confirms each one still applies.

**R-XXIX-072.** Every published migration-authored artefact MUST record, in `reason` and
`change_note`: the interview `question_key` or the back-test finding that produced it, the
signatory, and the date. Three years later, "why is the LOP basis 26 days?" must be answerable
by a single lookup.

**R-XXIX-073.** Where the customer cannot answer a blocking question, the migration MUST NOT
select a default. It MUST escalate. A silently-defaulted policy is exactly the failure mode
SmartPRS 2 institutionalised, and repeating it at migration time would embed it in the new
system's first version.

**R-XXIX-074.** The **conflict detector** and the **regression harness** (spine S6) MUST be run
against the complete reconstructed rule set before publication. Publication is blocked on any
ambiguous pair (equal specificity, equal priority, overlapping conditions), per spine S3.2 —
ambiguity is a configuration error, never a silent coin-toss.

**Configuration reconstruction effort — indicative and PROVISIONAL.**

| Activity | Indicative effort per install |
|---|---|
| Policy interview preparation (pre-filling from the Discovery Pack) | 1–2 days |
| Interview sessions (payroll, attendance, leave, statutory, approvals, compliance) | 2–4 days elapsed, customer-side effort comparable |
| Candidate configuration authoring | 3–5 days |
| Back-test cycles and C4/C5 resolution | 5–15 days, **highly variable** — this is where unknown SmartPRS 2 behaviour surfaces |
| Shadow run (2–3 cycles) | 2–3 calendar months elapsed, ~2 days effort per cycle |
| Statutory verification by the compliance owner | Ametecs-side, once per rule pack, amortised |

The back-test line is the one that will move. It is a function of how much of the customer's
policy lived in category (3) — the manual practice — and that is unknowable until the interview
runs. **PROVISIONAL per R-XXIX-002.**

## XXIX.6 The migration tooling

### XXIX.6.1 Shape

Five stages, each independently runnable, restartable and dry-runnable, over an explicit staging
schema. The tooling is a **SmartPRS 3 module** (`Migration\Legacy`), not a collection of
scripts, because it must be versioned, tested, and auditable years after the fact.

```
  SmartPRS 2 DB (READ-ONLY)      Discovery Pack (signed)
          │                              │
          ▼                              ▼
    ┌─────────────┐   profile + fingerprint + dispositions
    │  1 EXTRACT  │◄───────────────────────────────────────┐
    └─────┬───────┘   raw, verbatim, hashed                │
          ▼                                                │
    ┌─────────────┐   staging.stg_<entity>                  │
    │  2 TRANSFORM│   typed, mapped, per-profile variant    │
    └─────┬───────┘                                         │
          ▼                                                 │
    ┌─────────────┐   invariants, referential closure,       │
    │  3 VALIDATE │   money identities, uniqueness           │
    └─────┬───────┘   → exceptions, NO writes to target      │
          ▼                                                 │
    ┌─────────────┐   idempotent upsert into SmartPRS 3      │
    │  4 LOAD     │   inside a per-entity transaction        │
    └─────┬───────┘   with legacy_source / legacy_id         │
          ▼                                                 │
    ┌─────────────┐   counts, sums, per-entity checks,       │
    │  5 RECONCILE│   tolerance policy, signed report ───────┘
    └─────────────┘
```

**R-XXIX-075.** Each stage MUST be separately invocable, MUST record its own start, end,
row counts and outcome, and MUST be safe to re-run. A stage that has completed MUST be
skippable by a subsequent run without re-doing its work, and MUST be forcibly re-runnable with
an explicit flag.

### XXIX.6.2 Extract

**R-XXIX-076.** Extract MUST copy source rows **verbatim** into staging, with no type coercion,
no trimming, no normalisation and no filtering except an explicitly declared and logged one. The
raw row is retained alongside the transformed one, because every later question ("was this
already NULL, or did we null it?") is answered from it.

**R-XXIX-077.** Extract MUST record, per source row, a SHA-256 of its canonical serialisation,
so that a re-extract can prove the source has not changed under the migration.

**R-XXIX-078.** Extract MUST introspect the source table's actual columns (R-XXIX-003) and MUST
record which of its expected columns were **absent** on this install. An absent column is data,
not an error — `installments_paid` exists only on installs where payroll has run.

**R-XXIX-079.** Extract MUST be chunked with a bounded memory ceiling and MUST NOT load a whole
table into memory. `attendance:dedupe` loads the entire `attendance_logs` table into PHP memory
(`DedupeAttendance.php:42-45`) and this is a documented production failure mode
(`B-…` §Q7); the migration tooling must not repeat it.

### XXIX.6.3 Transform

**R-XXIX-080.** Every transformation MUST be a named, versioned, individually testable unit with
a declared input shape, a declared output shape and a declared **profile applicability** (which
schema fingerprints it applies to). Selecting a transformation variant by anything other than
the registered profile is forbidden.

**R-XXIX-081.** A transformation MUST NOT silently drop a field. Every source field is either
mapped, explicitly discarded with a recorded reason, or raised as an exception. SmartPRS 2's
`ApprovalService::safeRow():265` silently discards unknown columns and has caused at least nine
documented field losses (`E-…` PO-13); the migration must be structurally incapable of the same
behaviour.

**R-XXIX-082.** Transformations MUST be **pure**: same input plus same profile plus same
mapping table yields the same output. No clock access except an injected migration instant, no
randomness, no network.

**R-XXIX-083.** Every mapping decision (a name resolved to an id, an enum value mapped, a
duplicate group merged, a date format chosen) MUST be recorded in `mig_mappings` with its rule,
its confidence and — where a human decided — the actor. The mapping table is an input to the
next run, so a decision made once is not re-asked.

### XXIX.6.4 Validate

Validation runs against staging and **never writes to the target**. It is the gate that makes a
dry run meaningful.

**The invariant classes, all mandatory:**

| Class | Examples |
|---|---|
| **Structural** | every NOT NULL target column populated; every declared type parseable; every string within length |
| **Referential** | every FK resolves; no orphan without a recorded disposition (R-XXIX-015); no reporting-manager cycle |
| **Uniqueness** | every target unique constraint satisfied, **with `tenant_id` participating** (Law 6) |
| **Tenancy** | `tenant_id NOT NULL` on every business row; zero cross-tenant references; zero rows attributed to the platform sentinel by accident |
| **Money** | `SUM(payslip lines) = payslip totals` exactly; `gross − deductions = net` exactly; `SUM(payslips) = run totals` exactly; no money value in a string or a JSON blob in the target (Law 7) |
| **Temporal** | no effective range overlaps within an artefact and scope; no gap in a `continuous` artefact; no `effective_to < effective_from`; no future-dated historical record |
| **Vocabulary** | every source enum value mapped; zero `UNKNOWN_FROM_MIGRATION` without an exception row |
| **Contamination** | every contaminated row carries its disposition; zero quarantined rows in a production-visible total |

**R-XXIX-084.** Validation MUST classify each failure as **BLOCKING** (the load cannot proceed
for this entity), **WARNING** (the load proceeds, the row is flagged and listed) or **INFO**.
The severity of each check is declared, not decided at run time.

**R-XXIX-085.** The load MUST NOT run for an entity with an outstanding BLOCKING validation
failure. There is no override flag. An accepted BLOCKING failure requires the check's declared
severity to be changed, which is a code change under review — deliberately, so that waiving an
invariant leaves a trace.

### XXIX.6.5 Load

**R-XXIX-086.** The load MUST be **idempotent**: re-running it MUST NOT create duplicates. Every
target row is keyed by `(legacy_source, legacy_table, legacy_id)` and upserted on that key.

**R-XXIX-087.** The load MUST be **restartable**: it MUST record a per-entity, per-chunk
watermark, and on restart MUST resume from the last committed chunk. A migration that must be
restarted from zero after eleven hours is a migration that will be run under pressure with
checks skipped.

**R-XXIX-088.** Each entity's load MUST run inside a transaction per chunk, and the chunk size
MUST be configurable. On failure the chunk rolls back, the error is recorded with the offending
row's `legacy_id`, and the run halts or continues per the entity's declared failure policy.

**R-XXIX-089.** The load MUST run with the target's ordinary write service (spine S9's
`EntityWriteService` for employees, and the equivalent for each aggregate) wherever one exists,
so that validation, uniqueness, audit and events are the **same** as for any other write. Where
volume makes that impractical (punches, payslip lines), a bulk path is permitted **only** if it
asserts the same invariants and writes the same audit summary, and this MUST be justified per
entity.

**R-XXIX-090.** Load order MUST be declared as a dependency graph, and the tooling MUST refuse
to load an entity whose dependencies have not completed successfully.

### XXIX.6.6 Bidirectional traceability

**R-XXIX-091.** Every SmartPRS 3 record created by migration MUST carry, permanently and
indexed: `legacy_source` (install id), `legacy_table`, `legacy_id`, `migration_run_id` and
`transform_version`. Every staging row MUST carry the `target_id` it produced. Both directions
MUST be queryable:

- **Forward:** *"where did this SmartPRS 3 payslip line come from?"* → the source `payslips` row,
  its `earnings` JSON key, the transform version that exploded it, and the run that loaded it.
- **Backward:** *"what became of SmartPRS 2 row `employees.id = 4417`?"* → the target employee,
  or the merge decision that folded it into another, or the exclusion decision and its reason.

**R-XXIX-092.** Traceability MUST survive the decommissioning of SmartPRS 2. The
`legacy_*` columns are permanent, not a migration-window convenience, because a payroll dispute
three years hence will ask exactly these questions.

### XXIX.6.7 Dry runs and the exception report

**R-XXIX-093.** Every entity MUST support a **dry run** that performs extract, transform and
validate, produces the full exception report and the reconciliation figures, and writes nothing
to the target. A dry run is the unit of rehearsal.

**R-XXIX-094.** The **exception report** is a first-class deliverable, produced by every run
(dry or live), and MUST contain, per exception: severity, entity, `legacy_id`, the business key
(employee code, month, document name — something a human can act on), the check that failed,
the observed value, the expected condition, the recommended action, and an `owner` and
`status` field for tracking. It MUST be exportable to a spreadsheet, because that is how the
customer will work it.

**R-XXIX-095.** The exception report MUST be **stable across runs**: an exception that persists
keeps its identifier, so the customer can see progress rather than re-triaging the same list.

## XXIX.7 Reconciliation (brief Section 110)

### XXIX.7.1 The signed reconciliation report

**R-XXIX-098.** Every migration run — dry and live — MUST produce a **Reconciliation Report**.
The report from the final live run is countersigned by the customer and by Ametecs and is the
artefact that closes Gate G-5. It is a permanent record, hashed, and referenced from
`mig_gate_events.evidence_hash`.

**Structure.**

```
Part A   Provenance
         install ref · schema fingerprint · Discovery Pack hash · tooling version
         migration run ids · operator · start/end instants · source DB snapshot identifier
Part B   Scope
         tenants, companies and periods in scope; entities loaded; entities excluded
         and why; the Contamination Register with dispositions
Part C   The mandatory checks (§XXIX.7.2), each with source, target, variance and outcome
Part D   Explained variances — each with its explanation, its reference and its money value
Part E   Expected corrections — each with its named defect and its money value, reported
         as SUCCESS (§XXIX.7.3)
Part F   Exception summary — open, accepted, resolved, by severity and by owner
Part G   Configuration reconstruction summary — artefacts published, interview answers
         referenced, back-test C1–C5 census, shadow-run results
Part H   Statements and signatures (§XXIX.9)
```

aggregation must never be able to hide offsetting errors.

### XXIX.7.3 The tolerance policy

This is the part of reconciliation that is most often left implicit and must not be here.

**Three tolerance classes, and nothing else.**

---

**Class E — EXACT. Must match to the paise, or to the row.**

No tolerance. Not "within ₹1". Not "within 0.01%". A variance of one paisa is a failure and
halts sign-off until it is explained and either corrected or reclassified.

Applies to: every migrated historical money total (RC-04, RC-05, RC-11 to RC-19), every count
of a migrated record (RC-01 to RC-03, RC-08, RC-21 to RC-27), every internal money identity
(RC-09, RC-10), and every signed opening balance (RC-06, RC-07, RC-15).

**Why exact.** These are *copies*, not recomputations. A migrated payslip is frozen
(R-XXIX-044); its total is a fact being carried across, and there is no mechanism by which a
faithful copy can differ. A variance here means a row was lost, duplicated, mis-typed or
mis-summed. Historical payroll is also the customer's statutory record: PF, ESI, PT and TDS
have been filed against these figures, and a migration that changes them by a rupee has changed
a filed return.

**R-XXIX-102.** A Class E variance MUST block Gate G-5. It may not be waived, accepted, rounded
away or netted against another variance.

---

**Class X — EXPLAINED. May differ, with a recorded, referenced explanation.**

A variance is permitted **only** when it carries: a named cause, a reference (a defect code, an
interview `question_key`, a contamination disposition, or an exception id), a money or row value,
and a named person who accepted it.

Legitimate Class X causes, exhaustively:

| Cause | Example | Reference |
|---|---|---|
| A declared exclusion | demo attendance excluded by `source='demo'` filter | contamination disposition D-XXIX-09 |
| A quarantined contamination | fabricated payroll excluded from totals | D-XXIX-01 |
| A merge decision | two duplicate employee records merged into one | `mig_mappings` merge id |
| An orphan disposition | payslips attached to a placeholder employee | `mig_row_map` disposition |
| A retention cut-off applied at migration | notification logs older than the agreed cut-off not migrated | interview answer RT-01 |
| A recomputation SmartPRS 2 performed incorrectly | RC-30 YTD: SmartPRS 2's figure is unscoped and double-counts lots | `A-…` §9 |
| A definitional change the customer chose | RC-29 seat count under a corrected definition | `I-…` §9 item 7 |
| A source figure that is structurally meaningless | RC-06 vs `loans.outstanding` | §XXIX.4.3 |

**R-XXIX-103.** A Class X variance with no reference is a **Class E failure**. "We think it is
because…" is not an explanation.

**R-XXIX-104.** Every Class X variance MUST be quantified in rupees where money is involved and
in rows where it is not. An unquantified explanation is not accepted.

**Class C — EXPECTED CORRECTION. Expected to differ, *because SmartPRS 3 is correcting a
defect*. Reported as a SUCCESS.**

This class exists because without it the reconciliation report would record the rebuild's
central purpose as a failure.

**R-XXIX-105.** A difference caused by SmartPRS 3 correctly applying a rule that SmartPRS 2
applied incorrectly **is a success**, MUST be reported in Part E under the heading *"Defects
corrected"*, MUST NOT be counted in the failure total, and MUST NOT be described in the report
as a variance, a discrepancy, an error or an exception. The report's language matters: the
customer reads it, and the first SmartPRS 3 payroll will look different in exactly these ways.

**R-XXIX-106.** A Class C difference is admissible **only** if it satisfies all four:

1. It maps to a **named entry in the defect register**, with its `file.php:line` citation.
2. Its direction is the direction the correction predicts. *(An LOP correction can only
   **reduce** net pay. If it increases net pay, the classification is wrong and it is a C4

3. It is **quantified** per employee per period.
4. It was **disclosed to the customer before go-live**, not discovered in the report.

### XXIX.7.4 What reconciliation cannot prove

Stated explicitly, because a signed report can otherwise be read as a warranty it is not.

- It cannot prove the **source data was correct**. It proves the migration was faithful. A
  fabricated payslip faithfully migrated is still fabricated; that is what the Contamination
  Register is for.
- It cannot prove **configuration is right**. Reconciliation compares migrated facts. Whether
  SmartPRS 3 will compute the *next* payroll correctly is proved by the back-test and the shadow
  run (§XXIX.5), not here.
- It cannot prove the **statutory figures were lawful**. Not one of the ~90 statutory values in
  SmartPRS 2 carries a source citation, an effective date or a verification record
  (`F-…` §12 item 1). Reconciliation proves the migrated PF total equals the source PF total; it
  says nothing about whether either was right.
- It cannot detect data **destroyed before discovery** — `attendance:dedupe`'s unlogged deletes
  (`B-…` OQ-B-12), the PCC `'overdue'` values (§XXIX.4.6), the nine silently-dropped request
  fields (`E-…` PO-13), or pre-`Audit::ensure()` audit rows with NULL hashes. These are recorded
  as **known unrecoverable losses** in Part B and acknowledged in the sign-off.

**R-XXIX-110.** The report MUST carry a "Known unrecoverable losses" section listing every such
item found on this install, with what was lost, when, by what mechanism, and the evidence that
it cannot be recovered. The customer signs this section separately.

## XXIX.8 Cutover strategy

### XXIX.8.1 The three options, per tenant

Cutover is chosen **per tenant**, not per estate. The choice is recorded in `mig_installs` and
justified against the criteria below.

| | **A. Big bang** | **B. Parallel run for N cycles** | **C. Phased by module** |
|---|---|---|---|
| **Shape** | Freeze SmartPRS 2, migrate, go live on SmartPRS 3, decommission | Both systems live; SmartPRS 2 is the system of record for N cycles; SmartPRS 3 shadows; then the record switches | Attendance first, then leave, then payroll, then compliance — each module cuts over independently |
| **Freeze window** | Longest — the full migration plus verification | Short at each end; the shadow runs against a live SmartPRS 2 | Several short windows |
| **Rollback** | Restore the SmartPRS 2 database and resume; SmartPRS 3 data discarded | Trivial — SmartPRS 2 never stopped being authoritative | Per module, but the seams are the risk |
| **Customer effort** | Lowest total, highest concentration | Highest — two systems operated for N cycles | Medium, sustained |
| **Risk of an undetected wrong number** | **Highest** — the first real payroll is the first real test | **Lowest** — N cycles of line-level diffs before anything is paid | Medium — payroll cannot be validated until the modules it depends on are across |
| **Fits** | Small tenants; no night shift; one company; no commission population; a clean Discovery Pack | Payroll-critical tenants; any tenant with a Class C money effect above the agreed threshold; multi-company; DRA gate active | Tenants who want attendance improvements early and can tolerate a longer overall programme |

**R-XXIX-111.** **Recommendation: Option B (parallel run) is the default** for any tenant that
runs payroll in SmartPRS 2. Option A is permitted only where **all** of the following hold, and
the exceptions are recorded:

- fewer than 50 employees in one company;
- no shift crossing midnight;
- no active loan or advance population;
- no commission or incentive population;
- Class C aggregate money effect below an agreed threshold (recommendation: ₹25,000 per
  period);
- zero blocking exceptions at Gate G-3;
- the customer has run a full dry run themselves and signed the reconciliation report from it.

**R-XXIX-112.** Option C (phased) MUST NOT split payroll from the attendance and leave data it
consumes within one period. A phased plan MUST cut over attendance, leave and payroll together
at a period boundary, and may only phase *around* that core (recruitment, compliance,
letters, reporting, licensing).

**R-XXIX-113.** Whichever option is chosen, cutover MUST occur at a **payroll period boundary**,
after the final SmartPRS 2 run for the period is approved and disbursed, and before the first
input of the next period is captured. Migrating mid-period splits a period across two systems
and makes the first SmartPRS 3 run unreconcilable.

### XXIX.8.2 The parallel-run comparison harness

This is the shadow-run harness of §XXIX.5.4, promoted to a production control. The difference
is that during parallel run the inputs are **live** and the customer's own staff are operating
both systems.

**Operating model, per cycle:**

```
Day 1 of cycle        SmartPRS 2 captures inputs as normal (system of record)
Continuous            incremental extract → SmartPRS 3 shadow tenant (R-XXIX-065)
Cycle close (S2)      SmartPRS 2 payroll run generated, approved, disbursed  ← money moves here
Cycle close + 0 (S3)  SmartPRS 3 shadow run generated in the same period      ← nothing moves
Cycle close + 1       DIFF: attendance days · leave · payslip lines · statutory ·
                            loans · commissions · run totals   (§XXIX.5.4 diff scope)
Cycle close + 2       Triage: every difference classified C1–C5
Cycle close + 3..5    C4/C5 resolved; configuration corrected; shadow re-run; re-diff
Cycle close + 5       Cycle verdict recorded in mig_gate_events
```

**R-XXIX-114.** The parallel run's diff MUST be produced **automatically** and MUST NOT depend
on anyone remembering to run it. It is a scheduled job with an alert on non-completion (spine
S18 operations dashboard).

**R-XXIX-115.** During parallel run, SmartPRS 3 MUST be technically incapable of paying anyone:
disbursement, bank-file generation, payslip publication and employee notification are disabled
at the platform level in the shadow tenant (R-XXIX-064), and the disablement is asserted by a
test that runs before each shadow cycle.

**R-XXIX-116.** Every input captured **only** in SmartPRS 2 during parallel run (a manual
punch, a leave approval, a loan sanction, a master edit) MUST reach SmartPRS 3 through the
incremental extract. Any input captured **only** in SmartPRS 3 is a divergence and MUST be
blocked: during parallel run SmartPRS 3 is read-mostly, and its write surfaces are restricted to
the migration and configuration paths.

### XXIX.8.3 Parallel-run acceptance criteria

The shadow-run criteria SR-1 to SR-9 (§XXIX.5.4) are the acceptance criteria, with three
additions that only apply once real staff are operating:

| # | Criterion |
|---|---|
| SR-10 | The customer's payroll operator has completed the **final** cycle in SmartPRS 3 unaided, within the same elapsed time as their SmartPRS 2 cycle, or the difference is understood and accepted |
| SR-11 | Every operational dependency is proven on the target: scheduler heartbeat, queue worker, biometric ingest freshness, mail delivery, backup completion and **a tested restore** (spine S18). SmartPRS 2's most damaging failures come from customers running neither a scheduler nor a worker (`L-…` OQ-L-02) |
| SR-12 | The **explainability** trace has been used in anger: the customer has taken at least one real employee query and answered it from "How was this calculated?" without Ametecs' help |

**R-XXIX-117.** Two consecutive cycles MUST meet all twelve criteria before cutover is
scheduled. One clean cycle is a coincidence; two is a system.

### XXIX.8.4 Rollback

**R-XXIX-118.** Every cutover MUST have a written rollback plan naming: the trigger conditions,
the decision-maker, the maximum decision window, the restore procedure, the data-loss envelope,
and the communication to employees. The plan is rehearsed, not merely written.

| Option | Rollback mechanism | Data-loss envelope | Decision window |
|---|---|---|---|
| **A. Big bang** | Restore the SmartPRS 2 database and document tree from the pre-cutover backup; re-point DNS/access; discard SmartPRS 3 data | Everything entered into SmartPRS 3 since cutover — hence the freeze window and the "no dual entry" rule | Until the first SmartPRS 3 payroll is **disbursed**. After disbursement, rollback is no longer a technical decision but a financial one |
| **B. Parallel run** | Stop using SmartPRS 3; SmartPRS 2 never stopped being authoritative | **None** | Any time before the record switches |
| **C. Phased** | Per module, restore that module's SmartPRS 2 tables and resume; the seam re-opens | Inputs entered in the migrated module since its cutover | Per module |

**R-XXIX-119.** The pre-cutover backup MUST be **restored and verified** in a scratch instance
before the freeze window opens (R-XXIX-005). A rollback plan that depends on an untested backup
is not a rollback plan, and SmartPRS 2 has no restore path of any kind (`I-…` Q-08).

**R-XXIX-120.** After the first SmartPRS 3 payroll has been **disbursed**, rollback is
prohibited without an explicit Product Owner and customer decision recorded in writing, because
it would mean two systems both holding a record of money that moved.

### XXIX.8.5 Freeze windows

| Window | What is frozen | Typical duration (PROVISIONAL) | Why |
|---|---|---|---|
| **W1 · Configuration freeze** | No changes to SmartPRS 2 masters: salary components, late policy, shifts, holidays, leave types, pay cycles, statutory settings | From Gate G-4 to cutover | These are the artefacts the back-test validated. A change invalidates it. Also: `MasterController.php:1205` **hard-deletes** configuration rows, which would make an already-migrated payslip unexplainable |
| **W2 · Master-data freeze** | No new employees, no employee edits, no org changes | 24–48 h before cutover | The employee migration's Pass E5/E6 resolutions are keyed to a known population |
| **W3 · Transaction freeze** | No punches accepted into SmartPRS 2, no leave decisions, no approvals | The cutover window itself, typically 4–12 h | The delta extract must have a stable endpoint |
| **W4 · Payroll freeze** | The final SmartPRS 2 run is approved, disbursed and locked; no regeneration | From the final run's approval to decommissioning | Regeneration **hard-deletes** the run and every payslip in it (`PayrollGenController.php:2389-2390`). A regeneration after extract would silently change the source of an already-reconciled migration |

**R-XXIX-121.** W4 is the most important and the least obvious. **SmartPRS 2's regenerate path
destroys a run and its payslips.** Any regeneration between extract and sign-off invalidates the
reconciliation report without any signal. The freeze MUST be enforced by removing the capability
from the users who hold it, not by asking them not to use it.

**R-XXIX-122.** During W3, biometric devices continue to buffer. The cutover plan MUST state how
punches captured during the freeze are ingested — recommendation: they are ingested into
SmartPRS 3 after cutover through the normal adapter path, and the delta extract's endpoint is
set at the freeze start so no punch is ingested twice. The Smart Biometric Bridge's local
buffering (spine S10.1) makes this safe; a direct `/iclock` device may not, and its buffer depth
MUST be checked before the window length is agreed.

### XXIX.8.6 The on-premise estate

The on-premise estate is a materially different problem and is addressed separately, as required.

**Three properties make it so.**

1. **The customer controls the upgrade timing.** An on-prem customer decides when — and whether
   — to accept an update. There is no mechanism by which Ametecs can migrate them on a schedule.
2. **Some are on lapsed AMC.** And `UpdateServerController::check():238-246` **refuses
   everything** when AMC has lapsed — so a lapsed customer cannot even receive a statutory
   correction, let alone a migration (`I-…` Q-10, which frames this as *"a liability question as
   much as a commercial one"*).
3. **The update channel that would carry the migration is itself being replaced.** The client
   self-update flow is *"genuinely good"* in architecture but has *"gaps in signing, DB safety,
   worker restart and a real health check"* (`I-…` §9 item 28), and `applyPlatform()` — the
   SaaS host's own self-update — has *"copy-over rollback, unbacked-up `public/`, no wrapper
   unwrap, no DB safety"* and is verdicted **REPLACE**. Using it to deliver a migration would be
   using an unproven mechanism to perform the least reversible operation in the product's life.

**Additional unknowns, each of which must be resolved per install before an on-prem migration is
attempted:**

| Unknown | Why it blocks | Reference |
|---|---|---|
| Is a scheduler installed? | Without it, backups, subscription alerts, compliance scans, transfers, probation and absence notifications all stop **silently** — and the migration's assumptions about what has been running are wrong | `I-…` Q-09; `L-…` OQ-L-02 |
| Is a queue worker running? | Determines whether any notification has ever been delivered, and whether `subscription_alerts.status='sent'` means anything | `M-…` Q-13; `L-…` OQ-L-02 |
| Is `demo:reset` scheduled? | It runs **unconditionally at 03:30** and creates or takes over an admin account with a published password. If the scheduler runs, this is a live vulnerability on that customer's server, and it must be closed before, not during, migration | `L-…` OQ-L-01, *"the single most urgent question in this document"*; `G-…` Q-02 |
| Does `admin@smartprs.local` exist? | Same class; `OnPremWorkspaceSeeder` is not environment-gated and the README publishes the credential | `N-…` Q-09, *"the highest-urgency item in this document"*; `G-…` Q-03 |
| Are builds SourceGuardian-encoded? | `InstallController.php:84-89` checks the loader at **warn** level, so a plain-source install is permitted. Affects whether the licence system offers any protection at all, and whether the source on the machine has been modified | `I-…` Q-07 |
| Does a second licensing system exist? | `guard-runtime.php` is described in reference docs as a **parallel** licensing system running before every request via `router.php`, with the README and the build script disagreeing on whether enforcement ends up true or false. If it exists, two licence systems may contradict each other during cutover | `I-…` Q-05 |
| What is the `.lic` key-pair status? | If the shipped pair is a development pair, rotation is required before any v3 licence is issued — and **rotation invalidates every existing `.lic`** | `I-…` Q-03, Q-04 |

**The on-premise migration approach.**

**R-XXIX-123.** On-premise migration MUST be **attended**. It is performed by an Ametecs
engineer, on the customer's machine or on a copy of it, at a scheduled time, with the customer
present. It MUST NOT be delivered as an unattended update package. The update channel carries
the *software*; the *migration* is a supervised operation.

**R-XXIX-124.** Statutory content delivery MUST be **separated from the AMC gate** so that a
lapsed customer can still receive a statutory correction. This is a liability position as much
as a commercial one and is **PRODUCT OWNER DECISION D-XXIX-14** (`I-…` Q-10). It is stated here
because it also determines whether a lapsed-AMC customer can be brought to a migratable state at
all.

**R-XXIX-125.** The on-premise programme MUST be sequenced by **readiness**, not by contract
value:

```
Wave 0  SECURITY REMEDIATION — every install, regardless of migration intent.
        Remove demo:reset from the schedule; delete admin@smartprs.local and any
        demo-*@smartprs.in; contain publicly readable documents (§XXIX.4.8);
        purge plaintext passwords from wa_log. This is not migration work and is
        not gated on AMC, migration intent or commercial status.
Wave 1  DISCOVERY — Gate G-1 for every install that will migrate. Read-only,
        low-risk, can proceed in parallel across the estate.
Wave 2  REFERENCE INSTALLS — 3 to 5 installs chosen to span the schema profiles
        found in Wave 1, migrated first, with the longest parallel runs. Their
        purpose is to prove the tooling per profile.
Wave 3  PROFILE COHORTS — remaining installs, grouped by schema fingerprint, so
        each cohort reuses a proven transformation set.
Wave 4  STRAGGLERS — lapsed AMC, air-gapped, unresponsive, or single-install
        profiles. Handled individually, commercially first.
```

**R-XXIX-126.** Wave 0 MUST NOT wait for the migration programme. The security items are live
exposures on customer servers today and their remediation has no dependency on SmartPRS 3.

**R-XXIX-127.** A customer who declines to migrate MUST have a stated support position:
what they continue to receive, for how long, and specifically whether statutory rule updates
reach them. **PRODUCT OWNER DECISION D-XXIX-15.**

**R-XXIX-128.** Where an on-prem customer's SmartPRS 2 licence artefacts must be re-issued
(key rotation, `.lic` invalidation, re-activation — `I-…` §9 items 17, 18), the re-issue MUST be
sequenced **before** the migration window, never inside it. A migration that also has to
re-license the install has two independent failure modes in one window.

### XXIX.9.2 The sign-off artefact

**R-XXIX-132.** Go-live is authorised by a single **Migration Sign-off Certificate** per install,
executed by a named customer signatory with authority over payroll and HR, and by a named
Ametecs signatory. It is hashed, stored, and referenced from `mig_gate_events`.

**Contents — every section mandatory:**

```

3  WHAT WAS NOT MIGRATED, AND WHY

   reference (D-XXIX-nn), decision-maker and date.
   Explicit customer acknowledgement for:
     · fabricated payroll quarantined, and the company-months with NO real payroll

   Per §XXIX.7.4 / R-XXIX-110. Signed separately.

   Every artefact published for this tenant, its version, effective_from, and the
   interview question_key or back-test finding that justified it.
   Customer statement: "The configuration listed reflects our policy."

9  OPEN EXCEPTIONS ACCEPTED AT GO-LIVE
   Each with risk, owner, and remediation date. Zero blocking exceptions permitted.

   The completed script (U-01 … U-23), tester, date, outcome per item, defects raised
   and their status. The four non-waivable items called out.

   RESTORE TESTED, with date · monitoring and alerting live · runbook handed over ·
   named support contacts both sides

   Explicit, in plain terms:
     · The migration is faithful to the source. It does not warrant that the source
       was correct.
     · Statutory values are supplied in a signed rule pack verified by Ametecs'
       named compliance owner as at its stated effective date. Neither party warrants
       historical SmartPRS 2 statutory calculations.
     · The audit trail migrated from SmartPRS 2 is marked pre-migration unverified and
       is NOT tamper-evident. SmartPRS 3's chain is anchored at the migration event.
     · Offer and NDA acceptances migrated from SmartPRS 2 are legacy-grade evidence,
       with the gaps listed at §XXIX.3.11.

   The date SmartPRS 2 becomes read-only; the date it is shut down; where its final
   backup is held, in what form, encrypted how, for how long, and who may restore it.

   Customer signatory (name, role, date) · Ametecs signatory (name, role, date)
   Ametecs compliance owner, for section 12's statutory statement (spine D-03)
```

**R-XXIX-133.** Section 5's acknowledgement MUST be signed **before** the first SmartPRS 3
payroll run, not after. Its entire purpose is that the customer is not surprised by a correct
number.

**R-XXIX-134.** SmartPRS 2 MUST NOT be shut down at sign-off. It MUST be placed in a
**read-only** state for a stated period (recommendation: two full statutory filing cycles, and
no less than twelve months), so that any question about a migrated figure can be answered
against the source. Its final backup is retained per section 13 with an explicit restore owner.

**R-XXIX-135.** Decommissioning MUST include destruction of the Discovery Pack per its retention
clock (R-XXIX-009) and of the PII-bearing `mig_exceptions` and `mig_legacy_raw_values` rows, with
the destruction audited. The permanent tables (R-XXIX-096) hold no personal values and are
retained.

## XXIX.10 The migration runbook

### XXIX.10.1 Single-tenant cutover, hour by hour

Assumes a mid-sized tenant — one to three companies, 300–800 employees, twelve months of
history, a parallel run already completed and accepted, all gates through G-5 passed. Times are
elapsed from T-0 = the start of the transaction freeze (W3). Every step names its owner, its
verification and its abort condition.

| Time | Step | Owner | Verification | Abort if |

**R-XXIX-136.** The runbook MUST be **rehearsed end to end** against a restored copy at least
once before the live window, by the same people who will run it, with the same timings recorded.
A first execution of an eleven-hour irreversible procedure must not be the live one.

**R-XXIX-137.** Two abort points are absolute and MUST NOT be argued past: a failed backup
restore at T+0h20, and any Class E reconciliation failure at T+7h30. At both points the correct
action is to stop; nothing irreversible has happened at either.

**R-XXIX-138.** The window in the table is **PROVISIONAL** (R-XXIX-002). The load and reconcile
durations are functions of `attendance_logs` and `payslips` volume, which are unknown until D2.
The rehearsal (R-XXIX-136) produces the real numbers, and the live window is scheduled from
those, with a 50% contingency.

### XXIX.10.2 The programme plan for the estate

```
PHASE 0 · SECURITY REMEDIATION                                  runs first, independently
  Every install, SaaS and on-prem, regardless of migration intent (R-XXIX-126).
  · demo:reset de-scheduled; demo/admin accounts audited and removed
  · publicly readable document trees contained; access-log evidence captured FIRST
  · wa_log plaintext passwords purged
  · findings reported to each customer (D-XXIX-08)
  Exit: every install evidenced clean, or its exception recorded and owned.

PHASE 1 · TOOLING AND DISCOVERY                                 parallel with Phase 0
  · Discovery Pack collector built, signed, tested against a restored SaaS database
  · Discovery run across the estate; schema profile register populated
  · Estate segmented by fingerprint; profile count is the first real estimate input
  Exit: Gate G-1 for every in-scope install. THE FIRST HONEST ESTIMATE IS PRODUCED HERE,
        NOT BEFORE (R-XXIX-001, R-XXIX-002).

PHASE 2 · REFERENCE MIGRATIONS                                  3–5 installs
  · One install per major schema profile, chosen for coverage not size
  · Full path: G-1 → G-6, longest parallel runs, most instrumentation
  · Every transformation variant proven; every Class C effect measured for the first time
  · The runbook's real timings established
  Exit: two reference installs live and reconciled; tooling frozen for cohort use.

PHASE 3 · SAAS COHORTS                                          by fingerprint
  · Cohorts sized so no cohort's parallel runs overlap another's cutover window
  · Discovery → interview → back-test → parallel → cutover, cohort by cohort
  · Per-cohort retrospective feeds the tooling
  Exit: SaaS estate migrated; SmartPRS 2 SaaS read-only.

PHASE 4 · ON-PREMISE WAVES                                      per R-XXIX-125
  Wave 2 references → Wave 3 profile cohorts → Wave 4 stragglers.
  Each install attended (R-XXIX-123). Licence re-issue sequenced BEFORE the window
  (R-XXIX-128). Lapsed-AMC customers resolved commercially first (D-XXIX-14, D-XXIX-15).
  Exit: every on-prem install migrated, or holding a stated support position.

PHASE 5 · DECOMMISSIONING
  · SmartPRS 2 read-only period elapses (≥ 12 months, ≥ 2 filing cycles)
  · Final backups verified, encrypted, retained per the certificate
  · Discovery Packs and PII-bearing migration tables destroyed, audited (R-XXIX-135)
  · Permanent traceability tables retained indefinitely (R-XXIX-096)
  Exit: SmartPRS 2 shut down.
```

**Sequencing rules.**

**R-XXIX-139.** Phase 0 has no dependency on any other phase and MUST NOT be sequenced behind
them.

**R-XXIX-140.** No cohort may begin cutover until at least one install of its schema profile has
completed a full cycle through G-6. A profile with only one install *is* its own reference and
carries reference-level scrutiny.

**R-XXIX-141.** The programme MUST NOT run more concurrent cutovers than it can staff for
hypercare and for a simultaneous rollback. The binding constraint is people, not tooling.

**R-XXIX-142.** No cutover may be scheduled in a statutory filing window for the jurisdictions
the tenant operates in. The filing calendar is a hard constraint on the schedule.

**R-XXIX-143.** The programme plan MUST be re-baselined after Phase 1 and again after Phase 2.
Any estimate produced before Phase 1 completes is a placeholder and MUST be labelled as one.

## XXIX.11 Configuration surface

The migration tooling is Ametecs-operated, not tenant-configurable. Its configuration surface is
therefore small and deliberately so — but every item below is data, not code, because a
transformation rule hard-coded in the tooling reproduces exactly the problem the tooling exists
to fix.

| Setting | Scope | Storage | Who changes it | Why it is data |
|---|---|---|---|---|
| Schema profile → transformation variant map | per fingerprint | `mig_schema_profiles.divergent_columns` + transform registry | Ametecs migration lead | A new profile must not require a code release |
| Date format list, per install, per column | per install | `mig_mappings` (`mapping_kind='date_format'`) | Customer-confirmed, recorded by the engineer | Ambiguous patterns are resolved per customer (R-XXIX-035) |
| Enum value → target code map | per install, per tenant | `mig_mappings` | Engineer, customer-confirmed | Observed vocabularies differ per install (R-XXIX-013) |

| Contamination dispositions | per install, per class | `mig_contamination.disposition` | Product Owner | §XXIX.4 |
| Retention cut-offs applied at migration | per tenant, per log table | interview answer RT-01 → config artefact | Customer | There has never been one (`J-…` §9) |

| Shadow-cycle count | per install | `mig_installs` | Product Owner | R-XXIX-069 |

**R-XXIX-144.** Reconciliation tolerance classes and validation severities are **not** run-time

## XXIX.14 Edge cases and failure states

Unglamorous and specific. Each names what happens, not merely that it is handled.

**Source-side**

1. **The source schema changes between G-1 and cutover.** Detected by the fingerprint re-check
   at T+0h45. **Abort.** A customer who applied a SmartPRS 2 update mid-programme has changed
   the thing the transformations were built against.
2. **A SmartPRS 2 migration runs during the window** and invokes `attendance:dedupe`
   (`2026_08_16_000200:128`), hard-deleting punches with no log. Prevented by the read-only
   source user (R-XXIX-004) and by the freeze; if it happens anyway, the pre-cutover backup is
   the only recovery, which is why R-XXIX-005 restores and verifies it first.
3. **A payroll run is regenerated after extract**, hard-deleting the run and its payslips
   (`PayrollGenController.php:2389-2390`). Silently invalidates RC-03/04/05. Prevented by W4 and
   by capability withdrawal (R-XXIX-121); detected by the source-hash check (R-XXIX-077).
4. **`DummyDataSeeder` is run on a customer database**, hard-deleting 23 tables for whichever
   tenant has `subdomain='demo'` (`J-…` PO-15; `M-…` Q-11). Detected by the D9 demo-tenant probe.
   If a real customer is named `demo`, that is an **immediate SmartPRS 2 operational risk**
   independent of the rebuild and is escalated in Phase 0.
5. **The `app_state` blob is unparseable** on a `longText` install — possibly truncated, with no
   error ever raised. Blocking exception; no automatic normalisation (R-XXIX-021).
6. **A collection inside `app_state` is heterogeneous** (`distinct_shapes > 1`). Same: blocking,
   human-decided.
7. **A tenant's `app_state` was silently corrupted by last-write-wins** with no way to detect it
   (`K-…` OQ 6). Undetectable by definition. Mitigated only by the customer reviewing the
   normalised output before Gate G-4, and recorded as a known limitation.
8. **The source database is larger than the window allows.** Detected at rehearsal
   (R-XXIX-136). Remedy: pre-migrate immutable history (punches and payslips older than N
   months) days ahead, then migrate only the delta in the window.
9. **A source table expected by the profile is absent** on this install. Recorded as data, not
   an error (R-XXIX-078); the entity's verdict becomes `DO NOT MIGRATE — absent` and appears in
   the certificate's section 3.
10. **Two employees share an `emp_code`** because a code was freed by soft-deleting an employee
    and then reissued — `unique(tenant_id, emp_code)` permits it (`J-…` §9 Q4). Attendance
    history cannot be attributed. Blocking; resolved per employee by the customer.
11. **A punch's `emp_code` matches no employee at any date.** Loaded into `punch_events` with
    `employee_id = NULL` and `resolution='unattributable'`; counted in RC-02; never silently
    dropped (spine S10).
12. **`emp_code LIKE 'USER-%'` rows** counting as present days for a code no employee holds
    (`B-…` OQ-B-11). Contamination class 10; dispositioned before load.
13. **A commission row's status is neither vocabulary.** Loaded as
    `UNKNOWN_FROM_MIGRATION`, listed, and its money value reported (R-XXIX-014).
14. **`loan_recoveries` rows point at a deleted run.** The instalment counter is permanently
    wrong. Loaded as ledger movements attached to a placeholder run; the loan's balance comes
    from the signed statement regardless (R-XXIX-024).
15. **An `activity_logs` row has a NULL `row_hash`** — a chain break. Migrated; the break is
    counted and reported. The chain is never re-computed (D-XXIX-07).
16. **A document row has no `file_path`** (master-created rows — `H-…` §9). Loaded with
    `file_state='no_path_at_source'`; listed.
17. **A document file exists on disk with no row.** Inventoried, reported, and dispositioned by
    the customer: adopt as an orphan document, or leave behind.
18. **A file's SHA-256 differs after transfer.** Failed load for that document; retried; if it
    persists, blocking (R-XXIX-030).

**Target-side and process**

19. **The load fails mid-entity.** The chunk rolls back; the watermark holds; `--resume` picks
    up from the last committed chunk (R-XXIX-087).
20. **The load is run twice.** Idempotent upsert on `(legacy_source, legacy_table, legacy_id)`
    produces no duplicates (R-XXIX-086). Asserted by a test (§XXIX.15 T-08).
21. **A reconciliation check passes at tenant level and fails at company-month level.**
    **Failure** (R-XXIX-101). Offsetting errors must not net out.
22. **A Class C difference moves in the wrong direction** — an LOP correction that *increases*
    net pay. Reclassified as C4 unexplained and investigated (R-XXIX-106.2). This is the
    tripwire that catches a mis-attributed correction.
23. **A Class X variance has no reference.** Treated as a Class E failure (R-XXIX-103).
24. **The customer cannot answer a blocking interview question.** Escalate. Never default
    (R-XXIX-073).
25. **The customer answers "as it is today"** for a behaviour that is a defect. Recorded as a
    finding requiring escalation — their understanding of their own payroll is wrong
    (R-XXIX-058).
26. **A statutory answer is contested** (C-ESI-OT, C-ARREARS-TAX, C-PROBATION, C-PF-APPL). The
    defect is carried forward **unchanged and flagged**; the correction waits for the ruling
    (R-XXIX-108).
27. **Shadow run is skipped for time.** Prohibited by Gate G-4 for parallel-run installs; for
    big-bang installs it is precisely why R-XXIX-111's conditions are narrow.
28. **A device buffer overflows during the freeze window** and punches are lost at the device.
    Checked before the window length is agreed (R-XXIX-122); if the buffer cannot cover the
    window, the window is shortened or ingest is bridged.
29. **Punches are ingested twice** — once into SmartPRS 2 before the freeze and once into
    SmartPRS 3 after. Prevented by the delta endpoint; detected by the natural-key uniqueness
    on `(tenant, employee, instant, source)` and by RC-02.
30. **Rollback is called after disbursement.** Prohibited without a written decision
    (R-XXIX-120), because two systems would both hold a record of money that moved.
31. **The customer signs off, then discovers a wrong figure.** SmartPRS 2 is read-only, not
    gone (R-XXIX-134), and `migrate:trace` answers where the figure came from. This is the
    scenario the twelve-month read-only period exists for.
32. **An on-prem install cannot be reached** — unresponsive, air-gapped, or lapsed AMC. Wave 4;
    resolved commercially before technically (R-XXIX-127).
33. **An on-prem install has a second licensing system** (`guard-runtime.php` —
    `I-…` Q-05) that blocks the migrated application. Detected in Discovery D11; resolved before
    the window, never inside it (R-XXIX-128).
34. **A migration engineer needs production data to debug.** Prohibited. Debugging happens on a
    restored copy in an isolated environment (R-XXIX-006), and the exception report carries the
    business key needed to reason about a row without reading it.

## XXIX.18 Compliance with the seven laws

| Law | How this part complies |
|---|---|
| **1 · No business literal in code** | Every transformation rule, mapping, vocabulary, date format, retention cut-off and disposition is data in `mig_mappings` / `mig_contamination` / the transform registry, not a literal in the tooling (§XXIX.11). The one deliberate exception — tolerance classes and validation severities — is justified at R-XXIX-144 precisely because making them data would let a failing migration be made to pass |
| **2 · No schema change at runtime** | The tooling holds a **read-only** source connection (R-XXIX-004) and executes no DDL against either database outside declared migrations. Staging tables are created by migrations, not by the tooling |
| **3 · Nothing overwritten; everything versioned and dated** | Migrated history is **frozen** (R-XXIX-044); source rows are retained verbatim (R-XXIX-076) with their raw values (`mig_legacy_raw_values`); `mig_gate_events` is append-only; reconstructed configuration is effective-dated through the ordinary publish lifecycle (R-XXIX-055) |
| **4 · Every number explains itself** | Every reconciliation figure traces to its source rows through `mig_row_map` (R-XXIX-091); every back-test and shadow difference carries a full trace (R-XXIX-067); a trace-less diff line throws (T-38) |
| **5 · Authorisation server-side, declarative, fails closed** | Migration endpoints are platform-scoped, capability-gated, CI-asserted (R-XXIX-147, R-XXIX-148); `migrate:load` requires explicit live mode plus interactive confirmation (R-XXIX-145) |
| **6 · Tenancy is structural** | `tenant_id` is `NOT NULL` on every tenant-scoped `mig_*` table; RC-27 asserts **zero** NULL/0-tenant rows in the target; T-40 asserts cross-tenant isolation of migrated rows |
| **7 · Money is exact** | Every money reconciliation is computed in integer paise (R-XXIX-100); Class E admits no tolerance (R-XXIX-102); `SUM(lines) = totals` is an exact gate (R-XXIX-043); eight named tests carry literal expected values with no deltas (R-XXIX-151) |
